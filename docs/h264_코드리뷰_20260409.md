# H264 인코딩/디코딩 코드 리뷰
검증일: 2026-04-09

## 개요

H264 인코딩(MFT 인코더, AMF/NVENC/QSV 벤더 경로) 및 디코딩(MFT 디코더, Android MediaCodec), 프레임 전송(UDP 청킹) 전반을 코드 수준에서 리뷰한 결과이다.
전반적으로 LAN 스트리밍 기준 프로덕션 수준이며, 엣지 케이스에서 문제가 될 수 있는 항목을 아래에 정리한다.

---

## CRITICAL (즉시 수정 권장)

### C1. Android 디코더 — 입력 버퍼 크기 초과 시 빈 버퍼 큐잉
- **파일:** `apps/android_direct_client/app/src/main/cpp/android_video_decoder.cpp:158-160`
- **현상:** `frame.payload.size() > inputBufferSize`일 때 0바이트 빈 버퍼를 `AMediaCodec_queueInputBuffer(codec_, inputIndex, 0, 0, 0, 0)`으로 제출한다.
- **위험:** 코덱이 EOS(End of Stream)로 오인하거나 프레임이 무음 손실된다. 에러 로그도 없다.
- **수정안:** 빈 버퍼 제출 대신 에러 로그 출력 + 해당 프레임 스킵 처리.

### C2. MFT 인코더 — 출력 타임스탬프 신뢰 플래그 영구 비활성
- **파일:** `apps/native_poc/src/mf_h264_codec.cpp:1485-1490`
- **현상:** `sampleTimeOutputTimestampTrusted_`가 한번 `false`로 설정되면 복구 경로가 없다. 단일 이상치(네트워크 글리치, 인코더 일시 이상 등)로 영구적 타임스탬프 동기화 손상이 발생할 수 있다.
- **위험:** 장시간 세션에서 한 번의 타임스탬프 이상이 나머지 전체 세션의 타임스탬프 정확도를 영구 저하시킨다.
- **수정안:** 타임아웃 또는 정상 출력 연속 N회 조건으로 `true` 복구 경로 추가, 또는 인코더 리셋 시 함께 초기화.

### C3. UDP 재조립 — payloadSize 상한 미검증
- **파일:** `apps/native_poc/src/native_video_client_shared_core.cpp` (UDP assembler)
- **현상:** 첫 청크 수신 시 `assemblingPayload_.assign(assemblingExpected_, 0)`으로 버퍼를 할당하는데, `payloadSize` 필드에 상한 검증이 없다.
- **위험:** 변조 또는 손상된 패킷의 `payloadSize`가 수 GB일 경우 메모리 폭주(DoS). LAN 환경이라도 방어 코드가 필요하다.
- **수정안:** `payloadSize`에 합리적 상한(예: 16MB) 초과 시 드롭 + 경고 로그.

## HIGH (조기 수정 권장)

### H1. MFT 디코더 — pending timestamp 큐 오버플로
- **파일:** `apps/native_poc/src/mf_h264_codec.cpp:1885-1889`
- **현상:** 디코더 `pendingInputSampleTimesHns_` 큐가 512개 고정 크기이다. 디코더 정체 시 입력이 계속 들어오면 오래된 타임스탬프가 `pop_front()`로 제거되고, 출력 프레임이 잘못된 타임스탬프에 매핑된다.
- **위험:** 고부하 상황에서 타임스탬프 어긋남 → 지연 측정/동기화 오류.
- **수정안:** 순환 버퍼 또는 오버플로 시 경고 로그 추가, 또는 입력/출력 시퀀스 기반 매핑으로 전환.

### H2. Android CSD 벡터 포인터 안정성
- **파일:** `apps/android_direct_client/app/src/main/cpp/android_video_decoder.cpp:337-341, 397-405`
- **현상:** CSD-0/CSD-1 데이터를 `std::vector`에 저장하고 `AMediaFormat_setBuffer`에 포인터를 전달한다. 현재 코드에서는 벡터 재할당이 일어나지 않아 안전하지만, 리팩토링 시 use-after-free 위험이 있다.
- **수정안:** CSD 벡터에 대해 크기 변경 금지 주석 + `assert(csd0_.capacity() >= csd0_.size())` 등 방어 assertion 추가.

## MEDIUM (리팩토링 시 수정)

### M1. MFT 인코더 — pEvents 릴리스 수동 관리
- **파일:** `apps/native_poc/src/mf_h264_codec.cpp:1430-1523` (`drain_outputs` 내부)
- **현상:** `MFT_OUTPUT_DATA_BUFFER.pEvents`를 수동으로 `Release()`하는 패턴. 특정 early return 경로에서 릴리스 누락 가능성.
- **수정안:** RAII 래퍼(ComPtr 또는 scope guard)로 전환.

### M2. D3D Device Manager — 디바이스 로스 미처리
- **파일:** `apps/native_poc/src/mf_h264_codec.cpp:1011-1026` (인코더), `1621-1633` (디코더)
- **현상:** D3D11 디바이스 매니저를 초기화 시점에 설정하지만, GPU 디바이스 로스 시 리셋 로직이 없다. DXGI device removed 발생 시 MFT가 실패하고 GPU 메모리가 해제되지 않는다.
- **수정안:** 디바이스 로스 감지 시 매니저 재설정 또는 인코더/디코더 전체 재초기화 경로 추가.

### M3. 인코더 SPS/PPS 캐시 갱신 누락
- **파일:** `apps/native_poc/src/mf_h264_codec.cpp:1333-1347`
- **현상:** SPS/PPS 시퀀스 헤더를 초기화 시점에만 캐시한다. 인코더가 중간에 파라미터 변경(해상도 변경 등)을 하면 디코더가 오래된 SPS/PPS를 수신하게 된다.
- **수정안:** `MF_E_TRANSFORM_STREAM_CHANGE` 이벤트 수신 시 SPS/PPS 재추출.

### M4. MFT 디코더 reset() 후 키프레임 미요청
- **파일:** `apps/native_poc/src/mf_h264_codec.cpp:1894-1899`
- **현상:** `reset()` 호출 시 내부 상태만 초기화하고, 호스트에 키프레임 요청을 자동으로 보내지 않는다. 외부에서 수동으로 요청해야 한다.
- **수정안:** 리셋 후 키프레임 요청 플래그를 자동 설정하거나, 호출자에게 반환값으로 키프레임 필요 여부를 전달.

### M5. Android selection ack 유실 시 프레임 영구 드롭
- **파일:** `apps/android_direct_client/app/src/main/cpp/android_video_decoder.cpp:119-136`
- **현상:** `pendingSelectionGeneration_` ack이 유실되면 `staleFrameDropCount_`만 증가하고 복구 경로가 없다. 프레임이 영구적으로 드롭된다.
- **수정안:** 타임아웃 기반 selection ack 재요청 또는 일정 프레임 드롭 후 강제 복구.

### M6. MFT 디코더 — 출력 타임스탬프 누락 시 큐 매핑 오류
- **파일:** `apps/native_poc/src/native_video_client_main.cpp:1851-1867`
- **현상:** 출력 샘플에 타임스탬프가 없을 때 입력 큐에서 `pop_front()`로 대체하는데, 출력 순서가 입력 순서와 다르면(리오더링) 잘못된 타임스탬프가 매핑된다.
- **위험:** 일부 MFT 구현에서 B-frame 리오더링 시 발생 가능. 현재 H264 Baseline/Main에서는 드물다.
- **수정안:** 출력 샘플의 presentation time 기반 매칭 또는 리오더링 불가능 프로필 강제.

### M7. MFT 인코더 — async 폴링 윈도우 제한
- **파일:** `apps/native_poc/src/mf_h264_codec.cpp:1552-1588`
- **현상:** async 인코더 이벤트 폴링이 기본 1회(1ms)만 수행된다. 이벤트가 폴링 윈도우 직후 도착하면 해당 출력을 놓칠 수 있다.
- **영향:** 현재 `asyncPollMax=1` 기본값에서 실측 문제 없음 확인됨 (계획 문서 M2.5 재측정 결과). `asyncPollMax=4`는 오히려 악화.
- **수정안:** 현행 유지. 단, 제한 사항으로 문서화.

## 잘 구현된 부분

- MFT 인코더 벤더별(AMF/NVENC/QSV) 경로 분기 + `mft_auto` AMF 우선 선택 + fallback 로직
- async/sync MFT 이중 지원 + 이벤트 폴링 제어 (`REMOTE60_NATIVE_H264_ASYNC_POLL_MAX`)
- 키프레임 요청 토큰 버킷 + 최소 간격 이중 스로틀링
- 인코더/디코더 양측 타임스탬프 전파 + 6분할 병목 계측 메트릭
- `HOST_BOTTLENECK_STAGE` 9개 후보 자동 감지
- UDP 청크 순서 검증 및 프레임 조립 (`UdpH264FrameAssembler`)
- Android MediaCodec CSD 분리 + Surface 출력 통합
- 프레임 게이팅(정적 장면 스킵) + 혼잡 상태 머신 통합
