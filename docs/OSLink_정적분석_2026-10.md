# OSLink 정적 분석 — GNLink 설계 시사점 (2026-10-21~22)

대상: 이 PC 의 OSLink 설치본 x86 PE 9개(`C:\LDPlayer\OSLink\bin\`)와 OSLink 자체 로그. 분석은 별도 세션이 읽기 전용으로 했다
(대상 실행·주입·디버거·서비스/입력 조작 없음). 1차는 dumpbin·오프라인 PE 파서, 2·3차는 Ghidra 12.1.4 디컴파일(REA 경유).
**원자료는 저장소 밖 `C:\work\oslink-analysis\`**(README·q1~q7·evidence·tools.md, 근거 주소·Evidence ID·로그 줄·SHA256) 에 있고,
이 문서는 그중 **GNLink 설계에 쓰는 결론만 우리 말로** 옮긴다. OSLink 코드는 옮기지 않는다.

판정 용어: **확인** = 정적 코드에서 도출했거나 기존 로그에 기록된 사실(실행 재현 아님) · **추정** = 근거를 이은 해석 · **미확인** = 찾지
못함(없다는 뜻이 아님). 디컴파일 한계(no-return 가정·간접 호출·이름 복구 불가) 때문에 "호출자 없음" 은 부재 증거가 아니다.
**조사한 함수·경로에서 본 것을 OSLink 제품 전체의 유무로 넓히지 않는다.**

검증용 독립 대조(2026-10-21~22): PE 4개 SHA256 이 tools.md 와 일치, 핵심 문자열(`SendInput`·`SetThreadDesktop`·`SendSAS`·
`PasswordField`·`leidian_fb_rgb_mem`·`capture frame time out to many`) 존재, ldremote.exe 0x0045ef40 = `c2 04 00`(`ret 4`, q7 의
키프레임 콜백 no-op 주장), Ghidra zip SHA256 이 GitHub 공식 digest 와 일치.

## 1) 캡처 감시 — 존재·재시작 요청은 확인, API 정체(hang) 시간 감시는 미확인

- **확인**: 데스크톱 전환 알림이 재시작 플래그를 세우고, 감시 루프가 그 플래그와 capture.exe 존재를 보고 → kill → 현재 데스크톱
  (Default 또는 Winlogon)에 다시 띄운다. 루프 주기는 대기 인자(0x1f4)로 본 **약 500 ms 정적 추정**이다(실측 주기·복구 시간 아님).
- **확인(그 루프 범위)**: 디컴파일로 읽은 **이 감시 루프**에는 프레임 진행 시각이나 API 호출 경과 시간 검사가 없다. 다른 함수·
  프로세스의 감시 여부는 **미확인**이다.
- **확인**: DXGI 획득은 timeout 0 으로 부르고 WAIT_TIMEOUT / ACCESS_LOST / ACCESS_DENIED 를 구분한다. 연속 timeout 10회부터 로그만
  남기고 그 분기 자체는 재시작을 요청하지 않는다. DXGI 가 실패하면 GDI(BitBlt) 로 넘어가는 경로가 있다.
- **확인(로그)**: kill 도우미가 성공을 보고한 뒤에도 "capture.exe didn't killed" 가 남은 기록이 있다 — 종료 성공 표시 ≠ 종료 완료.
- **미확인**: 반환하지 않는 AcquireNextFrame/ReleaseFrame 의 시간 감시, 게임·전체 화면 감지 시 WGC/hook 전환 조건.

**GNLink 시사점**
- 확인한 존재/플래그 루프만으로는 회사 PC `dxgi-worker-wedge phase=release`(dxgi-wedge-first-session r1) 같은 ReleaseFrame 정체를
  검출한다고 보장할 수 없다. GNLink 는 **5 s DXGI 워치독 계약(`host_startup_capture.cpp`)을 유지**하고, 캡처 분리 뒤에도 같은 계약을
  별도로 검증한다.
- 분리 시 감시는 **프로세스 존재 · 프레임 진행 · 호출 반환**을 각각 따로 보고, 재시작은 **이전 프로세스 종료 확인 + 새 워커 준비
  완료**까지 확인해야 한다.

## 2) 잠금 화면 입력 — 로컬 입력은 UIA 포커스 보조 + SendInput

- **확인**: SYSTEM 이벤트 프로세스의 입력 스레드가 현재 입력 데스크톱 이름을 비교해 `SetThreadDesktop` 으로 옮겨 간다(데스크톱마다
  입력 프로세스를 바꾼다는 근거는 없다 — 데스크톱마다 다시 띄우는 것은 캡처 프로세스다). 로컬 입력은 `SendInput`(텍스트는 Unicode
  INPUT 배열), 일부 키는 `keybd_event`.
- **확인**: 잠금/로그인 화면에서 UI Automation 으로 로그인 UI 를 찾아 PasswordField 에 SetFocus → 포커스 재확인. 실패하면 로그를
  남기고 성공 알림을 건너뛴다. 이 호출 지점의 호출자는 결과를 검사하지 않는다(그 지점의 자동 재시도 근거 없음 — 다른 계층의
  재시도까지 부정하지는 않는다).
- **확인(정적 경로)**: Ctrl+Alt+Del 은 키 조합이 아니라 `sas.dll!SendSAS(0)` 로 보낸다(실제 성공은 미확인).
- **미확인**: 네트워크에서 온 키가 이벤트 프로세스까지 오는 전체 경로, 네트워크/IPC 에서 credential 을 따로 보호하는지, 전송 암호화.

**GNLink 시사점** (lockscreen-keys 와 연결)
- 최종 로컬 입력이 SendInput 이라는 점은 GNLink 도 같다 — SendInput 사용 여부가 차이가 아니다. 비교할 것은 **GNLink 가 명시적으로
  설계한 계약**(목적 분리된 sealed 비밀번호·1회 전달·재사용 방지·검증된 LogonUI 암호 칸)과, OSLink 에서 확인한 로컬 입력/포커스
  범위다.
- 위 GNLink 계약은 `codex_lockkeys_dxgi_r1.md` 로 **확정된 설계 목표**이고 2026-10-22 현재 **구현 전**이다(잠긴 세션의 평문 문자
  경로 차단 A6 포함). 지금 제품이 이미 그렇게 동작한다는 뜻이 아니다.
- 결과는 **데스크톱 준비 · 포커스 확보 · 입력 전달 · 실제 잠금 해제**를 따로 회신한다. 포커스 실패를 호출자가 무시하는 구조를
  따르지 않는다.

## 3) 영상 전달과 인코딩 위치 — 추적한 경로는 공유 메모리 원본 프레임 → ldremote → ZEGO raw API

- **확인**: capture.exe 의 `Global\leidian_fb_rgb_mem_*` 파일 매핑 생성 코드, ldremote.exe 의 같은 기본 이름 기반 매핑 열기·뷰 매핑
  코드, 제어·알림용 이벤트/뮤텍스 객체(로그의 request_event / notify_event / input_mutex)가 각각 있다.
- **확인(정적 호출 연결)**: ldremote 의 VideoManager 원시 프레임 처리에서 ZEGO SDK 의 custom capture raw-data API 까지 호출이 이어진다.
- **미확인**: 매핑 뷰에서 모든 프레임 콜백까지의 완전한 연결, 모든 캡처 모드가 같은 경로인지. 즉 이것이 제품의 **유일한** 영상
  경로라고 확인한 것은 아니다.
- **확인 / 추정 / 미확인(형식)**: DXGI 캡처는 `DXGI_FORMAT_B8G8R8A8_UNORM` 을 요구한다(확인). ldremote 프레임 설정은 stride W/W÷2/W÷2·
  길이 W×H×3/2 로 구성된다(확인) — planar 4:2:0 과 맞는 배치라는 것은 **추정**이고, 정확한 SDK 형식 enum·IPC 픽셀 형식·색 변환
  위치는 **미확인**이다.
- **추정(높음)**: 추적한 raw 제출 경로에서 압축은 ldremote 안 ZEGO SDK 경계 이후에 일어난다.

**GNLink 시사점 — 기존 문서 정정**
- `OSLink_구조분석.md`(2026-08) 의 "프레임은 명명 파이프로 건넌다" 와 "① 캡처만 분리(OSLink 방식) = NV12 텍스처" 는 확정 설명으로
  쓸 수 없다. 이번에 확인한 근거는 **공유 메모리 매핑과 raw 소비 경로**다. 파이프(`ld-winpipe-*`)는 실재하나 이번 조사에서 프레임
  운반 근거는 찾지 못했다 — 어떤 모드에서도 파이프 영상 전달이 없다고 단정하지는 않는다. 그 문서에 정정 표시를 달았다.

## 4) 캡처 재시작 직후 복구(IDR) — 캡처 재기동과 앱 퍼블리시 수명은 별개, SDK 인코더 수명은 미확인

- **확인**: 캡처 감시(kill→boot)는 ZEGO 객체를 다루지 않는다. 채널 생성/파기·퍼블리시 시작/정지·엔진 init/uninit 은 ldremote 의
  별도 경로다.
- **확인(로그 1건)**: 과거 15:08:38 재기동 뒤 같은 스트림 문맥으로 프레임 처리가 다시 시작됐다(그 몇 초 뒤 publisher 오류 1회 —
  "무중단" 이라고 하지 않는다). 같은 논리 스트림은 **SDK 내부 인코더 인스턴스가 같다는 증거가 아니다.**
- **미확인**: SDK 내부 인코더의 유지·재생성·재설정. 재기동 직후 첫 IDR·SPS/PPS 를 만드는 조건과 시점 — 강제 keyframe·config 변경·
  손실 복구·GOP 중 무엇이 먼저 작동하는지 모른다(**GOP 에만 맡긴다는 해석도 근거 부족**). 앱이 요청한 키프레임 간격 값(120)은
  있으나 실제 적용값은 모른다. 상대의 키프레임 요청 콜백은 `CustomVideoCapture` 클래스 구현이 no-op(`ret 4`)이지만, 그 객체가 실제
  등록 인스턴스인지는 미확인.
- **확인**: 새 프레임 취득이 실패하면 그 처리를 건너뛰고, 별도 경로가 캐시된 원본 프레임을 조건부·제한적으로 다시 제출한다(반복
  카운터·간격 조건, 정확한 스케줄·reset 은 미확인). 해상도가 바뀌면 버퍼를 비우고 다시 만든 뒤 SDK 에 새 설정을 넘긴다(인코더
  재생성·IDR 보장은 미확인).

**GNLink 시사점 — 미디어 워커 분리(작업목록 CS) 의 경계 선택**
- **캡처만 분리**: OSLink 의 raw IPC 관찰을 참고한 **설계 대안**이다. 캡처 재시작과 논리 연결·코덱 재시작을 분리하는 설계가
  **가능하다**(OSLink SDK 내부 인코더가 실제로 유지되는지는 미확인). 대가는 원본 프레임 IPC(1080p BGRA 약 8 MB/프레임, CPU 경로)
  또는 GPU 공유 텍스처(`OSLink_구조분석.md` §5.3 의 어댑터·드라이버·MFT 지연 해제 조건)와 버퍼 수명·해상도 변경·잠금/세션 경계의
  캐시 폐기 계약이다.
- **캡처+인코딩 분리**(`OSLink_구조분석.md` §5.1 권고 ②): 워커가 죽으면 코덱 상태도 사라진다. 그래서 `OSLink_구조분석.md` §6 ADR
  초안의 투명 재시작 트랜잭션(broker 의 barrier·ForceIDR·SPS/PPS 포함 key 만 수용·옛 incarnation drop·seed 게이트)이 **필수**다.
  OSLink 조사는 이 형태의 IDR 보장 근거가 되지 않는다.
- 이번 결과는 ②권고와 §6 ADR 초안(**승인 전**)을 뒤집지 않는다. ①을 "NV12 공유 텍스처" 로만 보던 판단에 **CPU 원본 공유 메모리**
  변형이 비교 후보로 추가될 뿐이다. 어느 쪽이든 **프로세스 기동 → 매핑/타깃 준비 → 원본 프레임 도착 → 인코딩 bootstrap → 뷰어 첫
  디코드**를 단계별로 관측해야 한다. 경계 확정은 Codex 판정과 spike 측정으로 한다.

## 5) 로그인 전 접속 — 관찰된 시작 경로는 사용자 토큰 없이 네트워크 프로세스 기동 실패

- **확인(로그 10-21 14:34)**: 서비스가 ldremote 를 띄우려다 `WTSQueryUserToken error:1008`(사용자 토큰 없음) → 기동 실패를 반복하고,
  로그온 사건 뒤에야 사용자 토큰으로 기동에 성공했다. 같은 때 SYSTEM 이벤트 에이전트(Winlogon) 생성은 성공했다 — **에이전트 기동
  성공 ≠ 네트워크 준비**.
- **미확인**: 무로그인이 오래 유지될 때의 다른 대체 경로. 제품 전체가 로그인 전 접속을 지원하지 않는다고 단정하지 않는다.

**GNLink 시사점**: "로그인한 세션의 잠금 화면" 과 "아무도 로그인하지 않은 화면" 은 다른 시나리오로 각각 실기한다. 10-21 실기 화면은
Windows Update 재시작 뒤 자동 로그인+잠금으로 판단된다(이벤트·레지스트리 근거, Security logon type 은 미확인 — lockscreen-keys r1 §4).

## 6) 그 밖 — 미확인

- 목록 썸네일 주기·크기·사전 연결 정책: 근거를 찾지 못함. 로그의 640×360 publisher 설정을 썸네일 사양으로 쓰지 않는다.
- 전송 암호화: 암호 라이브러리·ZEGO 암호화 setter 는 있으나 해결된 호출자를 찾지 못했다(간접 호출 가능). 평문·암호화 어느 쪽으로도
  판정하지 않는다.
- Android 확대·선명화(SH 관련): APK 를 분석하지 않아 **미분석·미확인**.
