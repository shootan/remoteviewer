# GNLink UI — 화면 구성과 상태표

개선 작업의 **검토용 1차 산출물**이다. 큰 디자인 문서가 아니라, **어떤 화면이 어떤 상태를 가지며 그때
무엇이 보여야 하는가**만 적는다. 각 행은 나중에 **실렌더 스크린샷 한 장**으로 증명될 대상이다.

⚠️ 이 표는 **보이는 것**에 대한 계약이다. 내부 class/ID 전면 rename 은 범위가 아니다.

## 4. 공통 규칙

- **좁은 창**: 최소 폭에서 카드 1열, toolbar 항목 줄바꿈, 문구 말줄임.
- **고DPI**: **100 / 150 / 200%** 에서 잘림·겹침 없음. GDI 쪽은 `dpi_scale()` 경유.
- **다중 모니터**: 모니터 간 이동 시 DPI 재계산.
- **상태 구분은 색에만 의존하지 않는다** — 아이콘·텍스트·형태를 함께 쓴다.
- **키보드**: focus 링이 보이고 Tab 순서가 화면 순서와 같다.
- **hover / focus / disabled** 를 네 화면에서 같은 방식으로.

## 5. 🔴 기능 결함 — "대상 선택" 무반응 (원인 미확정)

사슬은 **이미 연결돼 있다**:
```
toolbar WM_LBUTTONUP → onTargets(viewer_startup)
  → set_picker_visible_and_sync_stream (viewer_picker.cpp:101)
  → release_swapchain / Invalidate
```
⚠️ **callback 이 있는 것을 확인하고도 handler 를 더 얹는 방식은 쓰지 않는다.** 아래 다섯을 **분리해
격리 재현**한 뒤에 고친다:

| # | 가설 | 계측 | 나오는 로그 |
|---|---|---|---|
| 1a | **down 이 기록되지 않음** | `WM_LBUTTONDOWN` 의 hit id | `[toolbar] down id=N x=.. y=..` |
| 1b | **누른 곳과 뗀 곳이 다름** | `WM_LBUTTONUP` 의 두 early return | `[toolbar] up ignored: no press recorded` / `... released over A but pressed B` |
| 1c | **callback 이 비어 있음** | 호출 직전 유무 | `[toolbar] targets clicked, callback present\|MISSING` |
| 2 | visible 전환이 안 됨 | `exchange` 로 전후를 한 번에 | `[picker] visible 0->1 activeGen=N` |
| 3 | **paint 가 안 옴** | 표시 1회당 첫 그리기에서만 | `[picker] first paint after show, client=WxH` |
| 4·5 | input gate / reveal 경합 | 2와 3 사이의 시간차 + `activeGen` | 위 두 줄의 시각 간격 |

⚠️ **이 계측은 아무 결정도 바꾸지 않는다.** 1b 의 두 갈래는 **원래 있던 `return 0`** 이고, 조용했을
뿐이다 — 정상 동작(버튼 밖에서 뗌)과 죽은 버튼이 밖에서 똑같이 보였다.

**읽는 법**: `down` 은 있는데 `up ignored` 면 **1b**(제품 결함 아님, 안내 문제). `targets clicked` 까지
가고 `[picker] visible` 이 없으면 **2**. `visible 0->1` 은 있는데 `first paint` 가 없으면 **3** —
swapchain 이 위에 합성되므로 **그리기가 안 온 것과 영상이 멈춘 것이 화면에서 구분되지 않는다.** 둘 다
있는데 화면이 그대로면 **4·5**.

**기대 동작**: 클릭 → **같은 세션에서** picker 표시 → 새 선택/닫기 후 **영상·입력 정상 복귀**. 실패 시
사유 안내. **새로 고침도 반응이 보여야 한다.**

⚠️ **picker 열기/닫기가 재접속 · 불필요한 capture 재시작 · IDR 폭주 · 입력 stuck 을 만들면 그 변경은
반려 대상이다.**

표시가 없고**, 다른 카드도 눌리는 상태로 남는다. 검증용이 지적한 *"창을 여는 중 이 영구 잔존"* 과
같은 자리다 — 카드에 진행 표시를 주고, 끝나면 그 표시가 사라지는 것이 정상 복귀의 관측점이 된다.

**✅ 이미 괜찮은 것 (바꾸지 않는다)**
- **empty 상태가 이미 있다** — `등록된 PC가 없습니다` + 다음 행동 안내. 위 표의 *"현재 없음"* 은 제
  오기였고 정정했다.
- **온라인 표시가 색만이 아니다** — 초록 점 **+ `연결 가능`/`오프라인` 텍스트** + 오프라인은 흐리게.
- 로그인 placeholder 가 `https://주소` 로 바뀐 것이 화면에서 확인된다(#523).

## 9. 제품 창 촬영 — 되는 것과 안 되는 것 (2026-09-11 실측)

도구: `.claude/shoot_viewer.ps1` — **사용자 권한**, 새 승격 없음. 실행 중인 GNLink(Host 20012 ·
Stream 26104 · InputService 28832)를 **건드리지 않기 위해** 뷰어를 **아무도 듣지 않는 43999** 로 띄운다.
루프백이라 바깥으로 나가는 트래픽도 없다.

**✅ 얻은 것 — S7 창 제목**
실제 제품 창의 제목이 **`GNLink`** 로 확인됐다(`product-viewer-connecting-00.png` 의 타이틀 바).
`remote60 native video client` 는 사라졌다. **이건 제품 창에서 찍은 것이지 하네스가 아니다.**

**🔴 못 얻은 것 — 연결 전 화면이 머물지 않는다**
본문이 완전히 검은 채로 **약 400ms 만에 종료(exit code 5)** 했다. 즉 **`호스트에 연결하는 중…` 을
보여주며 기다리는 화면이 이 경로에는 없다.** 위 S5 표에 그 상태를 적어 뒀지만, **호스트가 응답하지
않을 때 실제로 보이는 것은 잠깐의 검은 창**이다.
⚠️ **한 번 검었다** 와 **계속 검다** 는 다른 주장이라 프레임을 연속으로 찍었고, 그래서 종료가 보였다.
⚠️ 실행 3회 중 2회는 내가 멈출 때까지 살아 있었다 — **종료 타이밍이 일정하지 않다.** 원인은 조사하지
않았다(범위 밖). 여기서는 **"연결 전 상태를 안정적으로 촬영할 수 없다"** 는 사실만 확정한다.

**따라서 남은 상태(목록·선택 진행·toolbar 경로 badge)는 살아 있는 세션이 필요하다.**
- ❌ fixture 호스트를 띄우는 방법은 **와이어/협상 경로를 타므로 하드 경계** — 하지 않는다.
- ❌ 실 계정 로그인 — 비밀번호를 요구하지 않는다.
- ✅ **사용자가 평소 하는 원격 연결 중에 로그만 남기는 방식**(2단계 계측)이 남은 유일한 길이다.
  별도 조작을 요구하지 않는다.

## 10. 🔴 S5 개선안 — 안내 없는 검은 창 (표시안만, 구현 아님)

**현재**: 호스트가 응답하지 않으면 **제목만 `GNLink` 인 검은 창**이 뜨고 잠시 뒤 **조용히 사라진다**
(실측 exit code 5). **무엇이 왜 안 됐는지 한 글자도 없다.** 사용자는 "눌렀는데 아무 일도 없었다" 로
받는다 — 이번 task 의 *"실패 시 원인 안내"* 에 정확히 해당한다.
⚠️ **종료 타이밍 원인은 조사하지 않는다**(검증용 지시). 여기서 정하는 것은 **표시**뿐이다.

**표시안**

| 단계 | 표시 | 비고 |
|---|---|---|
| 시도 중 | `<대상 PC> 에 연결하는 중…` + 진행 표시 | 검은 화면 대신 **즉시** 나온다. 첫 프레임 전에도 |
| 지연 | `응답을 기다리는 중입니다…` | 몇 초 넘어가면 바뀌어 **멈춘 것이 아님**을 보인다 |
| 실패 | **사유 한 줄** + **[다시 시도] [닫기]** | 창이 **사라지지 않는다** — 사라지면 사유를 읽을 수 없다 |

**사유 문구**(가진 정보로 구분 가능한 것만; 없는 정보를 지어내지 않는다)

| 상황 | 문구 |
|---|---|
| 상대가 응답하지 않음 | `PC 가 응답하지 않습니다. 그 PC 에서 GNLink 가 실행 중인지 확인해 주세요.` |
| 주소는 닿았으나 거절 | `연결이 거절됐습니다. 계정이 같은지 확인해 주세요.` |
| 그 외 | `연결하지 못했습니다.` + **내부 코드 병기**(로그 대조용) |

⚠️ **색만으로 구분하지 않는다** — 아이콘 + 문구를 함께. 좁은 창에서 버튼이 줄바꿈되지 않게(P1 과 같은
실수를 반복하지 않는다).
⚠️ **재시도 버튼이 자동 재시도가 되면 안 된다** — 실패 로그가 덮인다.

**구현 전 확인 필요**: 창을 남기려면 종료 경로를 건드려야 하는데, 그 경로가 **왜 그 시점에 나가는지가
아직 미상**이다. 표시만 바꾸고 수명은 그대로 둘 수 있는지 먼저 봐야 하므로 **검토 후 구현 여부 결정**.

## 11. 1차(표시만) 결과 — **그 조건에서는 실행되지 않는 코드였다**

⚠️ **정정**: 처음에 *"수정이 증상을 못 고친다"* 로 적었는데 **틀린 결론이다.** 촬영 경로는
`connect()` 가 실패해 **`draw_overlay` 가 있는 present 루프에 도달하지 못한다.** 즉 그 환경은 이
수정을 **시험할 수 있는 환경이 아니었다.** *"수정이 안 통한다"* 와 *"이 조건에서는 그 코드가 실행되지
않는다"* 는 다르다 — 오늘 반복해서 틀린 바로 그 구분이다(검증용 지적).

`draw_overlay` 가 첫 프레임 전에 곧바로 반환하던 자리에 **`연결하는 중…`**(4초 넘어가면
**`응답을 기다리는 중입니다…`**)을 그리도록 넣었다. 조건은 `lastPresentedVersion == 0` —
`lastPresentedCaptureUs` 는 **picker 가 닫힐 때마다 0 으로 되돌리므로** 세션 중에 다시 0 이 되어
살아 있는 영상 위에 글씨를 쓰게 된다. 버전은 올라가기만 한다.

**그런데 제품 창은 여전히 검다.** 재촬영 결과:
```
window title: 'GNLink'
viewer exited after 120ms, code 5
wrote 1 frames
```
**창이 뜨고 120ms 안에 프로세스가 나간다.** `draw_overlay` 는 `viewer_present.cpp:380` 에서 확실히
호출되지만 **그 전에 WM_PAINT 가 한 번도 오지 않는다.** 찍힌 검은 화면은 *"early return 으로 아무것도
안 그린 화면"* 이 아니라 **아직 한 번도 그리지 않은 창**이다.

⚠️ **그러므로 이 수정은 신고된 증상을 고치지 못한다.** 원인은 `draw_overlay` 의 조기 반환이 아니라
**프로세스가 나가는 것**이다. 표시만 바꾸라는 범위 안에서는 여기까지가 한계다.
⚠️ 종료 타이밍은 **일정하지 않다** — 최근 3회는 120~400ms 에 exit 5, 그 전 2회는 2초 넘게 살아 있었다.
**원인은 조사하지 않았다**(지시 범위 밖).

**그럼에도 이 변경은 남긴다**: *"창은 떠 있는데 아직 프레임이 없는"* 상태는 실재하고, 그때는 이 문구가
나온다. 다만 **그 상태를 이 환경에서 만들 수 없어 제품 창으로는 미검증**이다 — fixture 호스트는
와이어 경로를 타므로 하지 않는다.

**2차(창 유지 + [다시 시도]/[닫기])가 실제 해법으로 보인다.** 다만 그것은 **종료 경로를 건드리는
일**이고, 왜 그 시점에 나가는지가 미상인 채로 손대면 안정성 경계에 닿는다 — 검증용 판단 대기.

## 12. 2차 — **연결 실패를 말하고, 읽을 시간을 준다** (완료)

**exit 5 는 미상이 아니었다.** `viewer_startup.cpp:390` 의 `connect()` 실패다 — 검증용이 소스에서
찾았고 나도 확인했다. 아무도 듣지 않는 43999 로 띄웠으니 **정상 동작**이었고, 종료 시각이 120ms~수 초로
들쭉날쭉했던 것도 **거부가 즉시냐 SYN 재시도가 있느냐**로 설명된다.
**문제는 종료 자체가 아니라, 이미 알고 있는 실패 사유를 한 글자도 말하지 않고 창을 닫은 것**이었다.
사유는 내내 `std::cerr` 로 나가고 있었다 — 사용자가 볼 수 없는 곳으로.

**한 것**: 실패 시 **창을 유지**하고 **사유 한 줄 + [다시 시도] [닫기]** 를 그린다.
```
127.0.0.1:43999 에 연결하지 못했습니다.
그 PC 에서 GNLink 가 실행 중인지 확인해 주세요.
(코드 5)
          [다시 시도]   [닫기]
```
- 사유는 **가진 정보로 구분되는 것만**: 주소 오류(4) · 연결 실패(5) · 준비 실패(3) · 그 외. **내부 코드
  병기**로 로그와 대조된다. 방화벽·계정 같은 **모르는 것은 말하지 않는다.**
- ⚠️ **자동 재시도 없음.** [다시 시도] 는 사용자가 누를 때만이고, 누르면 로그에 그렇게 남는다 —
  자동이면 실패 로그가 덮인다.
- ⚠️ **성공 경로 무접촉**: 연결이 되면 첫 바퀴에서 루프를 빠져나가며 **호출 순서가 이전과 같다.**
  `connect` 자체·와이어·협상·타임아웃 값은 건드리지 않았다.

**증거**
- 제품 창 스크린샷 `.claude/ui-preview/product-viewer-connecting-*.png` **30프레임**(이전엔 1프레임 뒤
  종료). 위 문구와 버튼 둘이 보인다.
- 회귀 `viewer_startup_failure_test` **4 PASS** — 포트가 실제로 비어 있음 · **2.5초 뒤에도 살아 있음**
  (이전 동작은 ~120ms 종료) · 사유를 띄울 창을 여전히 가짐 · **닫으면 종료되고 exit 5 는 그대로**.
- ⚠️ **버튼 클릭 자체는 회귀가 아니라 스크린샷 증거**다. 히트 테스트를 테스트에서 복제하면 레이아웃을
  두 곳에 적게 되므로 하지 않았다.

## 14. 🔴 toolbar 경로 표시 — **모르는 것을 "직접" 이라고 말하고 있었다** (2026-09-12)

`client_session_toolbar.cpp:83` 이 이랬다:
```cpp
text += g.state.relay ? L" · 릴레이" : L" · 직접";
```
`relay` 는 **기본값 false 인 bool** 이다. 그래서 **아무것도 답하기 전** — 사용자가 바를 쳐다보는 바로
그 순간 — 화면은 **확정된 직접 연결**이라고 말했다. **기본값은 측정이 아니다.**

**세 번째 상태를 만들었다.** bool 하나가 세 답을 담을 수 없다.
| 상태 | 표시 |
|---|---|
| 아직 모름 | `◌ 경로 확인 중` |
| 직접 | `→ 직접` |
| 릴레이 | `⇄ 릴레이` |
기호를 붙인 것은 **색에 기대지 않고 셋을 구분**하기 위해서다(바는 한 줄 텍스트라 쓸 색도 없다).

**어디서 "알게" 되는가**
- 디렉터리가 답했을 때(`viewer_startup.cpp:339`) — 그때 `relayPathKnown=true`
- **주소를 직접 준 경로** — 그 길에는 릴레이가 없으므로 `직접` 이 **가정이 아니라 사실**이다.
  이전에는 이 경로에서 `relayPath` 를 **아무도 쓰지 않아** 기본값 false 가 그대로 표시됐다.

**단정은 제품 함수로 한다**: 문구 조립을 `session_toolbar_status_text(state)` 로 꺼냈고, 바가 그것을
호출한다. 테스트는 **규칙을 복제하지 않고 제품이 쓰는 그 함수**를 부른다.
`session_toolbar_click_test` **12 → 17 PASS**: 미확정이 `직접` 으로 안 나옴 · `확인 중` 이라고 말함 ·
릴레이/직접 각각 말함 · **셋이 텍스트로 서로 다름**.

⚠️ **미촬영**: 바의 실제 픽셀. 이 창은 테스트가 만들고 테스트와 함께 사라지므로, 화면을 남기려면
창을 테스트 밖까지 살려 둘 방법이 필요하다. **문구 계약은 위 단정으로 닫았고, 그림은 남지 않았다.**
⚠️ **auto-hide(원격 클릭 가로채기·누르는 중 사라짐)는 아직 손대지 않았다.**

## 16. 강조색이 두 개였다 (2026-09-12, 검증용이 사진에서 발견)

`shell.html` 쪽 네 화면은 **파랑**(`--accent #3b82f6`), picker 는 **초록**이었다. **한 제품의 두 화면이
자기 색을 다르게 알고 있었다.** 게다가 초록이 **같은 무게로 둘** — 선택된 카드와 `전체 화면` 버튼 —
이라 **무엇이 선택인지 색으로는 답이 안 나왔다.**

**고친 것**
- 버튼 active 채움 `RGB(48,96,62)` → **`RGB(59,130,246)`** (shell.html 과 같은 파랑)
- 선택 카드: 테두리 파랑 + 캡션 **옅은 파랑 틴트**(채움 아님) + **오른쪽 위 ✓ 배지**
  - 카드는 **상태**, 버튼은 **동작**이다. 둘 다 꽉 채우면 같은 종류로 읽힌다 — 그래서 카드는 틴트다.
  - ⚠️ **✓ 는 색 대신이 아니라 색과 함께다.** 흑백 스크린샷·색이 틀어진 모니터·파랑과 회청을 구분하지
    못하는 눈에서도 선택이 남아야 한다.

⚠️ **레이아웃 안전 조건 확인**: 카드 기하는 `compute_card_grid()` 하나에서 나오고 **그리기와 히트테스트가
같은 함수를 부른다**(`viewer_picker.cpp:72,202,216`). 그래서 기하를 바꾸면 둘이 자동으로 같이 움직인다.
`desktopButtonRect` 는 `compute_client_layout()` 소관이라 **이번 변경과 무관**하다.
