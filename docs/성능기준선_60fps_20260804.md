# P3 기준선 — 캡처 경로 변경 전 (2026-08-04)

R1/R2/R3가 캡처 경로를 바꾸기 **전에** 남긴 기준선. 이후 측정은 이 표와 비교해서
개선인지 회귀인지 귀속한다.

## 조건

| | |
|---|---|
| 요청 fps | **60** |
| 백엔드 | DXGI |
| 포트 | 44100 / 44101 (격리, 제품 호스트 미접촉) |
| 클라이언트 | GNLinkViewer (localhost) |
| 씬 | `perf_scene_generator.ps1` 합성 (scroll / video) |
| 원격 세션 | **없음** (물리 콘솔) |
| 커밋 | `327dd8d` |

## 결과

| 씬 | DEC_AVG (3회) | 중앙값 | LAT_P95_US |
|---|---|---|---|
| 1080p-scroll | 49.22 / 55.44 / 51.00 | **51.0** | 3,268 ~ 13,921 |
| 1080p-video | 56.44 / 56.80 / 46.11 | **56.4** | 4,619 ~ 10,274 |

공통: `PRESENT_GAP_OVER_1S=0`, `UDP_ASSEMBLY_DROPPED_TOTAL=0`, `GATE_A_PASS=True`,
`GATE_A_SHELLWINDOW_FALLBACK_DETECTED=False`, host CPU 43~58% (1코어 환산).

## 이 수치가 말하는 것

**60fps 요청에서 로컬 Windows 뷰어는 49~57fps를 낸다.** 사용자가 보고한 "60프레임은 더
심하다"가 이 경로에서는 재현되지 않는다. 소스가 60을 준다는 P1 결과와도 일치한다.

따라서 P3의 조사 범위는 여기가 아니라 **Android 클라이언트 경로 또는 실제 네트워크**다.
localhost + Windows 뷰어는 이미 목표에 근접해 있으므로, 남은 결손은 그 둘 중 하나에서
발생한다.

## 회귀 판정 기준

이후 작업 뒤 같은 명령으로 재측정했을 때:

- `DEC_AVG` 중앙값이 scroll 51.0 / video 56.4 대비 **10% 이상 하락하면 회귀**
- `PRESENT_GAP_OVER_1S`가 0이 아니면 회귀
- `GATE_A_SHELLWINDOW_FALLBACK_DETECTED=True`가 나오면 캡처 경로 파손

## 재현 명령

```powershell
& automation\run_perf_baseline_fps.ps1 -Fps 60 -Repeats 3 `
  -Only @('1080p-scroll','1080p-video') -CaptureBackend dxgi `
  -OutDir <새 폴더>
```
