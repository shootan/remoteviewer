# 계정 로그인 · 호스트 등록 · UDP 홀펀칭 설계

작성일: 2026-07-28
상태: 설계 확정, 서버 1차 구현

## 1. 목표

- 클라이언트를 켜면 로그인 화면이 뜨고, id/pw로 로그인한다.
- 그 계정에 등록된 **호스트 목록만** 보인다. 계정당 호스트는 여러 대 가능하다.
- 하나 고르면 바로 연결된다. IP·포트를 외울 필요가 없다.
- 호스트도 같은 id/pw로 로그인해 자기 자신을 등록한다. 한 번 입력하면 캐싱하고, 변경도 가능하다.
- **회사 PC처럼 인바운드가 막힌 환경에서도 접속**된다.

## 2. 왜 이게 방화벽을 통과하는가

방화벽은 밖에서 들어오는 연결은 막지만 안에서 나가는 연결은 허용한다.
그래서 양쪽 모두 **밖으로 나가서** 디렉터리 서버에서 만난다.

```
회사 PC ──(아웃바운드)──> 디렉터리 서버 <──(아웃바운드)── 폰
                              │
                    서로의 공인 주소를 교환
                              ▼
회사 PC <════════ 직통 UDP (홀펀칭) ════════> 폰
```

홀펀칭 원리: 각자 상대 주소로 UDP를 먼저 쏘면, 자기 쪽 NAT에 "이 목적지로 보냈다"는 매핑이
생기고 그 매핑이 상대의 패킷을 되받아준다. 양쪽이 동시에 쏘면 서로의 매핑이 만들어져 길이 열린다.

**서버는 만나게만 해주고 영상은 지나가지 않는다.** 그래서 저사양 인스턴스로 충분하다.
릴레이(TURN)는 홀펀칭이 실패하는 환경이 실제로 확인되면 그때 판단한다. 미리 만들면 서버 대역폭만 잡아먹는다.

## 3. 구성 요소

| 구성 | 위치 | 역할 |
|---|---|---|
| 디렉터리 서버 | 네이버클라우드 인스턴스 | 계정 인증, 호스트 등록/목록, 주소 교환, 펀치 중개 |
| 호스트 | 원격 대상 PC | 로그인 후 자기 등록 + 하트비트, 펀치 수행, 기존 영상/입력 스트리밍 |
| 클라이언트 | Android 앱 | 로그인, 호스트 목록, 선택 시 펀치 후 기존 UDP 경로로 연결 |

**중요: 기존 영상/입력 프로토콜은 그대로 둔다.** 연결이 성립된 뒤부터는 지금과 완전히 동일하다.
디렉터리 서버가 하는 일은 "어느 주소로 쏘면 되는지" 알려주는 것까지다.

## 4. 서버 API

전 구간 HTTPS 전제(운영). 개발 중에는 HTTP 허용.

### 인증
- `POST /api/login` `{id, pw}` → `{sessionToken, expiresAt}`
  - 실패 시 지수 백오프. 존재하지 않는 계정과 틀린 비밀번호를 구분해 응답하지 않는다.

### 호스트 (호스트 PC가 호출)
- `POST /api/host/register` `{id, pw, hostName, machineId}` → `{hostId, hostToken}`
  - 같은 `machineId`로 다시 부르면 기존 등록을 갱신한다(재설치해도 목록이 늘지 않음).
- `POST /api/host/heartbeat` `{hostToken, udpPort}` → `{ok, pendingPunch:[...]}`
  - 서버는 이 요청의 **출발지 IP**를 호스트의 공인 IP로 기록한다.
  - 30초 주기. 90초 무응답이면 오프라인 처리.

### 클라이언트
- `GET /api/hosts` (Bearer sessionToken) → `[{hostId, hostName, online, lastSeen}]`
- `POST /api/connect` `{hostId, udpPort}` → `{hostPublicIp, hostPublicUdpPort, punchToken}`
  - 동시에 호스트의 다음 하트비트 응답에 `pendingPunch`로 클라이언트 주소를 실어 보낸다.

### UDP 주소 관측 (핵심)
공인 IP만으로는 부족하다. NAT는 **포트까지** 변환하므로, 실제 미디어 소켓이 밖에서 어떤
포트로 보이는지 알아야 한다.

- 호스트/클라이언트는 **미디어에 쓸 바로 그 UDP 소켓**으로 서버의 UDP 포트에 관측 요청을 보낸다.
- 서버는 수신한 패킷의 출발지 `ip:port`를 그대로 회신한다(STUN 최소 구현).
- 이 값이 상대에게 전달되는 주소가 된다.

## 5. 연결 순서

```
1. 호스트: /api/host/register (최초 1회) → hostToken 저장
2. 호스트: UDP 관측 → 자기 공인 ip:port 파악
3. 호스트: /api/host/heartbeat (30초 주기, 공인 주소 갱신)

4. 클라: /api/login → sessionToken
5. 클라: /api/hosts → 목록 표시
6. 사용자가 호스트 선택
7. 클라: UDP 관측 → 자기 공인 ip:port 파악
8. 클라: /api/connect → 호스트 주소 수신
9. 호스트: 다음 하트비트에서 클라 주소 수신

10. 양쪽 동시에 상대 주소로 punch 패킷 반복 전송(200ms 간격, 최대 5초)
11. 어느 한쪽이 상대 punch를 받으면 성립 → 기존 UDP hello 핸드셰이크로 진입
12. 5초 내 실패 시 사용자에게 안내(현재는 릴레이 없음)
```

## 6. 보안

이 기능은 "인터넷에서 내 PC를 조작할 수 있게 만드는" 기능이므로 아래는 선택이 아니다.

- **비밀번호는 절대 평문 저장·로그 금지.** scrypt 해시 + 계정별 salt.
- 서버 통신은 **TLS 필수**(운영). 토큰이 평문으로 흐르면 의미가 없다.
- `sessionToken`/`hostToken`은 난수 32바이트. 만료 있음.
- 로그인 실패 백오프, 계정 존재 여부 노출 금지.
- `punchToken`은 1회용·단기 만료. 이걸로 아무나 주소를 캐낼 수 없게 한다.
- **미디어 자체는 아직 암호화되지 않는다.** 현재 UDP 영상/입력은 평문이다.
  홀펀칭으로 인터넷을 통과하게 되면 이건 실제 위험이 된다. 별도 과제로 남긴다.
- 저장소에 실제 자격증명을 커밋하지 않는다. 서버 설정은 환경변수로만 받는다.

## 7. 호스트를 GUI 앱으로

현재 호스트는 콘솔 실행이라 id/pw를 넣을 자리가 없다. 최소 GUI를 붙인다.

- 최초 실행: 로그인 창(id/pw, 호스트 이름) → 등록 후 `hostToken`을 사용자 프로필에 저장
- 이후 실행: 자동 로그인, 트레이 상주, 상태(온라인/오프라인/접속 중) 표시
- 트레이 메뉴에서 계정 변경·로그아웃
- 저장 위치는 `%LOCALAPPDATA%\remote60\host.json`, 토큰만 저장하고 비밀번호는 저장하지 않는다.
