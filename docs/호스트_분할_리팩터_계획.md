## 2) 설계 원칙

1. **기능 기준 분할**이 1차 기준이다(사용자 요구). 스레드 기준이 아니다.
2. **행동 보존 우선**: Phase 0~3은 리네임·이동·래핑만. 조건/순서/타이밍/로그 문자열 불변. 동작을 바꾸고 싶은 발견은 §7 "Phase 4 후보"에 적고 넘어간다.
3. **1클래스 1파일, ≤ 800줄.** 파일 머리에 5줄 요약: 역할 / 소유 스레드 / 입력 / 출력 / 호출자.
4. 30줄 초과 람다는 멤버 함수로. 스레드 본체(`std::thread([&]{...})`)는 `Run()` 멤버로.
5. 각 클래스는 다른 클래스를 **참조**(포인터/레퍼런스)로만 알며, `main()`이 조립한다. 전역(`gUdpPace*` 3개)은 해당 클래스 멤버로 흡수.
6. 순수 결정 로직(ABR, frame gating, kick 스케줄, 백엔드 승격 백오프)은 **시간을 인자로 받는** 형태로 만들어 단위테스트 가능하게 한다(기존 `capture_cadence_gate` 선례).
7. 네임스페이스 `remote60::native_poc` (d3d_capture_readback/capture_cadence_gate 관례). 파일명 접두사 `host_`.

## 7) 스레드 소유권 — 지금 규칙의 성격과 Phase 4 재설계

### 7.1 판정: 규칙 대부분은 모놀리스의 산물이다

코드 주석의 "X는 Y 스레드에서 쓰지 말 것" 류 규칙을 분류하면:

**(a) 근본 제약 — 리팩터 후에도 유지 (3개)**

| 제약 | 이유 |
|---|---|
| WGC `FrameArrived` 콜백 스레드에서 캡처 리소스(pool/readback/staging) 재생성 금지 | WinRT 콜백 안에서 자기 pool을 파괴/재생성하면 재진입·데드락. 코드 주석 7479~7484 |
| MFT(`H264Encoder`) submit/drain은 한 스레드 | Media Foundation 비동기 MFT 계약. 인코더 스레드를 따로 두는 건 가능하지만 지연 특성이 바뀌는 **설계 변경**(Phase 4 후보) |
| 소켓 쓰기는 한 스레드(sender) | 청크 인터리브 방지 |

**(b) 인위 규칙 — 502개 변수를 한 스코프에 두고 락 없이 신호하려다 생긴 것 (Phase 4에서 제거)**

| 현재 패턴 | 왜 생겼나 | 재설계 |
|---|---|---|
| `*Pending` atomic 플래그 + "루프 상단에서 exchange로 소비" ≈ 12개 (desktopBackendReq, monitorSelect, captureModeReq, runtimeTune, senderRecovery, senderRequestKey, senderSendFailed, captureSizeChange, wgcContentSizeMismatch, clientRequestedKeyFrame, udpPeerChanged, streamControlActive 전이) | 손으로 만든 메일박스. 요청 payload는 별도 atomic(`*Seq`, `*Value`, `*XPermille`)에 흩어짐 | **`MainLoopMailbox`** 하나: `std::variant<SelectMonitor, SelectWindow, SetCaptureMode, TuneEncoder, RequestKeyframe, BackendRequest, PeerChanged, …>` 큐. 키별 "최신 것만 유지"(coalesce)로 현재의 덮어쓰기 의미 보존 |
| "`forceKeyNext`는 sender 스레드에서 절대 쓰지 말 것" (3241~3245) | forceKeyNext가 main 소유 plain bool이라 sender는 `senderRecoveryPending`으로 우회 | sender가 `RequestKeyframe{reason=barrier}`를 post → 규칙 자체가 소멸(타입이 강제) |
| `*FallbackReason` 문자열 4종 + 전용 mutex + set/copy 람다 4개 | 구조체가 없어서 | `BackendFallbackInfo` 1개 스냅샷 |
| `clientMetrics*` 20개 (control 쓰기 / main·ABR 읽기, 각각 atomic) | 구조체가 없어서 | `ClientMetricsSnapshot` — control이 락 아래 통째 교체, ABR이 통째 복사 |
| `hostCaptureTarget*` 5개 + `hostCaptureMetaMu` (control이 창 목록 응답에 쓰려고 읽음) | 〃 | `CaptureSession::SnapshotTarget()` |
| `captureCadenceMu` 아래 plain uint64를 통계 틱이 같은 락으로 읽는 규칙 (9088~9091) | 〃 | `CaptureCadenceGate::Snapshot()` |

### 7.2 절차 (사용자 확인 사항 반영)

- Phase 0~3: 위 규칙을 **그대로 보존**한다. 단, 주석에만 있던 규칙을 각 struct/클래스 머리의 `// thread:` 블록으로 옮겨 **한 곳에 모은다**. 이 목록이 Phase 4의 작업 목록이다.
- Phase 4 (구조가 선 뒤, 별도 사이클): (b)를 메일박스/스냅샷으로 교체. 커밋 단위 = 패턴 한 줄. 이때만 동작이 바뀌므로 e2e 6/6 + 실기 게이트를 건다.
- 이유: 구조 이동과 동작 변경을 한 커밋에 섞으면 회귀 원인을 못 가른다. 규칙이 "인위적"이라는 판단이 맞더라도 제거는 구조가 선 뒤가 싸다.

## 9) HANDOFF 게이트와의 관계

- Phase 0은 순수 이동이라 **0.2.56 실기 판정과 무관하게 지금 진행 가능**.
- 실기 판정 결과로 코드 수정(sticky input routing)이 필요해지면 **Phase 0-1 이후** `host_input_inject`/`InputRouter`에서 한다 — 660줄짜리 단독 파일이라 지금보다 쉽다.
- Phase 1~3은 **P2(readback 60fps) 착수 전**에 끝낸다. P2가 건드릴 영역(CaptureSession/Watchdog)이 바로 리팩터 대상이라 순서가 바뀌면 두 번 고친다.
- `native_video_client_main.cpp`(5,318줄, main 2,100줄, 람다 13)는 이미 shared_core/tcp_control/toolbar/macro_window가 분리돼 있어 후순위. 같은 방식으로 별도 계획.
