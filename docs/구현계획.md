## 0) 이 단계의 목표

M0~M8에서 **화면은 잘 나오게** 만들었다. 이 단계의 목표는 **실제로 접속되고, 접속된 뒤에 할 일을
다 할 수 있게** 만드는 것이다. 남은 격차는 성능이 아니라 도달성과 권한이다.

- **도달성**: 제한적인 네트워크(회사/게스트 Wi-Fi, 대칭 NAT)에서 접속된다.
- **권한**: UAC 동의 창을 보고 누를 수 있다. 현재는 둘 다 불가능하다.
- **정확성**: 실패가 실패로 보인다. 지금은 여러 경로에서 실패가 성공처럼 보고된다.

## 1) 근거 대장 (측정 vs 가정)

작업 우선순위가 여기에 달려 있어 분리해 둔다. **가정을 측정으로 바꾸는 항목이 가장 싸고 가장 중요하다.**

| # | 명제 | 상태 | 근거 |
|---|---|---|---|
| E1 | 회사 Wi-Fi에서 UDP 43000 아웃바운드가 막힌다 | **측정됨 — 기각** | 2026-08-06 N7 Phase 1. 회사 Wi-Fi 5회 전 시도에서 폰의 펀치가 서버 UDP 43000에 도달(첫 발 10ms, 시도당 27발). 막힌 건 외부 43000이 아니라 **사내 공인 IP로 되돌아가는 헤어핀 경로**다. 덤: 전 시도 `samePort=true` — 폰 NAT는 엔드포인트 독립 매핑(cone) |
| E2 | 이 공유기는 NAT 포트를 보존한다 | **측정됨** | `bindPort=43000` → `public=...:43000` |
| E3 | UAC는 secure desktop(Winlogon)에 그려진다 | **측정됨** | 이 PC `PromptOnSecureDesktop=1`, `EnableLUA=1`, `ConsentPromptBehaviorAdmin=5` |
| E4 | 어떤 캡처 백엔드도 데스크톱을 전환하지 않는다 | **코드 확인** | 저장소 전체에서 `SetThreadDesktop`/`OpenInputDesktop` 히트 2곳뿐이며 둘 다 캡처 아님 (`native_video_host_main.cpp` 이름 probe, `secure_input_service_main.cpp` 입력 attach) |
| E5 | ACCESS_LOST 후 WGC 강등이 영구적이다 | **코드 확인** | `activeDesktopBackend = Wgc` 이후 복귀 경로가 명시적 클라이언트 요청뿐이고, 그 요청도 `resolve_output`에서 재실패 |
| E6 | SYSTEM 에이전트가 잘못된 세션을 타겟한다 | **코드 확인** | `WTSGetActiveConsoleSessionId()`가 유일한 세션 선택자. `docs/잠금화면_사전로그인_설계.md`의 실측 표에 호스트 세션 2 / 콘솔 세션 9 기록 |
| A1 | "데스크톱이 초당 33회만 갱신된다" | **측정됨 — 거짓 (기각)** | 2026-08-04 P1. 같은 도구, 같은 PC. 원격 세션 중에는 출력이 `2236x1232` 하나뿐이고 **33/s**, 원격 해제 후 물리 `1920x1080`에서 **60~62/s**. 33은 원격 가상 디스플레이의 천장이었고 콘텐츠 한계가 아니었다 |
| A2 | Winlogon에서 `GetDC(NULL)+BitBlt`가 동작한다 | **측정됨 — 참** | 2026-08-04 U1 probe. SYSTEM으로 Winlogon에 attach 후 **BitBlt 2720x1080(가상 화면 전체)과 DXGI 1920x1080 둘 다** UAC 창을 선명하게 캡처. `docs/잠금화면_사전로그인_설계.md`의 "DXGI만 가능" 주장은 **반증됨** |

> **두 가정 모두 측정으로 대체되었고, 둘 다 앞선 결론을 뒤집었다.**
>
> **A1 기각의 파급.** "파이프라인은 98.7% 효율이고 남은 한계는 소스다"라는 기존 결론이
> 무효다. 소스는 60을 준다. 데스크톱 60fps가 안 나온 원인은 **아직 규명되지 않았고**,
> 원격 세션에서 측정한 지표는 전부 재검토 대상이다. 새 항목 **P3**으로 추적한다.
>
> **측정 규칙.** 캡처율·fps 측정은 **RDP·OSLink 등 원격 세션에 붙은 상태에서 하지 않는다.**
> 원격 도구는 자기 가상 디스플레이를 얹고 그 주사율이 천장이 된다. 이 함정에 두 번 빠졌다.

> **2026-08-06 해결 — UAC 프롬프트 클릭 동작. 실기 확인 완료.** 원인은 **독립된 두 개**였다.
>
> | | 증상 | 원인 | 수정 |
> |---|---|---|---|
> | ① | 클릭이 **안 됨** (`err=5`) | `DESKTOP_JOURNALPLAYBACK` 액세스 마스크 누락 | 0.2.12 |
> | ② | 클릭이 **엉뚱한 곳**에 (오른쪽 아래) | 에이전트가 DPI awareness 미선언 | 0.2.13 |
>
> ①을 고치기 전까지 ②는 보이지도 않았다. 하나를 고쳐야 다음 것이 드러나는 구조였고, 그래서
> 중간 단계마다 "아직 안 된다"가 반복됐다.
>
> **드라이버도, 레지스트리 변경도, 인증서도 필요 없었다.** 아래 A/B/C 선택지는 전부 불필요했던
> 것으로 판명됐다 — 기록은 남기되 실행하지 않는다.
>
> ---
>
> **① `DESKTOP_JOURNALPLAYBACK` 누락 (0.2.12)**
>
> `SendInput`은 주입 전에 **두 가지**를 검사한다:
> 1. 호출 스레드가 현재 **입력 데스크톱**에 있는가
> 2. 그 스레드의 데스크톱 핸들이 **`DESKTOP_JOURNALPLAYBACK`** 으로 열렸는가
>
> 둘 중 하나만 실패해도 똑같이 `ERROR_ACCESS_DENIED(5)`가 나온다. **구분할 방법이 없다는 것이
> 이 버그가 오래 산 이유다.** 우리는 ①만 의심하며 세션·데스크톱·토큰을 전부 고쳤고, 실제 원인인
> ②는 마스크 한 줄이었다:
>
> ```cpp
> // 0.2.11까지 (secure_input_service_main.cpp)
> OpenInputDesktop(0, FALSE, DESKTOP_READOBJECTS | DESKTOP_WRITEOBJECTS | DESKTOP_SWITCHDESKTOP);
> //                          ↑ DESKTOP_JOURNALPLAYBACK 없음
> ```
>
> `SetCursorPos`는 이 권한을 요구하지 않는다. 그래서 **커서는 움직이는데 클릭만 거부되는**
> 정확히 관측된 증상이 나온다. SYSTEM 권한은 필요조건이었고(보안 데스크톱 DACL이 SYSTEM에만
> 열려 있다) 우리는 이미 만족하고 있었다 — 부족했던 건 요청한 액세스 마스크뿐이다.
>
> 수정: 마스크에 `DESKTOP_JOURNALPLAYBACK` 추가. 거부되면 기존 마스크로 재시도해 **커서 이동만은
> 살린다**(입력 전체를 잃는 것보다 낫다). 어느 쪽으로 열렸는지 로그에 `journal=ok|DENIED`로 남겨,
> 앞으로의 `err=5`가 이 버그의 재발인지 다른 원인인지 즉시 구분되게 했다.
>
> **검증 로그:** `agent desktop=Winlogon attach=ok journal=ok inject=ok`
>
> ---
>
> **② DPI awareness 미선언 (0.2.13)**
>
> ①을 고치자 클릭은 되는데 **의도한 지점보다 오른쪽 아래에** 찍혔다. 화면 좌표를 다루는
> 컴포넌트 중 **에이전트만** `SetProcessDpiAwarenessContext`를 부르지 않고 있었다 — 캡처 워커,
> 호스트 창, 뷰어는 전부 부른다.
>
> 호스트는 **물리 픽셀**을 캡처해서 보낸다. DPI-unaware 프로세스는 가상화된 좌표계를 받으므로
> `SetCursorPos(x, y)`가 배율만큼 곱해진 뒤 커서에 도달한다. **원점에서 멀수록 더 많이 밀리는**
> 오른쪽·아래 방향 오차가 정확히 이 형태다.
>
> 진단이 오래 걸린 이유: 매핑 계산은 처음부터 옳았다. 로그의 `in=(1091,721) → mapped=(1091,721)`은
> 항등이었고, 브로커도 대상 사각형을 매 메시지에 정확히 실어보내고 있었다. **좌표가 맞는데 커서가
> 다른 곳에 있다**는 사실 자체를 볼 수 없었던 게 문제 — 좌표 로그가 실패 경로에만 있었고, 클릭은
> 이미 성공하고 있었기 때문이다. `GetCursorPos` 되읽기를 넣자 한 번에 갈렸다.
>
> **교훈: 성공 경로에 계측이 없으면 "성공했지만 틀린" 상태는 보이지 않는다.** 실패 로그만으로는
> 부족하다.
>
> ---
>
> 아래는 이 결론에 이르기까지의 계측 기록이다. 기각된 가설들을 남기는 이유는, 같은 증상에
> 같은 오진을 반복하지 않기 위해서다.
>
> 0.2.11까지의 계측으로 실패 지점이 한 줄까지 좁혀졌다:
>
> ```
> agent started in session 1, created on desktop=Winlogon    ← 세션·데스크톱 모두 정확
> agent desktop=Winlogon attach=ok                           ← attach 성공
> inject FAILED at SendInput: in=(1091,721) mapped=(1091,721) err=5   ← ACCESS_DENIED
> secureInputAttempts=208 delivered=208 brokerFailed=0 skipUnauth=0   ← 라우팅 100% 정상
> ```
>
> `SetCursorPos`는 성공하는데(커서가 실제로 움직인다) `SendInput`만 거부된다. 좌표도, 세션도,
> 데스크톱 연결도 전부 맞다. **`WinSta0\Winlogon`에서 합성 입력이 차단되는 것이 secure desktop의
> 설계 목적 자체이므로, 유저모드 코드로 뚫는 방법은 없다.**
>
> 기각된 가설 (전부 실측으로):
> - ~~캡처가 secure desktop을 못 본다~~ → U1에서 반증. BitBlt·DXGI 둘 다 읽고, 폰에 UAC 창이 보인다
> - ~~프로세스가 잘못된 데스크톱에 생성된다~~ → `created on desktop=Winlogon`인데도 `err=5`
> - ~~코드 서명 + `uiAccess=true`가 답이다~~ → **OSLink 바이너리는 `uiAccess=false`인데도 된다.**
>   인증서를 샀으면 헛돈이었다
>
> 실제 메커니즘 (OSLink 설치본 실측, `C:\LDPlayer\OSLink\1.3.29.3_...`):
> ```
> LdVMou.sys   → Virtual Mouse      Manufacturer: ChangZhi   Status: OK
> LdVKbd.sys   → Virtual Keyboard   Manufacturer: ChangZhi   Status: OK
> LdScpVBus.sys→ Scp Virtual Bus    Manufacturer: ChangZhi   Status: OK
> devcon.exe   → 드라이버 설치 도구
> ```
> **가상 HID 드라이버로 넣은 입력은 HID 계층에서 올라오므로 Windows가 실제 마우스와 구별하지
> 못한다.** UIPI도 데스크톱 경계도 애초에 적용되지 않는다. TeamViewer·AnyDesk·Parsec도 같은 방식.
>
> 남은 선택지는 셋이고, **2026-08-06 사용자 판단으로 보류**:
>
> | | 방법 | 비용 | 대가 |
> |---|---|---|---|
> | A | `HKLM\...\Policies\System\PromptOnSecureDesktop = 0` | **코드 0줄** | 그 PC가 UAC 스푸핑 보호를 잃음 |
> | B | 서비스가 요청 프로그램을 직접 elevated 실행 | 소~중 | 임의 UAC 창은 여전히 못 누름 |
> | C | 가상 HID 드라이버 자체 개발 | EV 인증서 **매년** + 커널 리스크 | 정석이나 고정비가 붙음 |
>
> A가 유력한 이유: 프롬프트가 `WinSta0\Default`로 내려오면 SYSTEM 에이전트(System 무결성)가
> `consent.exe`(역시 SYSTEM)에 주입할 수 있어 UIPI가 막지 않는다. 그리고
> `secure_input_service_main.cpp:262`의 `start_agent(retrySession, current_input_desktop_name())`은
> 데스크톱 이름을 **동적으로 읽으므로 코드 수정이 필요 없다**. 단 `consent.exe`의 무결성 레벨은
> 실기 확인 전까지 가정이다.
>
> **U2a·U4는 헛수고가 아니다.** 세션 타겟팅과 좌표 매핑은 A·B·C 어느 길로 가도 그대로 필요하다.

## 3) 겹침 지도

한 덩어리로 처리해야 하는 것들. 따로 하면 같은 함수를 두 번 건드린다.

```
R3 (WGC→DXGI 복귀)  ≡  U0 (강등 고착 해제)       같은 코드
R1 (어댑터 재선택)   ≡  U3의 ACCESS_LOST 정책     같은 함수
R4 (런타임 중복)     ⊂  R1/R3 진행 시 반드시 마주침
V6 (보안 데스크톱)   ⊂  U2b
V13 (물리 세션 측정) ∥  P1 (동시 수행 가능)
```

**R1+R2+R3+R4 = U0 한 덩어리가 RDP 문제와 UAC 문제를 동시에 갚는다.**

## 4) 실행 순서

사용자 수동 확인이 필요한 항목은 뒤로 미루고 **혼자 끝낼 수 있는 코드 작업을 앞으로 당긴다.**
수동 확인은 한 번에 몰아서 요청한다.

### 트랙 A — 자율 진행 (코드 + 단위 테스트로 자체 검증 가능)

| 순서 | 항목 | 내용 | 규모 |
|---|---|---|---|
| A1 | **R1 + R2** | DXGI 어댑터 재선택 + 유령 출력 배제 (한 커밋) | 중 |
| A2 | **R3 = U0** | WGC 강등 고착 해제 + `secureDesktopActive` 상태 전달 | 소 |
| A3 | **R4** | 두 호스트 런타임의 폴백 로직 중복 제거 | 중 |
| A4 | **U2a** | 세션 타겟을 요청자 기준으로 (`WTSGetActiveConsoleSessionId` 제거) | 소 |
| A5 | **U4 + U5 + U2d** | 멀티모니터 좌표, 입력 결과 반환, 프로토콜 확장 | 중 |
| A6 | **N6** | 43000 병행 listen (트랙 B의 B1 결과가 통과일 때만) | 중 |

A1~A3은 RDP 문제와 UAC 문제의 **공통 기반**이라 따로 하면 같은 함수를 두 번 건드린다.
A4는 A5와 U2b보다 반드시 먼저다 — 안 하면 "엉뚱한 화면을 완벽하게 스트리밍"하게 된다.

### 트랙 B — 수동 확인 필요 (몰아서 요청)

| 순서 | 항목 | 필요한 것 | 게이트하는 작업 |
|---|---|---|---|
| B1 | **N1 최종 검증** | 회사 Wi-Fi에서 접속 시도 | N6, N4/N5 우선순위 |
| B2 | **P1 + V13** | RDP 끊고 물리 화면에서 1분 측정 | P2(NACK) 착수 여부 |
| B3 | **U1** | SYSTEM probe 실행 + UAC 창 띄운 상태 확인 | U2b 규모/방식 |
| B4 | **V 그룹** | Android 실기, 육안 비교 | 없음 (정리 성격) |

### 게이트 이후

| 조건 | 다음 작업 |
|---|---|
| B3에서 BitBlt 가능 | U2b/U2c → U3 (기존 GDI 워커 루프 재활용, 규모 축소) |
| B3에서 DXGI만 가능 | U2b/U2c → U3 (`GNLinkInputService`에 d3d11/dxgi 도입, 규모 증가) |
| B2에서 A1 기각 | P2보다 60fps 경로 재검토가 우선 |
| B2에서 A1 확정 | P2(NACK) 착수 |

**B1~B3은 합쳐서 한 시간이 안 걸리고 뒤 작업의 규모를 크게 바꾼다.** 트랙 A를 진행하는
동안 사용자가 편할 때 처리하면 된다.
