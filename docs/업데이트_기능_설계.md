## 2. 반영해야 할 기존 장애 (기록만 — 이 task 에서 고치지 않는다)

검증용 Claude 가 위임 시 지목한 4건. 각 건을 현재 트리에서 직접 재확인했고, **줄 번호를 실제 값으로 정정**해 적는다. `docs/full_code_audit_2026-09-08.md:94` 의 `I01` 항목이 (a)(그리고 부분적으로 (b)(c))과 같은 결함을 이미 원장에 올려 두었다 — 이 문서는 그 항목의 설계 근거를 채우는 쪽이다.

### (a) 종료 목록과 payload 목록의 불일치 → 스테이징·롤백 없는 혼합버전 디렉터리

- `stop_running_product()` 의 `kImages` 는 4개다: `GNLinkHost.exe`, `GNLinkStream.exe`, `GNLinkCapture.exe`, `GNLinkInputService.exe` — `installer_main.cpp:160-162`.
- kPayload 는 6개 exe 를 담는다. 빠진 둘: `GNLinkClient.exe`, `GNLinkViewer.exe` — `installer_main.cpp:48-57` (5·6번 항목).
- `write_file` 은 공유 모드 0 + `CREATE_ALWAYS` 이므로 대상이 실행 중이면 실패한다 — `:104-106`.
- `do_install()` 의 payload 루프는 **선언 순서**대로 돌고 실패 시 즉시 코드 4 로 반환한다 — `:294-307`.
- **귀결(순서까지 확정)**: 사용자가 PC 클라이언트를 켜 둔 채 업데이트하면 1~4번(`GNLinkHost`, `GNLinkStream`, `GNLinkInputService`, `GNLinkCapture`)은 이미 새 버전으로 덮인 뒤 5번 `GNLinkClient.exe` 에서 공유 위반으로 실패한다. 되돌리기가 없으므로 디렉터리에는 **신버전 exe 4개 + 구버전 `GNLinkClient.exe`/`GNLinkViewer.exe` + 구버전 `ui\*.html`** 가 남는다. 6·7·8번은 시도조차 되지 않는다.
- 등록 단계(서비스·방화벽·바로가기·Uninstall 키)는 `return 4` 뒤라 전혀 실행되지 않으므로, `DisplayVersion` 은 **구버전 값 그대로** 남는다 → 다음 실행 시 `detect_state()` 가 여전히 `Older` 로 보고, 실제 디스크 상태(혼합)와 레지스트리의 주장이 어긋난다.

### (b) `taskkill /F /T` 는 프로세스 트리를 죽인다 → Host 의 자식으로 뜬 업데이터는 교체 도중 함께 죽는다

## 3. 설계 초안 — 결정 가능한 부분만

4절의 미결(서명 체계, manifest 스키마, 서버 엔드포인트, Android 정책)에 **의존하지 않는** 부분만 적는다. 미결에 걸리는 지점은 본문에서 "→ 4.x" 로 표시하고 비워 둔다.

### 3.1 Windows 업데이터 상태기계

단계와 각 단계의 실패 처리. 상태는 스테이징 디렉터리(3.2)의 상태 파일로 영속화해, 중간에 프로세스가 죽어도 다음 기동이 어디서 끊겼는지 알 수 있게 한다.

| # | 상태 | 하는 일 | 실패 시 |
|---|---|---|---|
| 0 | `Idle` | 아무것도 하지 않음 | — |
| 1 | `CheckRequested` | 상호배제 획득(3.3) → 업데이트 정보 조회 | 락 실패면 즉시 종료(다른 업데이트 진행 중). 조회 실패면 `Idle` 복귀 + 로그, 제품 동작 무영향 |
| 2 | `Evaluate` | 받은 버전과 `kProductVersion` 을 `compare_versions()`(2(d))로 비교 | 같거나 낮으면 `Idle`. 파싱 불가면 `Idle` + 로그 |
| 3 | `Download` | 아티팩트를 스테이징 디렉터리의 임시 파일로 받는다. **현행 `http_post` 로는 불가**(1.4.4) — 신규 다운로드 경로 필요 | 부분 파일 삭제 후 `Idle`. 재시도는 다음 확인 주기로 미룸(즉시 루프 금지) |
| 4 | `Verify` | (i) 크기 일치, (ii) 콘텐츠 해시 일치, (iii) **출처 검증 → 4.1 Codex 결정 대기** | 아티팩트 삭제 + `Idle` + 로그. **검증 실패는 절대 다음 단계로 넘기지 않는다** |
| 5 | `Prepare` (handshake) | 교체 대상 프로세스들에게 "곧 교체한다"를 알리고 각자 안전 지점 도달을 확인 | 준비 응답이 시한 내에 오지 않으면 교체하지 않고 `Idle` 로 물러난다(강제 종료로 승격하지 않는다). 아티팩트는 보존해 다음 기회에 재시도 |
| 6 | `Quiesce` | 제품을 **정상 종료**시킨다. 대상은 kPayload 의 6개 exe 전부 — (a) 가 지목한 `GNLinkClient.exe`/`GNLinkViewer.exe` 포함. 서비스는 SCM 정지(1.1.6) | 시한 내 미종료면 `Prepare` 와 같은 규칙으로 물러난다 |
| 7 | `Swap` | 새 파일을 설치 디렉터리에 반영 | **이 단계만 롤백이 필요하다** — 아래 참조 |
| 8 | `Register` | 서비스 재등록·방화벽·바로가기·Uninstall 키(`DisplayVersion` 포함) 갱신 | 실패 항목을 기록하고 `Rollback` 판단. `DisplayVersion` 갱신은 Swap 성공과 원자적으로 묶여야 한다((a) 의 어긋남 재발 방지) |
| 9 | `Relaunch` | 교체 전 상태에 맞춰 제품을 다시 띄운다((c)) | 재실행 실패는 롤백 사유가 아니라 보고 사유. 사용자가 시작메뉴로 켤 수 있는 상태는 이미 성립 |
| 10 | `Health` | 재실행된 제품이 살아 있고 기능하는지 관측(3.6) | 시한 내 미달성 → `Rollback` |
| 11 | `Done` / `Rollback` | 스테이징 정리, 상태 파일 종결 | — |

`Swap` 의 형태(결정 가능한 부분):

- 현행처럼 대상 경로에 직접 쓰는 방식은 (a) 를 구조적으로 재생산한다. 대신 **전량을 먼저 스테이징에 펼친 뒤, 디렉터리 단위로 바꾼다.**
- 두 후보:
  - **(S1) 파일 단위 `MoveFileExW(..., MOVEFILE_REPLACE_EXISTING | MOVEFILE_WRITE_THROUGH)`** — 구버전은 사전에 `<name>.old` 로 이름을 바꿔 두고, 전부 성공하면 `.old` 를 지우고 하나라도 실패하면 `.old` 를 되돌린다. 설치 경로가 그대로라 서비스 바이너리 경로·방화벽 규칙 경로가 무효화되지 않는다.
  - **(S2) 디렉터리 교체** — `GNLink.new` 를 완성한 뒤 `GNLink` → `GNLink.old`, `GNLink.new` → `GNLink`. 원자성은 더 높지만 이름 변경 순간 서비스 이미지 경로가 잠깐 어긋나고, `%ProgramFiles%` 하위 디렉터리 이름 변경 권한/ACL 상속을 별도로 확인해야 한다.
- **권고: (S1).** 서비스 등록 경로(1.1.6)와 방화벽 규칙 경로(1.1.7)가 절대 경로로 박혀 있어 설치 경로를 유지하는 쪽이 부작용이 적고, 되돌리기 단위가 파일이라 실패 지점이 명확하다. 어느 쪽이든 **부분 성공 상태로 끝나지 않는 것**이 요구사항이다.
- `MOVEFILE_DELAY_UNTIL_REBOOT` 는 마지막 수단으로만 — 언인스톨이 이미 같은 폴백을 쓴다(`installer_main.cpp:411-413`). 업데이트에서 이걸 쓰면 "성공했는데 재부팅 전까지 구버전" 이라는 관측 불가능한 상태가 생기므로, 쓰더라도 결과를 `Done` 이 아니라 별도 상태로 보고해야 한다.

### 3.2 업데이터를 어디에 두고 어떻게 떼어낼 것인가 ((b) 근거)

두 요구가 **동시에** 성립해야 한다.

1. **설치 디렉터리 밖**에 있어야 한다 — `%ProgramFiles%\GNLink\` 안에 있으면 자기 자신이 교체 대상이 되고, 실행 중 이미지라 `write_file`(공유 0)이 실패한다((a) 와 같은 실패 모드).
2. **종료 시점에 `GNLinkHost.exe` 의 살아있는 자손이 아니어야** 한다 — `taskkill /F /T` 는 살아있는 부모→자식 사슬을 따라간다((b)).

**위치 (권고안):** `%ProgramFiles%\GNLink.update\` (설치 디렉터리의 형제).

- 근거: `%ProgramFiles%` 하위는 관리자만 쓸 수 있으므로 설치기 머리주석(`installer_main.cpp:1-13`)이 지키려는 불변식 — "제품 바이너리는 사용자 쓰기 가능한 곳에 두지 않는다" — 이 스테이징된 아티팩트에도 그대로 적용된다.
- **`%TEMP%` 는 부적합하다.** 언인스톨은 그렇게 하지만(`:353-357`) 그건 지우기만 하는 코드다. 업데이트는 *실행될 바이너리*를 스테이징하므로, 사용자 쓰기 가능한 폴더에 두면 비관리자가 그 파일을 바꿔치기해 관리자 권한으로 실행시킬 수 있다 — 설치기가 존재하는 이유를 정면으로 되돌린다. 같은 이유로 `%ProgramData%\GNLink\` 도 기본 ACL 이 사용자 쓰기를 허용하므로 **명시적 ACL 을 걸지 않는 한** 쓰지 않는다.
- 부수 효과: `do_uninstall()` 은 kPayload + `GNLinkSetup.exe` 만 지우므로(1.1.10) 새 디렉터리는 언인스톨에서 남는다. 언인스톨이 이 디렉터리도 정리하도록 하는 것은 **구현 시 반영할 항목**으로 여기 적어 둔다.

**떼어내기 (detach):**

- `DETACHED_PROCESS`·`CREATE_NEW_PROCESS_GROUP` 는 콘솔/신호 관계만 끊고 **부모-자식 관계는 그대로 남기므로 (b) 를 해결하지 못한다.** `CREATE_BREAKAWAY_FROM_JOB` 도 job 에만 관한 것이고, 호스트는 job 을 쓰지 않는다(1.3).
- 후보 두 가지:
  - **(D1) 조부모 고아화** — 호스트가 짧게 사는 런처를 띄우고, 런처가 실제 업데이터를 띄운 뒤 **즉시 종료**한다. 업데이터의 부모는 이미 죽은 프로세스라, `taskkill /T` 가 `GNLinkHost.exe` 에서 출발해 살아있는 자식을 열거할 때 업데이터에 도달하지 못한다. 새 권한 표면이 없고 호스트가 이미 상승돼 있어(1.2) 추가 UAC 도 없다.
  - **(D2) 일회성 예약 작업** — 업데이터를 SYSTEM 권한 예약 작업으로 등록해 작업 스케줄러가 부모가 되게 한다. 트리 무관성이 가장 확실하고 PC 클라이언트(비상승, 1.2)에서도 트리거할 여지가 생기지만, 새 등록 지점(작업 등록/삭제 수명)과 그 권한이 새 공격 표면이다.
- **권고: (D1)** 을 기본으로 하고, PC 클라이언트발 업데이트에서 상승 수단이 필요해지면 (D2) 또는 기존 LocalSystem 서비스 경유를 재검토한다. 어느 쪽이든 `Swap` 을 수행하는 프로세스는 `Quiesce` 가 죽이는 이미지 이름 목록(`GNLinkHost.exe` 등)과 **다른 이름**이어야 한다 — `taskkill /IM` 은 이미지 이름으로 지목하므로, 업데이터가 `GNLinkSetup.exe` 그 자체라면 이름이 목록에 없어 안전하지만 `GNLinkHost.exe` 의 사본이어서는 안 된다.

### 3.3 동시 업데이트 상호배제

- 수단: **명명된 뮤텍스**(예: `Global\GNLink.Update`). `Global\` 네임스페이스여야 세션이 달라도 배타가 성립한다(호스트는 사용자 세션, 서비스는 세션 0).
- 배제해야 할 상대는 다른 업데이터만이 아니다. 사용자가 직접 실행한 `GNLinkSetup.exe` 와도 배타여야 한다 — 지금 설치기에는 상호배제가 없다(2 참고 항목). 따라서 락 획득 코드는 **설치기와 업데이터가 공유하는 지점**에 있어야 한다.
- 락 획득 실패 시 동작: 대기하지 않고 즉시 물러난다. 업데이트는 지연 가능한 작업이고, 두 프로세스가 같은 디렉터리를 교체하는 상황을 만드는 것보다 한 주기 미루는 편이 항상 낫다.
- 뮤텍스는 프로세스 종료 시 사라지므로, 교체 도중 죽은 경우를 위해 **스테이징 상태 파일**(3.1)이 별도로 필요하다. 다음 기동은 뮤텍스가 아니라 상태 파일을 보고 "중단된 교체가 있는가"를 판정한다.

### 3.4 보존 대상 경로 (교체가 건드리면 안 되는 것)

1.6 의 표가 그대로 보존 목록이다. 확인된 사실:

- **모두 설치 디렉터리 밖에 있으므로, 설치 디렉터리를 통째로 바꾸는 (S2) 조차 이들을 건드리지 않는다.**
- 따라서 업데이트 설계상의 보존 요구는 "복사·복원"이 아니라 **"삭제·정리 대상에서 제외"** 다. 구체적으로:
  - `%LOCALAPPDATA%\remote60\host.json` — 지우면 호스트가 로그아웃 상태로 뜬다(`host_app_main.cpp:1441-1447` 이 이 파일로 로그인 여부를 정한다).
  - `%LOCALAPPDATA%\GNLink\` 전체 — 설정(`client.txt`), 잠금해제 자격증명(`unlock_*.cred`), 로그 4종. 로그는 NAS 대조의 근거이므로(프로젝트 규칙) 업데이트가 회전·삭제해서는 안 된다.
  - `HKCU\…\Run` 값 `remote60` — 자동 시작. 교체 중 호스트를 내렸다가 올릴 때 이 값을 다시 쓸 필요는 없다(값은 경로만 담고 설치 경로는 불변).
  - `HKLM\…\Uninstall\GNLink` — `DisplayVersion` 만 갱신 대상이고 나머지 값은 유지. `InstallLocation` 이 바뀌지 않는 것이 (S1) 권고의 이유 중 하나다.
- 반대로 **교체 대상**은 kPayload 8개 + `GNLinkSetup.exe`(1.1.2) 뿐이다.

### 3.6 각 단계의 완료조건 (무엇이 관측되면 성공인가)

"성공했을 것" 이 아니라 **관측 가능한 사실**로 적는다.

| 단계 | 완료조건 (관측) |
|---|---|
| `Evaluate` | 로그에 `installed=<a> available=<b> decision=<update|skip>` 한 줄. `compare_versions` 의 부호가 결정과 일치 |
| `Download` | 임시 파일 크기 == 공표 크기, 부분 파일 잔존 0 |
| `Verify` | 해시 일치 + 출처 검증 결과(→ 4.1). **실패 시 아티팩트 파일이 디스크에서 사라진 것**까지가 완료조건 |
| `Prepare` | 교체 대상 6개 exe 각각에 대해 "준비됨" 또는 "미실행" 이 확정. 미확정 잔존 0 |
| `Quiesce` | `GNLinkHost/Stream/Capture/InputService/Client/Viewer` 6개 이미지의 실행 중 인스턴스 0, 서비스 상태 `SERVICE_STOPPED`. **(a) 가 빠뜨린 Client/Viewer 를 여기서 반드시 센다** |
| `Swap` | 설치 디렉터리의 9개 항목 해시가 전부 새 버전과 일치, `.old` 잔존 0. 부분 일치 = 실패 |
| `Register` | `DisplayVersion` == 새 버전, 서비스 이미지 경로 == 설치 경로, 방화벽 규칙 1건 존재, `.lnk` 2개 존재 |
| `Relaunch` | 교체 전에 돌고 있던 것과 같은 구성이 다시 떠 있음: 호스트가 떠 있었으면 `GNLinkHost.exe` 1개 + (로그인 상태였으면) `GNLinkStream.exe` 1개 |
| `Health` | 호스트 로그에 새 버전 배너 + 디렉터리 하트비트 성공 1회. 클라이언트는 셸 창 생성 + 설정 로드 성공 |
| `Rollback` | 설치 디렉터리 9개 항목 해시가 전부 **구** 버전과 일치, `DisplayVersion` == 구 버전, 제품이 교체 전 구성으로 다시 떠 있음 |

### 3.7 검증 하네스에서 어떻게 재현할 것인가

이 저장소의 기존 방식(결정론적 단위 회귀 + 자동화 스크립트)에 맞춘다.

- **버전 비교**: 2(d) 의 추출을 전제로 `compare_versions` 단위 테스트를 새 타깃으로 추가한다. 현재 테스트 0건이므로 경계값(성분 개수 불일치, 접미사, 큰 성분)이 전부 신규 커버리지다.
- **상태기계**: 파일시스템·프로세스 조작을 seam 으로 주입해 실제 파일 없이 전이를 돌린다. 선례가 있다 — `H264Encoder::set_transform_for_test` 로 실 MFT 없이 실패 경로를 구동한 방식(`docs/history.md` #423). 같은 원칙(제품 기본 동작 불변, 상태 직접 세팅 금지, 실제 호출 경로 실행)을 적용한다.
- **(a) 재현**: 가짜 설치 트리를 만들고 `GNLinkClient.exe` 자리의 파일을 공유 0 으로 열어 둔 채 교체를 시도한다. **수정 전에는 앞 파일들이 덮인 채 실패**, 수정 후에는 어느 파일도 바뀌지 않았거나 전부 바뀌었음을 해시로 단정한다.
- **(b) 재현**: 부모 프로세스를 만들고 그 자식으로 업데이터 스텁을 띄운 뒤 `taskkill /F /T` 를 부모에 건다. (D1) 적용 전에는 스텁이 죽고, 적용 후에는 살아남아 교체를 마치는 것을 종료 코드로 단정한다.
- **(c) 재현**: `Relaunch` 후 대상 프로세스 인스턴스 수를 센다.
- **상호배제**: 뮤텍스를 잡은 상태에서 두 번째 인스턴스를 띄워 **대기하지 않고** 물러나는지(종료 코드) 확인한다.
- **환경 제약**: 이 회귀들은 RDP 여부와 무관하다(캡처·인코딩을 쓰지 않는다). 다만 프로젝트 규칙상 실기·통합 판정은 `qwinsta` 로 RDP 세션 없음을 확인한 뒤에만 근거로 쓴다.

## 4. Codex 결정 대기 (이 task 에서 결론내지 않는다)

아래 네 절은 **의도적으로 비워 둔 것**이다. 사실만 적고 선택은 하지 않는다.

### 4.1 아티팩트 출처 검증 방식 (서명 체계) — **Codex 결정 대기**

결정에 필요한 현행 사실(전부 확인됨):

- **제품에 HTTPS 가 없다.** `parse_directory_url()` 이 `https://` 를 명시적으로 거부한다 (`apps/native_poc/src/directory_client.cpp:83-93`, 오류 문구 `:87-91`; 계약은 `directory_client.hpp:29`, `:90`).
- native 코드 전체에 **WinHTTP·Schannel·기타 TLS 스택이 전무하다** (검색 0건, 1.4.4).
- 서버는 TLS 를 켤 수 있으나 환경변수 의존이며(`apps/directory/server.js:58-59`, `:1344-1360`), 꺼져 있으면 "tokens travel in clear" 경고를 찍는다 (`:1355-1357`). **현 NAS 배포본의 TLS 여부는 미확인.**
- Android 는 그 때문에 cleartext 를 전역 허용 중이다 (`app/src/main/res/xml/network_security_config.xml`, 파일 주석이 이유와 한계를 명시).
- **Authenticode 서명 인프라가 없다.** `dist/GNLinkSetup-*.exe` 는 빌드 산출물을 그대로 복사한 것이고(`docs/history.md` #426), 저장소·자동화에 서명 단계가 없다.
- 즉 지금은 다운로드 채널의 기밀성·무결성도, 아티팩트 자체의 출처 증명도 **어느 쪽도 없다**. 어떤 방식을 택하든 이 두 공백 중 무엇을 먼저 닫는지가 선택지다.

→ **방식 선택은 여기 쓰지 않는다.**

### 4.2 Android 서명·키 정책, 앱 데이터 보존 가능 여부 — **Codex 결정 대기**

결정에 필요한 현행 사실:

- `app/build.gradle.kts` 에 `signingConfigs` 가 없고 release 에도 `signingConfig` 지정이 없다(1.5). 배포된 것은 `assembleDebug` 산출물이며 debug 키로 서명돼 있다 (`docs/history.md` #331, #333).
- 배포 연속성은 **동일 인증서**(`dcc806ae…2990`)에 의존해 왔다 (`docs/history.md:5566`, `:5815`).
- Android 는 서명 키가 바뀐 APK 를 같은 `applicationId` 의 업데이트로 받지 않는다. 따라서 debug 키 → 릴리스 키 전환은 **제거 후 재설치**를 뜻하고, `android:allowBackup="true"` 임에도 제거 시 앱 데이터는 사라진다.
- 현재 권한은 `INTERNET`·`ACCESS_NETWORK_STATE` 둘뿐이고 `REQUEST_INSTALL_PACKAGES` 는 없다(1.5).
- `versionCode`(11) / `versionName`("0.2.12") 는 Windows 제품 버전(0.2.104)과 **별도 축**으로 움직여 왔다.

→ **키 전환 여부·시점, 데이터 보존 대책, 인앱 업데이트 채택 여부 모두 비워 둔다.**

### 4.3 manifest 스키마 확정 — **Codex 결정 대기**

관련 현행 제약만 기록:

- 제품 HTTP 클라이언트는 POST 전용이고 응답 본문을 **64 KB 에서 자른다** (`directory_client.cpp:346-355`). manifest 가 이 한계 안에 들어와야 하는지, 아니면 클라이언트를 먼저 고칠지가 스키마 크기 제약과 얽힌다.
- 버전 비교 의미론은 `compare_versions()` 의 규칙을 따를 수밖에 없다(2(d)) — 성분 숫자 비교, 비숫자 접미사에서 중단. manifest 의 버전 표기는 이 규칙과 모순되지 않아야 한다.

→ **필드 구성·형식은 비워 둔다.**

### 4.4 서버 신규 엔드포인트 확정 — **Codex 결정 대기**

관련 현행 제약만 기록:

- 라우트 테이블은 `메서드 경로` **정확 일치**이며 접두사 매칭도 정적 파일 서빙도 없다 (`server.js:564-585`). 바이너리를 서버가 직접 내보내려면 새 코드가 필요하다.
- 기존 8개 라우트는 전부 JSON POST 이고, 인증은 Bearer 세션 또는 `x-host-token` 두 종류뿐이다(1.4.1, 1.4.2).
- 세션은 메모리 전용이라 서버 재시작으로 소멸한다 (`server.js:490`). 업데이트 확인이 세션 인증을 요구하면 이 성질을 함께 다뤄야 한다.
- 로그 업로드는 계정/기기별 레이트 리밋을 이미 갖고 있다 (`:346-349`) — 새 엔드포인트의 남용 방지에 참고할 선례.

→ **경로·메서드·인증·아티팩트 호스팅 위치 모두 비워 둔다.**

## 5. 미확인 항목 (코드로 확인하지 못한 것)

1. **현 NAS 디렉터리 서버가 TLS 를 켜고 실행 중인지** — `REMOTE60_DIR_TLS_KEY/CERT` 는 배포 환경변수라 저장소 코드로는 알 수 없다. `automation/deploy_directory.ps1` 의 유닛 정의는 이번 조사 범위에서 열지 않았다.
2. **`taskkill /T` 의 자식 열거 시점 의미론** — 문서상 "프로세스와 그 자식 트리" 이지만, 실행 순간 살아있는 부모 사슬만 따라간다는 3.2 (D1) 의 전제는 **코드가 아니라 플랫폼 동작에 대한 판단**이다. 실행 검증(테스트)으로 확정해야 한다.
3. **`%ProgramFiles%\GNLink.update\` 의 실제 ACL 상속** — `%ProgramFiles%` 하위가 관리자 전용이라는 것은 설치기 주석의 근거(`installer_main.cpp:1-13`)와 일반적 Windows 동작이지만, 새로 만든 하위 디렉터리의 상속 결과를 이번에 실측하지 않았다.
4. **Windows 클라이언트 셸에 백그라운드 작업을 붙일 기존 지점** — 로그 업로더가 셸 프로세스 안에서 돈다는 사실(`log_upload.cpp:25-28` 주석)까지는 확인했으나, 확인 스레드를 붙이기 좋은 구체적 훅은 특정하지 않았다.
5. **Android 앱이 서버와 통신하는 코드 경로의 세부** — 매니페스트·gradle·배포 형태는 확인했지만, Kotlin 측 네트워크 코드(`LogUploader.kt`, `MainActivity.kt`)는 이번 범위에 없어 열지 않았다.
6. **설치 디렉터리에 남는 기타 파일** — `do_uninstall()` 이 kPayload + `GNLinkSetup.exe` 만 지운다는 것은 확인했으나(1.1.10), 실제 설치본이 그 9개 외에 무엇을 남기는지는 실기 관측이 필요하다.
