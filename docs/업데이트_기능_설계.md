설계에 직접 영향을 주는 귀결:

- `GNLinkInputService.exe` 는 asInvoker 지만 서비스로는 **LocalSystem** 으로 돈다(1.1.6). 상승은 설치 시 부모(설치기)에게서 온다.

### 1.3 Host 수명주기 — 자식 프로세스와 job object

관측된 부모-자식 관계(전부 코드 근거):

```
GNLinkHost.exe            (requireAdministrator, 트레이/로그인 창)
  └─ GNLinkStream.exe     CreateProcessW, host_app_main.cpp:444-446
       └─ GNLinkCapture.exe  CreateProcessW + job object, gdi_capture_process.cpp:272-283

GNLinkClient.exe          (asInvoker, WebView2 셸)
  └─ GNLinkViewer.exe     CreateProcessW, client_shell_main.cpp:529-532
```

- **Host → Stream**: `host_app_main.cpp:341` 에서 `executable_dir() + L"\\GNLinkStream.exe"` 를 잡고, `Supervise()` 루프가 `CreateProcessW(exe, ..., CREATE_NO_WINDOW, ...)` 로 띄운 뒤 `WaitForSingleObject(INFINITE)` 로 감시한다 (`:444-479`). 자식이 죽으면 재기동하며 크래시 스트릭·백오프를 계산한다 (`:481-486` 부근). 종료는 `TerminateChild()` (`:336-339`), 핸들 소유권은 `Supervise()` 단독 (H-01 원장, `:330-336` 주석).
  - **job object 없음.** Host 는 Stream 을 job 에 넣지 않는다.
- **Stream → Capture**: `gdi_capture_process.cpp:246-283`.
  - `CreateJobObjectW` + `JOBOBJECT_EXTENDED_LIMIT_INFORMATION.LimitFlags = JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` (`:246-255`).
  - 워커를 `CREATE_SUSPENDED` 로 만들고 → `AssignProcessToJobObject` → `ResumeThread` (`:272-288`). 즉 **부모가 죽으면 캡처 워커도 반드시 죽는다.**

## 2. 반영해야 할 기존 장애 (기록만 — 이 task 에서 고치지 않는다)

검증용 Claude 가 위임 시 지목한 4건. 각 건을 현재 트리에서 직접 재확인했고, **줄 번호를 실제 값으로 정정**해 적는다. `docs/full_code_audit_2026-09-08.md:94` 의 `I01` 항목이 (a)(그리고 부분적으로 (b)(c))과 같은 결함을 이미 원장에 올려 두었다 — 이 문서는 그 항목의 설계 근거를 채우는 쪽이다.

### (a) 종료 목록과 payload 목록의 불일치 → 스테이징·롤백 없는 혼합버전 디렉터리

### (d) 재사용 후보 — `compare_versions()`

- `installer_main.cpp:444-464`. 이미 **숫자 성분 비교**이고 사전순이 아니다(1.1.11). 업데이터의 "새 버전인가" 판정에 그대로 쓸 수 있는 유일한 기존 구현이다.
- 다만 지금은 설치기 번역 단위의 익명 네임스페이스 안에 있고(`:24` `namespace {`), 호출자도 같은 파일뿐이며 **단위 테스트가 없다**.
**Codex 확정 (2026-09-08): "공용 헤더 추출" 이 아니다.** 버전 비교는 세 런타임에서 벌어진다 — 서버의 JS(manifest 발행), Windows 의 C++(설치기·업데이터), Android 의 Kotlin. **헤더는 이 셋 사이에서 공유될 수 없다.** 따라서 설계 단위는 코드가 아니라 계약이다:

- **① 버전 비교 계약**을 문서로 확정한다. 현행 `compare_versions()` 의 의미론이 그 출발점이다: 각 위치의 연속 숫자를 성분으로 모아 비교(`:449-455`), 누락 성분은 0(`"0.1"` == `"0.1.0"`), 숫자도 `.` 도 아닌 문자를 만나면 비교 중단(`:459-463`). 계약에는 성분 개수 불일치·선행 0·비숫자 접미사·성분 오버플로(`unsigned long` 누적, `:451`,`:453`) 처리가 명시돼야 한다.
- **② 3개 런타임 공통 테스트 벡터**를 하나의 데이터 파일로 두고, C++·Kotlin·JS 각각의 테스트가 **같은 벡터를 읽어** 같은 답을 내는지 확인한다. 구현이 세 벌인 것은 피할 수 없으므로, 일치는 공유 코드가 아니라 공유 벡터로 보장한다.
- **③ 추출은 같은 언어 안에서만.** C++ 쪽에서는 `installer_main.cpp` 의 익명 네임스페이스(`:24`)에 갇힌 현재 구현을 헤더로 올려 설치기·업데이터·단위 테스트가 공유하게 한다. 이것은 ①②와 별개의, C++ 내부에 한정된 정리다.
- 현재 이 함수의 단위 테스트는 **0건**이므로(1.1.11) ②의 벡터가 곧 첫 커버리지가 된다. **실행은 이 task 범위 밖.**

### (참고) 계획 밖에서 눈에 띈 사항 — 고치지 않고 기록만

- `has_flag()` 는 커맨드라인 전체에 대한 **부분 문자열 검색**이다 (`installer_main.cpp:583-590`). 새 인자를 추가할 때 기존 플래그와 접두사가 겹치면(예: `/stage` 는 `/s` 를 포함) 의도치 않게 silent 로 해석된다. 업데이트용 인자를 설계할 때 이 함수의 성질을 전제로 이름을 고르거나, 인자 파싱을 바꾸는 별도 판단이 필요하다.
- 설치기에 **동시 실행 상호배제가 없다** (`wWinMain:593-616` 어디에도 뮤텍스·락 파일 없음). 지금도 `GNLinkSetup.exe` 두 개를 동시에 돌리면 같은 디렉터리에 교차로 쓴다.

## 3. 설계

이 절은 최초 작성 시 4절이 미결이라 "결정 가능한 부분만" 담았다. 개정 뒤에는 4절이 확정됐으므로 전송·서명에 걸리는 지점은 "→ 4.x" 로 **확정된 절을 가리킨다**(비워 둔 것이 아니다). 3.2 는 Codex 확정(`/T` 폐기 + 정확 대상 종료 + job 수명 + 실행 위치를 함께)에 맞춰 다시 썼다.

### 3.1 Windows 업데이터 상태기계

단계와 각 단계의 실패 처리. 상태는 스테이징 디렉터리(3.2)의 상태 파일로 영속화해, 중간에 프로세스가 죽어도 다음 기동이 어디서 끊겼는지 알 수 있게 한다.

| # | 상태 | 하는 일 | 실패 시 |
|---|---|---|---|
| 0 | `Idle` | 아무것도 하지 않음 | — |
| 1 | `CheckRequested` | 상호배제 획득(3.3) → 업데이트 정보 조회 | 락 실패면 즉시 종료(다른 업데이트 진행 중). 조회 실패면 `Idle` 복귀 + 로그, 제품 동작 무영향 |
| 2 | `Evaluate` | 받은 버전과 `kProductVersion` 을 `compare_versions()`(2(d))로 비교 | 같거나 낮으면 `Idle`. 파싱 불가면 `Idle` + 로그 |
| 3 | `Download` | 아티팩트를 스테이징 디렉터리의 임시 파일로 받는다. **현행 `http_post` 로는 불가**(1.4.4) — 신규 다운로드 경로 필요 | 부분 파일 삭제 후 `Idle`. 재시도는 다음 확인 주기로 미룸(즉시 루프 금지) |
| 4 | `Verify` | (i) 크기 일치, (ii) 콘텐츠 해시 일치, (iii) **출처 검증 — manifest detached 서명을 내장 공개키로 검증(4.1.2)** | 아티팩트 삭제 + `Idle` + 로그. **검증 실패는 절대 다음 단계로 넘기지 않는다** |
| 5 | `Prepare` (handshake) | 교체 대상 프로세스들에게 "곧 교체한다"를 알리고 각자 안전 지점 도달을 확인 | 준비 응답이 시한 내에 오지 않으면 교체하지 않고 `Idle` 로 물러난다(강제 종료로 승격하지 않는다). 아티팩트는 보존해 다음 기회에 재시도 |
| 6 | `Quiesce` | 제품을 **정상 종료**시킨다. 대상은 kPayload 의 6개 exe 전부 — (a) 가 지목한 `GNLinkClient.exe`/`GNLinkViewer.exe` 포함. 서비스는 SCM 정지(1.1.6) | 시한 내 미종료면 `Prepare` 와 같은 규칙으로 물러난다 |
| 7 | `Swap` | 새 파일을 설치 디렉터리에 반영 | **이 단계만 롤백이 필요하다** — 아래 참조 |
| 8 | `Register` | 서비스 재등록·방화벽·바로가기·Uninstall 키(`DisplayVersion` 포함) 갱신 | 실패 항목을 기록하고 `Rollback` 판단. `DisplayVersion` 갱신은 Swap 성공과 원자적으로 묶여야 한다((a) 의 어긋남 재발 방지) |
| 9 | `Relaunch` | 교체 전 상태에 맞춰 제품을 다시 띄운다((c)) | 재실행 실패는 롤백 사유가 아니라 보고 사유. 사용자가 시작메뉴로 켤 수 있는 상태는 이미 성립 |
| 10 | `Health` | 재실행된 제품이 살아 있고 기능하는지 관측(3.6) | 시한 내 미달성 → `Rollback` |
| 11 | `Done` / `Rollback` | 스테이징 정리, 상태 파일 종결 | — |

`Swap` 의 형태(결정 가능한 부분):

- 현행처럼 대상 경로에 직접 쓰는 방식은 (a) 를 구조적으로 재생산한다. 대신 **전량을 먼저 스테이징에 펼친 뒤, 디렉터리 단위로 바꾼다.**
- 두 후보:
  - **(S1) 파일 단위 `MoveFileExW(..., MOVEFILE_REPLACE_EXISTING | MOVEFILE_WRITE_THROUGH)`** — 구버전은 사전에 `<name>.old` 로 이름을 바꿔 두고, 전부 성공하면 `.old` 를 지우고 하나라도 실패하면 `.old` 를 되돌린다. 설치 경로가 그대로라 서비스 바이너리 경로·방화벽 규칙 경로가 무효화되지 않는다.
  - **(S2) 디렉터리 교체** — `GNLink.new` 를 완성한 뒤 `GNLink` → `GNLink.old`, `GNLink.new` → `GNLink`. 원자성은 더 높지만 이름 변경 순간 서비스 이미지 경로가 잠깐 어긋나고, `%ProgramFiles%` 하위 디렉터리 이름 변경 권한/ACL 상속을 별도로 확인해야 한다.
- **권고: (S1).** 서비스 등록 경로(1.1.6)와 방화벽 규칙 경로(1.1.7)가 절대 경로로 박혀 있어 설치 경로를 유지하는 쪽이 부작용이 적고, 되돌리기 단위가 파일이라 실패 지점이 명확하다. 어느 쪽이든 **부분 성공 상태로 끝나지 않는 것**이 요구사항이다.
- `MOVEFILE_DELAY_UNTIL_REBOOT` 는 마지막 수단으로만 — 언인스톨이 이미 같은 폴백을 쓴다(`installer_main.cpp:411-413`). 업데이트에서 이걸 쓰면 "성공했는데 재부팅 전까지 구버전" 이라는 관측 불가능한 상태가 생기므로, 쓰더라도 결과를 `Done` 이 아니라 별도 상태로 보고해야 한다.

### 3.2 업데이터를 어디에 두고 어떻게 떼어낼 것인가 ((b) 근거)

두 요구가 **동시에** 성립해야 한다.

1. **설치 디렉터리 밖**에 있어야 한다 — `%ProgramFiles%\GNLink\` 안에 있으면 자기 자신이 교체 대상이 되고, 실행 중 이미지라 `write_file`(공유 0)이 실패한다((a) 와 같은 실패 모드).
2. **종료 시점에 `GNLinkHost.exe` 의 살아있는 자손이 아니어야** 한다 — `taskkill /F /T` 는 살아있는 부모→자식 사슬을 따라간다((b)).

**위치 (권고안):** `%ProgramFiles%\GNLink.update\` (설치 디렉터리의 형제).

- 근거: `%ProgramFiles%` 하위는 관리자만 쓸 수 있으므로 설치기 머리주석(`installer_main.cpp:1-13`)이 지키려는 불변식 — "제품 바이너리는 사용자 쓰기 가능한 곳에 두지 않는다" — 이 스테이징된 아티팩트에도 그대로 적용된다.
- **`%TEMP%` 는 부적합하다.** 언인스톨은 그렇게 하지만(`:353-357`) 그건 지우기만 하는 코드다. 업데이트는 *실행될 바이너리*를 스테이징하므로, 사용자 쓰기 가능한 폴더에 두면 비관리자가 그 파일을 바꿔치기해 관리자 권한으로 실행시킬 수 있다 — 설치기가 존재하는 이유를 정면으로 되돌린다. 같은 이유로 `%ProgramData%\GNLink\` 도 기본 ACL 이 사용자 쓰기를 허용하므로 **명시적 ACL 을 걸지 않는 한** 쓰지 않는다.
- 부수 효과: `do_uninstall()` 은 kPayload + `GNLinkSetup.exe` 만 지우므로(1.1.10) 새 디렉터리는 언인스톨에서 남는다. 언인스톨이 이 디렉터리도 정리하도록 하는 것은 **구현 시 반영할 항목**으로 여기 적어 둔다.

**종료 방식 — `/T` 폐기 (Codex 확정 2026-09-08):**

> **경로를 분리하는 것만으로는 (b) 가 해결되지 않는다.** 업데이터를 어디에 두든, 종료 수단이 `taskkill /F /T` 인 한 "트리에 걸리지 않는다" 는 보장은 프로세스 부모 사슬의 우연에 기댄 것이다. 설계는 **종료 방식·job 수명·실행 위치 세 가지를 함께** 정해야 한다.

**① `/T` 를 쓰지 않는다.** 업데이트 경로의 정지 단계는 **종료할 프로세스를 정확히 지목**한다. 이미지 이름으로 트리를 쓸어버리는 대신, 교체 대상 6개 exe(1.1.2)의 **인스턴스를 열거해 각각을 명시적으로 종료**하고, 종료 여부를 개별로 확인한다. 그러면 "누가 누구의 자식인가" 가 정지 결과에 영향을 주지 않는다.

- 부수 효과가 아니라 요구사항이다: `Quiesce` 의 완료조건(3.6)이 "6개 이미지의 실행 중 인스턴스 0" 이므로, 정확히 지목해 세는 방식이 완료조건과 그대로 맞물린다.
- 현행 설치기의 `stop_running_product()`(`installer_main.cpp:137-178`)는 `/T` 를 쓰고 목록도 4개뿐이다((a)). 업데이트 경로는 이 함수를 그대로 쓰지 않는다.

**② job 수명을 설계에 넣는다.** 현재 job object 는 캡처 워커 한 곳에서만 쓰이며, `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` 로 `GNLinkStream.exe` 가 죽으면 `GNLinkCapture.exe` 도 반드시 죽는다(`gdi_capture_process.cpp:246-255`, 1.3). 이 성질은 정지 단계에서 **이용해야 할 보장**이지 회피 대상이 아니다 — Stream 을 정상 종료시키면 Capture 는 job 으로 확실히 따라 죽으므로, Capture 를 따로 죽이지 않아도 완료조건이 성립한다.

- 반대로 **업데이터는 어떤 job 에도 들어가서는 안 된다.** 제품 프로세스의 job 에 들어가면 그 job 이 닫힐 때 함께 죽는다. 업데이터를 띄울 때 job 상속 여부를 명시적으로 확인하는 것이 완료조건에 포함된다.
- 호스트는 Stream 을 job 에 넣지 않으므로(1.3) 현재로서는 업데이터가 상속받을 job 이 없다. 앞으로 호스트가 job 을 도입하면 이 전제가 깨지므로, 전제로 두지 말고 **확인 항목**으로 남긴다.

**③ 실행 위치는 위의 결과이지 해결책이 아니다.** `%ProgramFiles%\GNLink.update\` 는 (i) 교체 대상 디렉터리 밖이라는 요구와 (ii) 관리자 전용 ACL 이라는 보안 요구를 만족시키는 선택이며, 트리 kill 문제를 푸는 수단이 아니다. 그 문제는 ①이 푼다.

**부모-자식 분리에 대하여:** `DETACHED_PROCESS`·`CREATE_NEW_PROCESS_GROUP` 는 콘솔/신호 관계만 끊고 부모-자식 관계는 남긴다. `CREATE_BREAKAWAY_FROM_JOB` 은 job 에만 관한 것이다. 즉 **프로세스 분리로 트리 kill 을 피하려는 접근은 어느 것도 정면 해결이 아니다.** ①을 채택하면 이 논의 자체가 설계 전제에서 빠진다 — 그리고 그것이 5절 미확인 2번(`taskkill /T` 의 자식 열거 시점 의미론)을 **설계 위험에서 제거하는** 방법이다. 그 의미론에 의존하지 않는 설계가 되기 때문이다.

**그럼에도 남는 요구:** `Swap` 을 수행하는 프로세스의 이미지 이름은 정지 대상 6개와 **달라야 한다.** 정지 단계가 이름으로 인스턴스를 열거하므로, 업데이터가 `GNLinkHost.exe` 의 사본이면 자기 자신을 종료 대상으로 세게 된다.

### 3.3 동시 업데이트 상호배제

- 수단: **명명된 뮤텍스**(예: `Global\GNLink.Update`). `Global\` 네임스페이스여야 세션이 달라도 배타가 성립한다(호스트는 사용자 세션, 서비스는 세션 0).
- 배제해야 할 상대는 다른 업데이터만이 아니다. 사용자가 직접 실행한 `GNLinkSetup.exe` 와도 배타여야 한다 — 지금 설치기에는 상호배제가 없다(2 참고 항목). 따라서 락 획득 코드는 **설치기와 업데이터가 공유하는 지점**에 있어야 한다.
- 락 획득 실패 시 동작: 대기하지 않고 즉시 물러난다. 업데이트는 지연 가능한 작업이고, 두 프로세스가 같은 디렉터리를 교체하는 상황을 만드는 것보다 한 주기 미루는 편이 항상 낫다.
- 뮤텍스는 프로세스 종료 시 사라지므로, 교체 도중 죽은 경우를 위해 **스테이징 상태 파일**(3.1)이 별도로 필요하다. 다음 기동은 뮤텍스가 아니라 상태 파일을 보고 "중단된 교체가 있는가"를 판정한다.

### 3.4 보존 대상 경로 (교체가 건드리면 안 되는 것)

1.6 의 표가 그대로 보존 목록이다. 확인된 사실:

- **모두 설치 디렉터리 밖에 있으므로, 설치 디렉터리를 통째로 바꾸는 (S2) 조차 이들을 건드리지 않는다.**
- 따라서 업데이트 설계상의 보존 요구는 "복사·복원"이 아니라 **"삭제·정리 대상에서 제외"** 다. 구체적으로:
  - `%LOCALAPPDATA%\remote60\host.json` — 지우면 호스트가 로그아웃 상태로 뜬다(`host_app_main.cpp:1441-1447` 이 이 파일로 로그인 여부를 정한다).
  - `%LOCALAPPDATA%\GNLink\` 전체 — 설정(`client.txt`), 잠금해제 자격증명(`unlock_*.cred`), 로그 4종. 로그는 NAS 대조의 근거이므로(프로젝트 규칙) 업데이트가 회전·삭제해서는 안 된다.
  - `HKCU\…\Run` 값 `remote60` — 자동 시작. 교체 중 호스트를 내렸다가 올릴 때 이 값을 다시 쓸 필요는 없다(값은 경로만 담고 설치 경로는 불변).
  - `HKLM\…\Uninstall\GNLink` — `DisplayVersion` 만 갱신 대상이고 나머지 값은 유지. `InstallLocation` 이 바뀌지 않는 것이 (S1) 권고의 이유 중 하나다.
- 반대로 **교체 대상**은 kPayload 8개 + `GNLinkSetup.exe`(1.1.2) 뿐이다.

### 3.7 검증 하네스에서 어떻게 재현할 것인가

이 저장소의 기존 방식(결정론적 단위 회귀 + 자동화 스크립트)에 맞춘다.

- **버전 비교**: 2(d) 확정대로 **하나의 공통 테스트 벡터 파일**을 두고 C++·Kotlin·JS 세 런타임의 테스트가 각각 그것을 읽어 같은 답을 내는지 확인한다(헤더 공유가 불가하므로 일치는 벡터로 보장한다). 현재 C++ 쪽 테스트가 0건이므로 경계값(성분 개수 불일치, 선행 0, 비숫자 접미사, 성분 오버플로)이 전부 신규 커버리지다.
- **상태기계**: 파일시스템·프로세스 조작을 seam 으로 주입해 실제 파일 없이 전이를 돌린다. 선례가 있다 — `H264Encoder::set_transform_for_test` 로 실 MFT 없이 실패 경로를 구동한 방식(`docs/history.md` #423). 같은 원칙(제품 기본 동작 불변, 상태 직접 세팅 금지, 실제 호출 경로 실행)을 적용한다.
- **(a) 재현**: 가짜 설치 트리를 만들고 `GNLinkClient.exe` 자리의 파일을 공유 0 으로 열어 둔 채 교체를 시도한다. **수정 전에는 앞 파일들이 덮인 채 실패**, 수정 후에는 어느 파일도 바뀌지 않았거나 전부 바뀌었음을 해시로 단정한다.
- **(b) 재현**: 부모 프로세스를 만들고 그 자식으로 업데이터 스텁을 띄운 뒤 `taskkill /F /T` 를 부모에 건다. (D1) 적용 전에는 스텁이 죽고, 적용 후에는 살아남아 교체를 마치는 것을 종료 코드로 단정한다.
- **(c) 재현**: `Relaunch` 후 대상 프로세스 인스턴스 수를 센다.
- **상호배제**: 뮤텍스를 잡은 상태에서 두 번째 인스턴스를 띄워 **대기하지 않고** 물러나는지(종료 코드) 확인한다.
### 3.8 한 시도는 한 릴리스 — 스냅샷 staging (2026-09-08 구현)

`Download` 는 **검증된 manifest 가 준 목록 전체**를 받는다. 파일마다 "지금 latest 가 뭐냐" 를 다시
묻지 않는다. 서버는 그 사이에 움직일 수 있고, 그러면 **절반은 이 빌드 절반은 저 빌드인 설치**가
나온다. 그래서:

  * staging 디렉터리가 **`releaseId` 로 키잉**된다(`<stagingDir>\r-<releaseId>`). 두 릴리스가 같은
    자리를 쓸 수 없으므로, 한쪽의 절반 받은 파일이 다른 쪽의 파일로 완성되는 일이 없다.
  * `VerifyDownload` 는 **모든** 아티팩트의 크기와 해시를 검사한다. 하나라도 어긋나면 릴리스 전체를
    버린다.
  * `Swap` 은 시작 전에 **staged 릴리스가 있는지**와 **payload 이름 전부가 그 릴리스에 있는지**를
    확인한다. 없으면 아무것도 움직이지 않는다. 이것이 "모든 파일을 받아 검증한 뒤에만 교체 진입"
    을 관례가 아니라 **구조**로 만드는 지점이다.

#### 3.8.1 "혼합 0" 은 네 장치가 함께 만든다 — 무엇이 무엇을 막는지

이 절을 **"`releaseId` 가 혼합을 막는다"** 로 요약하면 안 된다. 그렇게 요약해 두면 나중에 누군가
나머지 셋 중 하나를 걷어내도 요약과 어긋나지 않고, **방어가 조용히 사라진다.** 각 장치가 정확히
무엇을 막는지 적어 둔다.

| 장치 | 정확히 무엇을 막는가 | 없으면 무슨 일이 일어나는가 | 증거 |
|---|---|---|---|
| **재조회를 하지 않는다** | 업데이터가 파일마다 "지금 latest" 를 다시 묻는 것 | 서버가 도중에 움직이면 **그 자체로** 절반씩 섞인 설치가 만들어진다 | `fetches == 3` (R1) |
| **서명이 목록 전체를 덮는다** | 이름을 다른 해시와, 해시를 다른 URL 과 짝짓는 것 | 목록의 일부만 진짜인 문서가 통과한다 | manifest 스위트 |
| **아티팩트별 size/sha256 대조** | 약속된 것과 **다른 바이트**가 staging 에 들어오는 것 | 같은 URL 에 다른 내용을 내주는 서버를 못 걸러낸다 | R3 의 실제 실패 사유가 `size mismatch for ui\shell.html` |
| **`releaseId` 로 키잉된 staging + `Swap` 진입 가드** | **시도를 가로질러** 섞이는 것 — 절반 받은 A 를 B 의 파일로 완성하는 것 | 두 릴리스가 같은 staging 자리를 쓰고, 교체가 어느 쪽인지 모른 채 진행된다 | A·B 를 연달아 받으면 **두 디렉터리에 6파일**, A 바이트 미덮임 |

특히 헷갈리기 쉬운 지점: **R3 에서 실제로 거부를 만드는 것은 `releaseId` 가 아니라 해시 대조다.**
서버가 첫 파일 뒤 릴리스 B 로 옮겨가 같은 URL 에 다른 바이트를 내놓을 때, 그것을 잡는 것은 검증된
manifest 가 못 박아 둔 크기·해시다. `releaseId` 는 **그 시도 안에서** 무엇을 막는 장치가 아니라,
**시도와 시도 사이에** 절반 남은 것이 다른 릴리스로 완성되지 않게 하는 장치다.

버전 일관성 검사(`file_contains_utf16_version`)는 **Setup 계열 이름에만** 적용한다. 버전 문자열을
UTF-16 리터럴로 갖는 것은 이 프로젝트가 빌드하는 PE 의 성질이고, 데이터 파일은 갖지 않는다. 모든
아티팩트에 요구하면 데이터 파일이 있는 릴리스는 통과할 수 없다.

### 3.9 목적지가 하위 폴더일 때 (2026-09-08 구현)

manifest 의 이름은 `ui\shell.html` 처럼 **설치 디렉터리 기준 상대 경로**일 수 있다. 벡터 매니페스트가
이미 그런 이름을 담고 있다. 그래서 교체 2단계는 복사 전에 **없는 상위 폴더를 만든다.**

만드는 것이 안전한 이유는 이름이 이미 `check_payload_names` 를 통과했기 때문이다 — 밖으로 나갈 수
없고, 드라이브를 지정할 수 없고, 대체 스트림을 달 수 없다. **어떤 경로가 허용되는지는 이 코드가
정하지 않는다**; 이미 검사된 상대 경로 아래에 폴더를 만들 뿐이다.

롤백은 **이 시도가 만든 폴더만** 지운다(깊은 것부터, 비어 있을 때만). 일어나지 않은 업데이트가
폴더를 남기는 것도 설치의 변경이다. 이미 있던 폴더는 건드리지 않는다.

### 3.10 롤백은 "되돌린 것" 과 "추가한 것" 을 모두 없애야 한다 (2026-09-08, 실제 사례)

롤백이 하는 일을 "옆으로 치워둔 것을 되돌린다" 로만 쓰면, **릴리스가 새로 추가한 파일**은 백업이
없으므로 되돌릴 대상이 아니고 — 그대로 남는다. 일어나지 않은 업데이트가 설치를 영구히 바꾼다.

그래서 교체는 **실제로 놓은 이름**(`placed_`)을 옆으로 치운 이름(`movedAside_`)과 **따로** 기록하고,
롤백은 백업이 있는 것은 복원하고 **백업이 없는데 놓인 것은 지운다.**

이 결함을 처음 잡으려고 쓴 회귀는 **통과했지만 아무것도 증명하지 않았다.** 복사가 실패한 파일을
"추가된 파일" 로 골랐기 때문이다 — 복사가 실행되지 않았으니 치울 것도 없었고, 롤백이 아무 일도 하지
않아도 단정이 성립했다. **롤백 코드를 꺼 보니 그대로 통과**해서 알았다. 지금은 추가되는 파일을
payload 목록의 **맨 앞**에, 막을 파일을 **맨 뒤**에 두어, 실패 시점에 추가 파일이 실제로 디스크에
있도록 만든다. 코드를 끄면 실패한다.

같은 점검에서 두 번째 헛단정도 나왔다: `GetFileAttributesW(p) & FILE_ATTRIBUTE_DIRECTORY` 는
**없는 경로에 대해서도 참**이다(`INVALID_FILE_ATTRIBUTES` 가 전 비트 1). 폴더 생성 여부를 그렇게
확인하던 두 단정은 폴더가 없어도 통과하고 있었다.

### 3.11 Relaunch — 무엇을 다시 띄우는가 (2026-09-08 구현)

완료조건은 "**교체 전에 돌고 있던 것과 같은 구성**" 이지 "제품이 가진 것 전부" 가 아니다. 사용자가
닫아 둔 것을 띄우는 것은 열어 둔 것을 못 띄우는 것만큼 틀렸다. 그래서 계획은 **정지시킨 프로세스
목록**에서 만든다 — 돌고 있지 않았던 것은 계획에 없다.

그리고 제품의 프로세스들은 **서로 대등하지 않다.** 대등하게 다루면 한 번에 네 가지가 어긋난다:

| 이미지 | 어떻게 | 왜 |
|---|---|---|
| `GNLinkHost.exe` | 업데이터의 자식 | 이미 `requireAdministrator` 였으므로 토큰을 물려받아 **UAC 프롬프트가 뜨지 않는다**(3.5) |
| `GNLinkClient.exe` | **셸을 통해 비승격으로** | 승격된 업데이터의 자식으로 띄우면 관리자 토큰을 물려받아 **이후 세션 전체가 관리자로 돈다** |
| `GNLinkInputService.exe` | SCM | 프로세스를 직접 만들면 서비스가 되지 않는다 |
| `GNLinkStream.exe` / `GNLinkCapture.exe` / `GNLinkViewer.exe` | **띄우지 않는다** | 호스트·클라이언트 셸이 감독하는 자식이다. 여기서 띄우면 **아무도 감독하지 않는 인스턴스**가 생기고, 감독자가 자기 것을 띄우면 **둘**이 된다 |

- 같은 이미지가 여러 개 돌고 있었어도 **항목은 하나**다. 제품은 각 하나씩 도는 것이 정상이고, 둘로
  돌아오는 것은 하나도 안 돌아오는 것보다 나쁘다.
- 제품이 모르는 이미지 이름은 **띄우지 않고 버린다.** 지금은 열거기에서 오지만 형태는 manifest 에서
  오는 이름과 같고, **데이터가 실행할 파일을 지명하게 두지 않는다** 는 규칙은 양쪽에 다 걸린다.
- 클라이언트를 셸 경로로 띄우지 못하면 **띄우지 않는다.** 자식으로 대신 띄우는 폴백은 없다 — 그
  폴백이 바로 피하려던 결과이기 때문이다. 이 경우 "비승격으로 띄우지 못했고 승격으로 대신 띄우지도
  않았다" 를 기록한다.

### 3.12 HealthCheck — 무엇을 증거로 받는가 (2026-09-08 구현)

**프로세스가 존재하는 것은 증거가 아니다.** 떠서 곧바로 제 일을 못 하는 것이 바로 health check 가
잡으라고 있는 실패이고, 존재는 그걸 구분하지 못한다. 그래서 증거는 **제품이 자기 자신에 대해 쓰는 한
줄**이다:

```
[host-app] health version=<버전> directory=<ok|pending|not-configured>
```

- **증거는 이번 실행의 것이어야 한다.** 로그 파일에는 이전 실행 — **교체된 그 버전** — 의 보고가 남아
  있고, 파일 전체를 읽는 검사는 지난주에 쓰인 배너를 보고 성공을 보고한다. **그게 바로 이 검사가
  잡으라고 있는 상황이다.** 그래서 재실행 **전에** 로그 크기를 기록하고, 그 뒤에 덧붙은 바이트만 본다.
- **"아직" 과 "아니오" 는 다르다.** `pending` 은 답이 오는 중이고, 타임아웃만이 그것을 실패로 바꾼다.
- **`not-configured` 는 실패가 아니다.** 로그인한 계정이 없으면 닿을 디렉터리가 없다. 그걸로 롤백하는
  것은 업데이트가 만들지 않은 결함을 지어내는 것이다.
- **구버전 보고는 지연이 아니라 실패다.** 교체한 파일을 여전히 무언가가 돌리고 있다는 뜻이고, 더
  기다려도 바뀌지 않는다. `WrongVersion` 으로 분리해 즉시 실패한다.
- 모르는 `directory=` 값은 **무시한다.** 새 제품이 쓴 상태가 옛 업데이터를 우연히 만족시키면 안 된다.

### 3.13 클라이언트 시작 시 확인 — 침묵의 정책 (2026-09-08 구현)

`client_shell_main.cpp` `wWinMain` 에서 창을 띄운 **직후, WebView 생성 전에** 시작하고 **기다리지
않는다.** 최적화가 아니라 요구사항이다 — 업데이트 서버가 답할 때까지 로그인 창을 안 보여주는
클라이언트는 그 서버로 가는 경로가 없는 기계에서 **쓸 수 없다.**

사용자에게 말하는 것은 **"새 버전이 있다" 뿐**이다. 나머지는 로그로만 간다:

- 시작 시 확인은 **서버에 닿지 못하는 것이 일상**인 노트북에서 돈다. 그걸 대화상자로 만들면 사용자는
  **대화상자를 닫는 법을 배우고**, 다음에 정말 중요한 것이 떠도 같이 닫는다.
- "최신입니다" 도 침묵한다. 사용자가 이미 그렇게 가정하고 있던 답이다.
- 로그에는 다섯 결과가 **구분되어** 남는다. 특히 `Unreachable` 은 **"최신" 으로 기록되지 않는다.**
- 답이 페이지보다 먼저 오면 **버리지 않고 들고 있다가** 페이지가 `ready` 를 보낼 때 보낸다.

> **통과하는 테스트가 옳음의 증거는 아니다** (2026-09-08, 실제 사례)
>
> 업데이터의 백업 파일을 등록 성공 직후 지우는 버그가 있었다. 상태기계는 `Register → Relaunch
> → Health` 순이고 Health 실패는 롤백인데, 그때 복원할 백업이 이미 없었다 — **예상된 실패 경로가
> 복구 불가능한 상태로 이어졌고, 안전장치가 필요한 바로 그 순간에 없었다.**
>
> 그 버그를 지키고 있던 것은 통과하던 단정이었다: `"backups are dropped only after
> registration"`. 그 문장은 **참이었다.** 참이었기 때문에 테스트가 통과했고, 테스트가 통과했기
> 때문에 버그가 안전해졌다. 그 단정은 옳음을 확인한 것이 아니라 **버그가 있는 동작을 사양으로
> 기록**하고 있었다.
>
> 교훈: 통과하는 테스트는 **무엇을 옳다고 적어 뒀는지의 증거**일 뿐이다. 단정을 쓸 때는 "지금
> 코드가 이렇게 한다" 가 아니라 **"왜 이래야 하는가"** 를 근거로 써야 하고, 그 근거를 댈 수 없는
> 단정은 사양이 아니라 스냅샷이다. 이 사례에서 옳은 단정은 "등록 뒤에 백업이 사라진다" 가 아니라
> **"롤백이 가능한 동안에는 백업이 살아 있어야 한다"** 였다.

- **환경 제약**: 이 회귀들은 RDP 여부와 무관하다(캡처·인코딩을 쓰지 않는다). 다만 프로젝트 규칙상 실기·통합 판정은 `qwinsta` 로 RDP 세션 없음을 확인한 뒤에만 근거로 쓴다.

## 4. 확정된 결정 (Codex 확정 2026-09-08 + 검증용 실측)

step1 최초 작성 시 이 절은 "Codex 결정 대기" 로 비어 있었다. B1(전송)·B2(서명)·B3(Android 키)이 확정되고 검증용 Claude 의 read-only 실측 2건이 더해져 아래로 채운다. 출처는 **[Codex 확정]** / **[검증용 실측]** 으로 구분한다.

> **이 절 전체에 걸리는 제약**: 아래는 **설계 확정**이며 **배포 승인이 아니다.** 운영 서명키의 생성·교체·보관 위치 결정, 운영 도메인·엔드포인트 확정, 실제 배포는 **모두 별도 승인 사항**이다. 4.5 에서 "코드 준비완료" 와 "배포가능" 을 분리해 정리한다.

### 4.1 전송과 아티팩트 출처 검증

#### 4.1.1 전송 — 업데이트 전용 WinHTTP HTTPS 클라이언트 신설 [Codex 확정]

- **업데이트 경로 전용으로 WinHTTP 기반 HTTPS 클라이언트를 새로 만든다.** manifest 조회와 아티팩트 다운로드가 그 대상이다.
- **기존 코드를 전면 전환하지 않는다.** `directory_client`(등록·하트비트·connect), 인증, `log_upload` 는 현행 평문 경로를 유지한다. 이들의 HTTPS 전환은 이 설계의 범위가 아니다.
- 신설 이유는 1.4.4 에 이미 기록된 사실 그대로다: 현행 공개 API 는 `http_post()` 하나뿐이고(`directory_client.hpp:98-103`), GET·Range·재시도가 없으며, 응답 본문을 **64 KB 에서 자르고**(`directory_client.cpp:346-355`), `https://` 를 명시적으로 거부한다(`:83-93`). 3.5 MB 급 아티팩트를 받을 수단이 아니다.
- **금지 사항 (예외 없음)**:
  - TLS 인증서 검증 끄기 금지 (`WINHTTP_OPTION_SECURITY_FLAGS` 로 오류를 무시하는 형태 포함).
  - 인증서 오류 우회·무시 금지. 검증 실패는 다운로드 실패로 처리한다.
  - **HTTPS → HTTP 리다이렉트 허용 금지.** 리다이렉트를 따라가더라도 스킴 강등은 거부한다.
- TLS 와 서명은 **둘 다** 유지한다. 하나가 다른 하나를 대체하지 않는다 — TLS 는 전송 구간을, 서명은 아티팩트 자체의 출처를 지킨다.

#### 4.1.2 출처 검증 — manifest detached 서명 + 바이너리 내장 공개키 [Codex 확정]

- **manifest 에 detached 서명을 붙이고, 신뢰 공개키는 제품 바이너리에 내장한다.** 검증은 클라이언트가 내장 키로 수행한다.
- **manifest 가 계약의 중심이다.** 플랫폼 · 버전 · 크기 · SHA-256 · 아티팩트 식별을 **모두 하나의 서명 대상에 묶는다.** 개별 필드를 따로 서명하거나, 일부만 서명 밖에 두는 형태는 채택하지 않는다 — 그러면 서명된 manifest 와 다른 아티팩트를 짝지어 붙이는 것이 가능해진다.
- **알고리즘 (기본안): ECDSA P-256 + SHA-256.** 대안은 RSA-2048 PSS + SHA-256.
  - 선택 근거: 세 런타임 모두 **표준 라이브러리로 제공**한다 — Windows 는 BCrypt/CNG, Android 는 `java.security.Signature`, 서버(Node)는 `crypto`.
  - **Ed25519 는 제외한다** — CNG 지원이 불균일해 Windows 쪽 가용성이 보장되지 않는다.
- **자체 암호 구현 금지.** 해시·서명·인코딩 모두 플랫폼 표준 API 를 쓴다.

#### 4.1.3 Authenticode 와 혼동하지 말 것 [Codex 확정]

**이 서명은 Authenticode 가 아니다.** 아티팩트가 우리가 발행한 것인지를 우리 클라이언트가 검증하는 수단일 뿐이다. 따라서:

- **UAC 게시자 신뢰(“알 수 없는 게시자” 표시)를 해결하지 않는다.**
- **SmartScreen 평판을 해결하지 않는다.**
- 이 둘은 Authenticode 코드 서명 인증서가 필요한 별개의 문제이며, 현재 저장소에 그 인프라는 없다(1.4.4·이전 4.1 기록).

### 4.2 Android 서명·키 정책과 앱 데이터 보존

#### 4.2.1 실측 — 동일 키 재사용이 가능하다 [검증용 실측]

검증용 Claude 가 read-only 로 확인한 사실:

| 항목 | 값 |
|---|---|
| 출하 APK | `dist/GNLink-0.2.12.apk` |
| 서명자 DN | `C=US, O=Android, CN=Android Debug` |
| 인증서 SHA-256 | `dcc806aeb30b2e3c53e4a0b96b9675f9e25af2bf071dbb37a3cb09f6b8ec2990` |
| 서명 스킴 | v2/v3 만 (**v1 JAR 서명 없음**) |
| 키 | 2048-bit RSA, SHA256withRSA |
| keystore | 이 PC 의 `%USERPROFILE%\.android\debug.keystore`, 별칭 `androiddebugkey`, PKCS12 |
| 유효기간 | **2026-04-06 ~ 2056-03-29** |

출하 APK 의 지문과 로컬 `debug.keystore` 의 `androiddebugkey` 지문이 **완전히 일치한다.** 서로 다른 출처가 같은 값을 가리킨다 — 1.5 에 기록한 `docs/history.md:5566`·`:5815` 의 인증서 지문(`dcc806ae…2990`)이 이 실측과 일치한다.

#### 4.2.2 확정 — 동일 키 in-place 업데이트 [Codex 확정]

- **같은 키로 서명해 기존 설치자에게 in-place 업데이트한다. 앱 데이터는 보존된다.**
- **제거 후 재설치 안, 데이터 소실을 전제한 안은 미승인이다.**
- step1 최초본이 적었던 "키 전환 = 제거 후 재설치 = 데이터 소실" 서술은 **동일 키를 쓸 수 없게 된 경우에 한정**된다. 지금은 그 경우가 아니다.

#### 4.2.3 기록해 둘 의존성

- **이 `debug.keystore` 가 사실상 유일한 릴리스 서명 신원이다.** 이 파일을 잃으면 기존 설치자에게 업데이트를 보낼 수단이 사라진다. **백업·보관 위치 결정이 필요하며 별도 승인 사항이다.** (키 파일 내용·비밀번호는 이 문서에 기재하지 않는다. 위 표의 지문·DN·유효기간은 비밀이 아니다.)
- **Play 스토어는 debug 인증서로 서명된 APK 를 거부한다.** 따라서 이 경로는 **직접 APK 배포 전용**이다. 스토어 배포를 하려면 별도의 릴리스 키와 그에 따른 신원 전환 문제가 다시 생긴다.
- `app/build.gradle.kts` 에 `signingConfigs` 가 없다(1.5). 릴리스 빌드가 같은 키로 서명되도록 **명시적 signingConfig 설정이 필요하다** — 지금은 `assembleDebug` 산출물을 배포해 우연히 같은 키가 쓰이고 있을 뿐이다.
- **`versionCode` 는 gradle 의 현재 값(11)이 아니라 실제로 배포된 최고값을 확인한 뒤 증가시킨다.** Android 는 `versionCode` 가 낮으면 업데이트를 거부한다.

#### 4.2.4 설치 경로

- **`REQUEST_INSTALL_PACKAGES` 권한이 필요하다** — 현재 매니페스트에는 없다(1.5). 사용자 승인 경로와 **취소 경로**를 함께 설계한다(취소해도 앱은 계속 쓸 수 있어야 한다).
- **FileProvider 가 무조건 필요한 것은 아니다.** 설치 방식에 따라 갈린다:
  - **(A) 파일 Intent 방식** (`ACTION_VIEW`/`ACTION_INSTALL_PACKAGE` 로 APK 파일 URI 전달) — 다른 앱(패키지 설치자)에 파일을 넘겨야 하므로 `FileProvider` 와 `content://` URI 가 **필요하다**.
  - **(B) `PackageInstaller` 세션 스트림 방식** — 앱이 세션을 열고 APK 바이트를 **직접 써 넣으므로** 파일 URI 를 다른 앱에 넘기지 않는다. 이 경우 `FileProvider` 는 **필요하지 않다.**
  - 어느 쪽을 택할지는 구현 단계 결정이며, 그 결정이 `FileProvider` 필요 여부를 정한다. **이 문서에서 (A)를 전제로 단정하지 않는다.**

### 4.3 manifest 스키마

4.1 확정에 따라 아래로 확정한다. **서명 대상은 manifest 문서 전체이며**(4.1.2), 아래 필드는 모두 그 안에 있다.

| 필드 | 내용 | 비고 |
|---|---|---|
| 스키마 버전 | manifest 형식 자체의 버전 | 미래의 형식 변경을 클라이언트가 거부/무시할 수 있게 한다 |
| 플랫폼 | `windows` / `android` | 한 manifest 가 여러 플랫폼을 담든 플랫폼당 하나든, **플랫폼 식별이 서명 안에 있어야 한다** |
| 제품 버전 | 배포 버전 문자열 | 2(d) 의 **버전 비교 계약**을 따른다 — 성분 숫자 비교, 비숫자 접미사에서 중단. manifest 의 표기가 그 계약과 모순되면 안 된다 |
| 아티팩트 식별 | 다운로드 위치와 아티팩트 이름 | |
| 크기 | 바이트 | `Download` 완료조건(3.6)이 이 값과 대조한다 |
| SHA-256 | 아티팩트 콘텐츠 해시 | `Verify` 단계의 무결성 근거 |
| (Android) versionCode | 정수 | 4.2.3 의 제약이 걸린다 |
| 서명 | manifest 문서에 대한 detached 서명 | 본문 밖에 둔다 |

- **64 KB 절단은 이 스키마의 제약이 아니다.** 그 한계는 `directory_client.cpp:346-355` 의 것이고, manifest 는 4.1.1 의 **신규 WinHTTP 클라이언트**가 받는다. 따라서 manifest 크기를 64 KB 에 맞출 필요가 없다.
- 서명 검증이 실패하면 manifest 의 어떤 필드도 신뢰하지 않는다 — 버전 비교조차 하지 않는다.

### 4.4 서버 신규 엔드포인트

4.1·4.3 확정에 맞춰 아래로 확정한다.

- **manifest 조회 엔드포인트를 신설한다.** 현행 라우트 테이블은 `메서드 경로` 정확 일치이고 접두사 매칭이 없으므로(`server.js:564-585`) 새 키를 추가하는 형태가 된다.
- **아티팩트 자체는 디렉터리 서버가 스트리밍하지 않는 것을 기본안으로 한다.** 현행 서버에 정적 파일 서빙도 바이너리 GET 경로도 없고(1.4.1), 3.5 MB 급 파일을 Node 이벤트 루프로 흘리는 것은 릴레이·하트비트와 같은 루프를 공유한다. 아티팩트는 **HTTPS 로 접근 가능한 정적 위치**에 두고 manifest 가 그 위치를 가리킨다.
- **인증**: manifest 조회는 기존 두 인증 수단(Bearer 세션 / `x-host-token`, 1.4.2)을 재사용한다. 다만 **세션은 메모리 전용이라 서버 재시작으로 소멸하므로**(`server.js:490`), 업데이트 확인이 세션 만료로 실패하는 것은 정상 동작으로 취급하고 다음 주기에 재시도한다(3.1 의 `CheckRequested` 실패 처리와 같다).
- **남용 방지**: 로그 업로드의 계정/기기별 레이트 리밋(`server.js:346-349`)을 선례로 삼는다.
- **운영 도메인·실제 엔드포인트 URL 확정과 배포는 별도 승인 사항이다** (4.5).

### 4.5 "코드 준비완료" 와 "배포가능" 의 분리 [Codex 확정]

두 상태를 문서에서 섞지 않는다.

**코드 준비완료** — 이 설계로 구현·검증이 끝난 상태. 다음이 모두 성립할 때:

- WinHTTP HTTPS 클라이언트, manifest 파서·서명 검증, 업데이터 상태기계(3.1)가 구현되고 3.7 의 회귀로 덮인다.
- **테스트 키**로 서명한 manifest 로 전 경로가 통과한다. 테스트 키는 **격리된 테스트 전용이며 실배포 신뢰키로 절대 쓰지 않는다.**
- Android 쪽은 `signingConfigs` 설정과 `REQUEST_INSTALL_PACKAGES` 경로가 구현되고, 설치 방식(A/B, 4.2.4)이 결정돼 있다.

**배포가능** — 실제로 사용자에게 업데이트를 내보낼 수 있는 상태. 위에 더해 다음이 **모두 별도 승인**을 받아야 한다:

- **운영 서명키 생성·보관 위치·교체 절차** 결정. 바이너리에 내장할 공개키가 이 키의 것으로 확정되어야 한다.
- **Android keystore 백업·보관 위치** 결정 (4.2.3).
- **운영 도메인과 엔드포인트 URL** 확정, 그리고 아래 4.6 의 nginx vhost 작업.
- 실제 서버 배포. **이 문서 작성 시점에 실배포는 하지 않았고, 하지 않는다.**

### 4.6 서버 TLS 현황 — 5절 미확인 1번 해소 [검증용 실측]

검증용 Claude 가 NAS 를 read-only 로 확인했다:

- **nginx 가 :443 에서 LISTEN 중이고 TLS vhost 가 다수 있다** (`shotan.org` 및 하위 도메인), Let's Encrypt 인증서 보유 (`/etc/letsencrypt/live/shotan.org`, `/etc/letsencrypt/live/vpn.shotan.org`).
- **그러나 29180/8080 으로 프록시하는 vhost 는 없다.** 그리고 `REMOTE60_DIR_TLS_KEY`/`REMOTE60_DIR_TLS_CERT` 는 설정돼 있지 않다 → 디렉터리 서비스는 **:29180 평문으로 직접 노출**되어 있다(1.4.3 의 조건부 TLS 분기에서 http 쪽으로 떨어진다).

**따라서 HTTPS 추가는 인증서 구매 문제가 아니라 nginx vhost 설정 작업이다.** 인증서와 TLS 종단은 이미 있고, 디렉터리 포트로 가는 프록시 정의만 없다.

- 이것은 4.1.1 의 HTTPS 전송 전제를 **충족 가능하게** 만든다 — 새로 확보할 것이 아니라 설정할 것이다.
- **운영 도메인·엔드포인트 확정과 vhost 적용은 배포 단계 의존성이며, 이 문서는 실배포를 하지 않는다** (4.5).

1. ~~현 NAS 디렉터리 서버가 TLS 를 켜고 실행 중인지~~ — **해소됨(4.6).** 검증용 Claude 의 read-only 실측: nginx 가 :443 LISTEN + Let's Encrypt 인증서 보유, 그러나 29180/8080 프록시 vhost 없음, `REMOTE60_DIR_TLS_KEY/CERT` 미설정 → 디렉터리는 :29180 평문 노출. HTTPS 추가는 인증서 확보가 아니라 nginx vhost 설정 작업이다.
