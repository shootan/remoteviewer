# 버퍼링/GPU 경합 분석 검토
검토일: 2026-04-09
대상 문서: `docs/버퍼링_GPU경합_분석_20260409.md`

---

## 결론

문서의 결론은 **부분 인정**한다.

- 인정하는 핵심:
  - WGC 캡처 readback 경로와 GPU 스케일러가 같은 D3D11 immediate context를 공유하고, 같은 mutex로 보호되어 있어 경합 가능성이 있다.
  - CPU readback, CPU `bgra_to_nv12`, 대용량 메모리 복사가 버퍼링 악화 요인으로 작동할 수 있다.
- 인정하지 못하는 핵심:
  - MFT H.264 인코더가 `d3dContextMu`를 통해 같은 방식으로 직접 경합한다는 서술
  - 현재 구조에서 안 (C)가 바로 안전하다는 단정
  - 런타임 지표 없이 원인을 “확정”한 서술

---

## 인정하는 부분

### 1. 캡처 콜백과 GPU 스케일러의 context/mutex 경합 가능성

다음 사실은 코드로 확인된다.

- host는 D3D11 디바이스와 immediate context를 1개만 만든다.
  - `apps/native_poc/src/native_video_host_main.cpp:2696-2702`
- 같은 context를 GPU 스케일러가 공유하며, `d3dContextMu` 포인터를 넘겨받는다.
  - `apps/native_poc/src/native_video_host_main.cpp:2713-2716`
- 캡처 콜백은 `d3dContextMu`를 잡은 상태에서 `CopyResource -> Map -> row memcpy -> Unmap`을 수행한다.
  - `apps/native_poc/src/native_video_host_main.cpp:3069-3080`
- GPU 스케일러도 같은 mutex를 잡은 상태에서 `UpdateSubresource -> VideoProcessorBlt -> CopyResource -> Map -> row memcpy -> Unmap`까지 수행한다.
  - `apps/native_poc/src/native_video_host_main.cpp:1707-1748`

즉, 문서가 말한 “경합 가능성” 자체는 맞다.

### 2. 캡처 readback과 CPU 변환이 추가 부하 요인이라는 점

다음도 코드 기준으로 인정한다.

- 캡처 콜백은 프레임마다 BGRA payload 버퍼를 새로 잡는다.
  - `apps/native_poc/src/native_video_host_main.cpp:3068`
- 인코드 직전 `bgra_to_nv12(...)`는 현재 CPU 경로다.
  - `apps/native_poc/src/native_video_host_main.cpp:4311-4317`
- `H264Encoder::encode_frame(...)`는 `std::vector<uint8_t> nv12`를 받아 CPU 메모리 버퍼 기반 `IMFSample`을 만든다.
  - `apps/native_poc/src/mf_h264_codec.cpp:189-207`
  - `apps/native_poc/src/mf_h264_codec.cpp:1396-1405`

즉, 현재 경로는 “GPU 캡처 -> CPU readback -> CPU 색변환 -> MFT encode”의 성격이 강하며, 이 자체가 buffering 악화 요인일 수 있다.

### 3. 단, GPU 스케일러 경합은 항상 발생하지는 않음

문서의 방향성은 맞지만 조건이 빠져 있다.

- GPU 스케일러는 `activeEncodeW/H != captureW/H`일 때만 동작한다.
  - `apps/native_poc/src/native_video_host_main.cpp:4283-4308`

따라서 “GPU 스케일러 경합”은 항상 상수항이 아니라, 리사이즈가 활성화된 프로필에서만 커진다.

## 인정하지 못하는 부분

### 1. MFT 인코더가 `d3dContextMu`의 직접 경합 주체라는 주장

이 부분은 현재 코드 기준으로 인정하지 못한다.

- 인코더는 `encoder.set_d3d11_device(d3d.Get())`로 DXGI device manager만 등록한다.
  - `apps/native_poc/src/native_video_host_main.cpp:2710-2711`
  - `apps/native_poc/src/mf_h264_codec.cpp:1011-1026`
- 실제 `encode_frame(...)` 입력은 GPU 텍스처가 아니라 CPU NV12 바이트 배열이다.
  - `apps/native_poc/src/mf_h264_codec.cpp:1396-1405`
- host 코드에서 인코더가 `d3dContextMu`를 잡는 경로는 없다.

따라서 “캡처·스케일·인코더 3자 mutex 직렬화”는 과한 서술이다.  
현 시점에서 더 정확한 표현은 “캡처 readback과 GPU 스케일러의 shared immediate context 경합 + CPU 전처리 부담”이다.

### 2. 안 (C)가 현재 구조에서 바로 안전하다는 주장

이 부분도 인정하지 못한다.

- 캡처 콜백이 쓰는 staging 텍스처는 단일 공유 객체다.
  - `apps/native_poc/src/native_video_host_main.cpp:2968-2988`
  - `apps/native_poc/src/native_video_host_main.cpp:3053-3059`
- 현재 문서안처럼 `Map` 후 memcpy 동안 락을 풀면, 다른 콜백 재진입이나 staging 재사용과 충돌하지 않는다는 보장이 코드상 없다.

즉, 안 (C)는 방향은 좋지만 그대로는 안전성 검증이 부족하다.  
최소한 “staging ownership 분리”나 “readback staging ring” 같은 보강 설계가 먼저 필요하다.

### 3. 원인 “확정” 서술

이 문서는 코드 해석만으로는 plausible하다. 하지만 확정이라고 쓰기에는 계측이 부족하다.

현재 host는 이미 다음 지표를 로그로 내보낸다.

- `cb2eAvgUs`, `cb2eMaxUs`
- `gpuScaleAttempts`, `gpuScaleSuccess`, `gpuScaleFail`, `gpuScaleCpuFallback`
- `capAgeAvgUs`, `capAgeMaxUs`
  - `apps/native_poc/src/native_video_host_main.cpp:4881-4903`

그런데 분석 문서는 이 런타임 지표를 인용하지 않는다.  
따라서 현 상태는 “강한 가설”이지 “확정 RCA”는 아니다.

### 4. Zero-copy 경로의 난이도 설명이 다소 낙관적임

장기 방향 자체는 타당하지만, 현재 코드와의 간격이 크다.

- 현재 `H264Encoder` 인터페이스는 GPU surface 입력이 아니라 CPU NV12 바이트 입력 전제다.
  - `apps/native_poc/src/mf_h264_codec.hpp`
  - `apps/native_poc/src/mf_h264_codec.cpp:1396-1405`

따라서 zero-copy는 단순 최적화가 아니라 encoder 입력 인터페이스 재설계까지 포함한 별도 작업으로 보는 것이 맞다.

## 인정하는 부분을 어떻게 수정할지

### 1. RCA 문구를 먼저 정정

기존 문서의 원인 문구는 아래처럼 바꾸는 것이 맞다.

- 기존:
  - “단일 D3D11 디바이스를 캡처·스케일링·인코딩 3개 경로가 공유하고, `d3dContextMu`로 직렬화된다.”
- 수정:
  - “WGC 캡처 readback과 GPU 스케일러가 같은 D3D11 immediate context와 `d3dContextMu`를 공유한다.”
  - “여기에 CPU readback, CPU `bgra_to_nv12`, 대용량 복사가 겹쳐 buffering을 악화시킬 가능성이 있다.”
  - “MFT 인코더는 같은 디바이스를 참조하지만, 현재 코드에서 `d3dContextMu`의 직접 경합 주체로 확인되지는 않는다.”

### 2. 측정을 먼저 추가

수정은 바로 들어가기보다 계측을 먼저 넣는 것이 안전하다.

- 캡처 콜백에서 `d3dContextMu` 대기 시간 / 점유 시간을 분리 계측
- GPU 스케일러에서 `d3dContextMu` 대기 시간 / 점유 시간을 분리 계측
- 스케일러 active 비율(`resize active` vs `1:1 bypass`) 계측
- 캡처 readback 세부 시간 분해:
  - `CopyResource`
  - `Map wait`
  - `row memcpy`
  - `Unmap`

이렇게 해야 “buffering의 주범이 캡처 readback인지, scaler인지, CPU NV12 변환인지”를 구분할 수 있다.

### 3. 단기 수정은 “단일 staging 공유”를 깨는 방향으로

문서의 안 (C)는 그대로 적용하지 말고, 아래처럼 바꾸는 것이 안전하다.

- 캡처 readback용 staging 텍스처를 단일 객체에서 2~3 slot ring으로 변경
- 각 콜백은 자기 slot을 점유한 뒤 `CopyResource -> Map`까지만 mutex 안에서 수행
- row memcpy는 mutex 밖에서 수행
- memcpy 완료 후 다시 mutex를 잡고 `Unmap` + slot release

이렇게 하면 “memcpy를 lock 밖으로 빼는 효과”는 얻으면서도, 현재 문서안의 가장 큰 위험인 단일 staging 재사용 충돌을 줄일 수 있다.

### 4. 중기 수정은 capture/scaler 경합을 분리

계측 후에도 경합이 크면 다음 순서가 맞다.

- 캡처 readback 디바이스/컨텍스트 분리
- 스케일링 + 인코딩용 디바이스/컨텍스트 분리
- 단, 이 단계는 인코더까지 같은 mutex 경합 주체라는 가정이 아니라, “capture readback과 scaler 경합 분리”를 목표로 정의해야 한다.

### 5. 장기 수정은 별도 과제로 분리

Zero-copy는 다음 별도 작업으로 취급해야 한다.

- `H264Encoder` 입력을 CPU NV12 바이트가 아니라 GPU surface 또는 GPU-backed sample로 받을 수 있는지 feasibility 검증
- frame gating / change detection이 CPU readback 없이 유지 가능한지 별도 설계
- AMF/NVENC/QSV/MFT backend별 호환성 검토

즉, zero-copy는 “다음 단계의 최적화 옵션”이지, 현재 RCA 문서의 직접 후속 1순위로 적기에는 범위가 너무 크다.

## 최종 판단

이 분석 문서는 다음처럼 해석하는 것이 정확하다.

- **인정**:
  - 캡처 readback과 GPU 스케일러의 shared immediate context/mutex 경합 가능성
  - CPU readback + CPU 색변환 + 메모리 복사 비용
- **보류/비인정**:
  - 인코더를 같은 mutex 기반 direct contender로 본 부분
  - 안 (C)의 현재 구조상 안전성
  - 런타임 근거 없는 “원인 확정” 톤
- **권장 후속**:
  - 먼저 측정 지표 보강
  - 그 다음 safe staging ring 기반 short-term fix
  - 이후에만 device split 또는 zero-copy를 검토
