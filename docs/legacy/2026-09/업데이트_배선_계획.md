## 1. 남은 제품 배선 목록

### W1. 업데이터 실행 파일이 존재하지 않는다 — 가장 큰 구멍

`run_update` 를 부를 **바이너리 자체가 없다.** 나머지 배선은 전부 이것 위에 얹힌다.

- 새 타깃 `remote60_updater` → `GNLinkUpdater.exe`, `requireAdministrator` 매니페스트.
- 링크: `update_state_machine` · `update_effects` · `update_manifest` · `update_signature` ·
  `update_http` · `payload_name` · `install_registration` · `update_registration_wiring` ·
  **`update_process_targets`**(현재 아무도 링크하지 않음) · **`update_relaunch`**(현재 아무도
  링크하지 않음).
- **설치 위치는 `installDir` 밖**(설계 3.2). 자기가 교체 대상 디렉터리 안에 있으면 자기를 교체하게
  된다. `validate()` 가 이미 그것을 거부하므로, 위치를 잘못 잡으면 **업데이트가 시작조차 안 된다**.
- 명령줄로만 동작한다. `--install-dir` · `--staging-dir` · `--manifest-url` · `--platform` ·
  `--parent-pid` · `--ready-event` · `--log`. **기본값 없음** — `UpdateEffectsConfig::validate()`
  가 이미 강제하는 규율을 진입점에서도 지킨다.

### W2. 설치기 payload 에 업데이터가 없다

`installer_main.cpp:53-62` 의 `kPayload` 는 7항목 + Setup 이다. 여기에 없는 파일은 설치되지 않는다.

- `IDR_PAYLOAD_UPDATER` 추가 → `installer/payload.rc.in` · `CMakeLists.txt:310-360` 의 staging
  `add_custom_command` · `kPayload` 세 곳.
- 다만 **목적지가 다르다.** 다른 payload 는 `installDir` 로 가지만 업데이터는 그 밖으로 가야 한다
  (W1). `do_install()` 에 목적지가 다른 항목을 다룰 자리가 지금은 없다.

### W2a. 업데이터를 어디에 설치할 것인가 — **결정: installDir 안, 실행은 자기 복사본으로**

W2 가 드러낸 구조 문제("목적지가 다른 payload 를 `do_install()` 이 다룰 자리가 없다")를 어느 쪽으로
푸는지 정한다. 두 안이 있었다.

**(가) 목적지를 항목별 속성으로** — `PayloadFile` 에 목적지를 붙이고 업데이터만 `installDir` 밖으로.
**(나) 업데이터도 보통 payload 로 `installDir` 에 넣고, 실행할 때 자기를 복사해 그 복사본으로 재실행.**

**(나)를 고른다.** (가)는 설치 코드가 덜 바뀌지만 **치명적인 결과**가 있다: `installDir` 밖에 있는
파일은 **교체 대상이 될 수 없다.** payload 이름은 설계상 상대 경로만 허용하고 traversal 을 거부하므로
(#442·#444), 밖에 있는 업데이터를 가리킬 방법이 아예 없다. 그러면 업데이터는 **컴파일 시점 상수에
묶인 채 영원히 남는 두 번째 유지보수 바이너리**가 된다 — 등록에서 (C)안을 탈락시킨 것과 **똑같은
덫**이다(history #440). 게다가 언인스톨은 `installDir` 을 지우므로 밖의 파일은 **고아로 남는다.**

(나)의 동작:

1. 설치기는 `GNLinkUpdater.exe` 를 **다른 payload 와 똑같이** `installDir` 에 넣는다. `kPayload`
   루프도, 언인스톨도 그대로다. **설치 코드에 새 구조가 생기지 않는다.**
2. 업데이트를 시작할 때, 실행된 업데이터는 **자기를 작업 디렉터리로 복사하고 그 복사본을 실행한 뒤
   종료한다.** 이후 진짜 작업은 복사본이 한다.
3. 복사본은 `installDir` 밖에 있으므로 `validate()` 의 "업데이터가 교체 대상 안에 있다" 검사를
   통과하고, 스왑은 `installDir\GNLinkUpdater.exe` 를 **보통 파일처럼 교체·백업·롤백**한다.

⚠️ **작업 디렉터리는 관리자만 쓸 수 있어야 한다.** 복사본은 상승된 채로 실행되므로, 사용자 쓰기가
가능한 곳에 두면 **복사와 실행 사이에 바꿔치기할 창**이 생긴다 — 권한 상승 취약점이다.

**위치는 `%ProgramFiles%\GNLink.update\` 다.** 설계 1차 조사(history #427)가 이미 이 판단을 내려
뒀고, 거기서 **`%TEMP%` 와 `%ProgramData%` 를 명시적으로 배제**했다 — 사용자가 쓸 수 있어 설치기가
지키는 불변식(LocalSystem 서비스 바이너리가 사용자 쓰기 가능한 폴더에 있으면 그 폴더에 쓸 수 있는
누구나 SYSTEM 을 얻는다, `installer_main.cpp:1-13`)을 되돌리기 때문이다. **이 문서의 초안이 그
결정을 모르고 `%ProgramData%` 를 적었던 것을 정정한다.**

`%ProgramFiles%` 아래는 기본 ACL 이 이미 관리자 전용이라 **따로 ACL 을 세울 필요가 없다** — 세워야
하는 방어는 세우다 빠뜨릴 수 있는 방어다. 그리고 `GNLink.update` 는 `GNLink` 의 **형제**이지 하위가
아니므로(`GNLink` 다음 글자가 구분자가 아니라 `.`), "작업 디렉터리가 installDir 안" 검사에 걸리지
않는다.

**함께 고친 것**: `UpdateEffectsConfig::validate()` 가 업데이터를 **파일 이름**으로 비교하고 있었다.
그러면 (나)가 원천 봉쇄된다 — 교체되는 파일과 실행 중인 파일이 다른데도 이름이 같아서 거부된다.
**전체 목적지 경로로 비교**하도록 바꿨다. 실제로 참이어야 하는 명제는 더 좁다: **이 스왑의 어떤
목적지도 지금 실행 중인 이미지여서는 안 된다.** 디렉터리 검사(업데이터가 `installDir` 안에 있으면
거부)는 그대로 남아 있으므로 방어는 줄지 않는다.

### W3. Host 의 update/later 승인 동작이 없다

지금은 `MessageBoxW(MB_OK)` 로 "새 버전이 있습니다" 라고 말하고 끝난다.

- `UpdateAvailable` 일 때 **update / later 선택**을 준다.
- update 를 고르면 업데이터를 **자식으로** 실행한다. 호스트는 이미 상승돼 있으므로 토큰을 물려받고
  **UAC 프롬프트가 뜨지 않는다**(설계 3.5, UPD-FIELD-02).
- ⚠️ **권한·락·staging 을 확보한 뒤에만 호스트가 종료한다.** 먼저 죽으면 업데이트가 실패했을 때
  되살릴 주체가 없고, 사용자에게는 그냥 제품이 사라진 것으로 보인다. 그래서 handoff 가 필요하다:
  업데이터가 `--ready-event` 로 받은 named event 를 **락 획득 + 다운로드 + 검증까지 끝낸 뒤** signal
  하고, 호스트는 그 신호를 받은 뒤에만 종료한다. 신호가 오지 않거나 업데이터가 먼저 죽으면
  **호스트는 그대로 계속 돈다** — 실패의 기본값은 "아무 일도 일어나지 않음" 이어야 한다.
- 업데이터는 호스트를 Quiesce 대상으로 삼으므로, **업데이터 자신이 호스트의 job object 에 속하면 안
  된다**(설계 3.2 ②).

### W4. Client 시작 팝업이 실행으로 이어지지 않는다

지금은 `shell_status_json("idle", ...)` 문구뿐이다.

- 알림에 **"지금 업데이트"** 액션을 붙인다.
- 클라이언트는 **비승격**이라 `%ProgramFiles%` 를 스스로 교체할 수 없다. 업데이터를
  `ShellExecuteW(L"runas")` 로 띄워 **UAC 를 정확히 1회** 발생시킨다.
- **취소하면 교체하지 않고 클라이언트를 계속 쓸 수 있어야 한다**(설계 3.5). 취소는 오류가 아니다.
- 교체 뒤 클라이언트는 **원래의 비승격 문맥으로** 복귀한다 — `update_relaunch.cpp` 의
  `launch_via_shell` 이 그 몫이고, 지금 실행된 적이 없다(§2).

### W4a. 재실행 실패는 **안전한 실패이지 성공이 아니다** (2026-09-08 정정)

앞서 "셸 경로가 없으면 클라이언트가 안 뜨는 것이 정답" 이라고 적었다. **틀렸다.** 승격 폴백을 두지
않은 것은 옳지만, 그 결과를 **성공으로 기록하면 안 된다.** 폴백을 안 만든 것과 실패를 성공이라고
부르는 것은 다른 이야기다.

상태기계에는 이미 **`UpdatedButNotRelaunched`** 라는 별도 종착점이 있고, 재실행 실패는 롤백이 아니라
그것으로 끝난다. 그 부분은 이미 맞다. **없는 것은 그 뒤다**:

> **줄 번호로 가리키지 않는다.** 이 문단은 한때 `update_state_machine.cpp:167-178` 이라고 적었고,
> 그 사이 파일이 자라 **그 줄은 다른 것을 가리키게 됐다.** 자라는 파일을 줄로 가리키면 유통기한이
> 짧다 — 이름으로 가리킨다.

- **`Done` 으로 숨지 않는다** — 이미 그렇다. 유지한다.
- ⚠️ **사용자에게 말한다.** 지금은 아무 말도 하지 않는다. "업데이트는 끝났고, 클라이언트는 시작
  메뉴에서 직접 켜야 한다" 를 사용자가 알아야 한다. **아무 말 없이 끝나는 것이 가장 나쁘다** —
  사용자는 업데이트가 프로그램을 없앴다고 생각한다.
- **복구 상태를 남긴다.** ✅ 완료. 항목별 결과는 `RelaunchEffects::lastOutcomes` 로 나오고 업데이터가
  단계별로 로그에 적는다(`relaunch (required) ...` / `relaunch (optional) ...`). 여기 적혀 있던
  `lastActions` 는 **아무도 읽지 않아서 지웠다** — 읽히지 않는 출력은 기록이 아니라 미결이다.
- **무엇이 안 떴는지 구분한다.** ✅ 완료, 그리고 계획보다 멀리 갔다. `bool` → `RelaunchVerdict`
  (`AllBack`/`OptionalMissing`/`RequiredMissing`) 로 바뀌었고, 그 뒤 **단계 자체가 둘로 나뉘었다**:
  `RelaunchRequired()` → health → commit → `RelaunchOptional()`(설계 3.11.0, history #473). 아래 원문은
  당시 상태를 남긴 것이다 — 지금 `relaunch` 는 `bool` 하나를 돌려준다 — 그래서 **호스트가 못
  뜬 것과 클라이언트가 못 뜬 것이 같은 값**이 된다. 아래 W4b 참조.

### W4b. Host 무인 재시작은 클라이언트 복귀와 **급이 다르다**

**원격에서 업데이트한 사용자는 호스트가 스스로 돌아오지 않으면 그 기계에 다시 접속할 수단이 없다.**
클라이언트가 안 뜨면 사용자는 시작 메뉴에서 켜면 되지만, 호스트가 안 뜨면 **그 기계 앞에 사람이
가야 한다.** 같은 `false` 로 뭉뚱그릴 수 없다.

- Host 는 설계 3.6 대로 **추가 사용자 조작 없이** 재실행되어야 한다. 이 요구는 클라이언트 복귀
  실패를 허용한다고 해서 낮아지지 않는다.
- 그래서 `relaunch` 의 결과를 **항목별 구조체**로 바꾼다: 어떤 이미지가, 어떤 종류로, 성공했는지
  실패했는지, 실패 이유가 무엇인지. `UpdatedButNotRelaunched` 라는 결과는 같더라도 **detail 이
  무엇이 안 돌아왔는지 반드시 이름을 대야 한다.**
- 호스트가 업데이터의 자식으로 뜨므로, **업데이터가 job object 에 속하면 호스트도 딸려 죽는다**
  (설계 3.2 ②). W1 에서 확인할 것.

### W4c. 다중 데스크톱·다중 세션을 **일괄 실패로 규정하지 않는다**

앞서 ⓒ(다중 데스크톱/다중 세션)를 통째로 "안 뜨는 게 정답" 으로 묶었다. **과했다.** 지원 가능한
경우까지 실패로 규정하면 되돌릴 수 있는 것도 안 되돌린다. 둘로 나눈다.

**복원 계약(지원 대상)** — 어느 사용자·어느 세션으로 되돌리는가:

- 업데이트 직전에 클라이언트가 **돌고 있던 그 세션·그 사용자**로 되돌린다. `ProcessTarget` 에
  이미 PID·이미지 경로·생성 시각이 있으므로, **세션 ID 와 사용자 SID 를 함께 잡아** 그 세션의
  셸을 통해 띄우면 된다.
- 콘솔 세션에 그 사용자가 로그인해 있고 셸이 살아 있으면 **지원 대상이다. 떠야 한다.**

**실제로 불가능한 조건(안 뜨는 것이 안전한 실패)**:

- 그 세션이 이미 로그아웃돼 있다 — 되돌릴 대상이 없다.
- 그 세션에 셸(Explorer)이 없다 — 비승격으로 띄울 경로가 없다.
- 업데이터가 그 세션에 접근할 수 없다.

**두 경우 모두** 결과는 `UpdatedButNotRelaunched` 이고 **사용자 안내가 따른다.** 차이는 전자가
**버그**이고 후자가 **설계된 안전한 실패**라는 점이다. 시험에서 그 둘을 구분할 수 있어야 한다.

### W5. Quiesce 대상 열거가 연결되지 않았다

`UpdateEffectsConfig::enumerateTargets` / `requestStop` 은 필수 필드인데, 그것을 채울
`enumerate_product_processes` / `request_process_stop` 의 호출자가 **0건**이다. 업데이터(W1)가
연결한다.

### W6. Relaunch / Health 가 연결되지 않았다

`make_relaunch_effects` 호출자 **0건**. 업데이터가 **Quiesce 가 실제로 정지시킨 목록**을 넘겨 만들고,
`UpdateEffectsConfig::relaunch` / `healthCheck` 에 꽂는다. 로그 경로(`healthLogPath`)는 호스트가
실제로 쓰는 `%LOCALAPPDATA%\GNLink\host_app.log` 여야 한다.

### W7. Android 는 전부 미배선

`UpdateManifest.kt` 는 파싱만 있고 부르는 사람이 없다.

- **확인**: 앱 시작 시 비동기 + 명시적 "업데이트 확인". 네트워크 실패가 실행·로그인을 막지 않는다.
- **다운로드**: 앱 전용 저장소로.
- **검증**: 파일 sha256 == manifest · 서명 검증(`rawSignatureToDer` 는 있으나 호출자 없음) ·
  **`versionCode` 가 현재보다 큰지**. 셋 다 통과해야 설치로 넘어간다.
- **설치**: `REQUEST_INSTALL_PACKAGES` 를 매니페스트에 추가하고 `canRequestPackageInstalls()` 확인.
  방식은 (A) 파일 Intent / (B) `PackageInstaller` 세션 중 택일 — 이 선택이 `FileProvider` 필요
  여부를 정한다.
- **경로 3종을 전부 다룬다**: 승인 / **취소** / **권한 거부**. 뒤의 둘은 오류가 아니라 정상 종료다.

### W8. 서버 발행 ↔ 클라이언트 소비 추적표가 없다

`apps/directory/server.js` 의 `/api/update/manifest` 가 내보내는 필드와 C++·Kotlin·JS 가 읽는 필드의
대응을 표로 고정한다. 지금은 세 런타임이 **같은 벡터**를 읽는 것까지만 보장되고, **서버가 실제로
발행하는 문서**가 그 벡터와 같은 모양인지는 라우트 테스트 1건이 전부다.

## 2. 실행계층 검증 방법

### 2.1 이전 판단을 철회한다

`update_relaunch.cpp` 를 **어디에도 링크하지 않은 것**을 "격리" 라고 적었고, 미검증 목록에
**"자동 회귀로 대체 불가"** 라고 썼다. 틀렸다.

**`CreateProcess` 자체는 라이브 파괴가 아니다.** dummy exe · 임시 설치 root · 임시 로그 경로를
주입하면 **같은 OS 실행 경로를 실제로 검증할 수 있다.** 지금 그게 안 되는 진짜 이유는
`update_relaunch_plan.cpp` 가 **제품 이미지 이름을 스스로 정하기 때문**이고, 그것은 받아들일 제약이
아니라 **고칠 설계**다. "링크 0" 은 격리 품질의 증거가 아니라 **그 코드가 한 번도 실행되지 않았다는
자백**이다.

### 2.2 무엇을 바꾸는가

- **R1 — 이미지 표를 주입 가능하게.** `relaunch_plan(stopped)` → `relaunch_plan(stopped, table)`.
  제품 표(`kKnownImages`)는 **기본값으로 남긴다**. 테스트는 자기 dummy 이름표를 넘긴다.
  **허용목록 성질은 그대로다** — 표에 없는 이름은 여전히 못 뜬다. 바뀌는 것은 "표가 어디서 오는가"
  뿐이고, 그래서 "데이터가 실행할 파일을 지명하게 두지 않는다" 는 규칙이 약해지지 않는다.
- **R2 — `update_relaunch.cpp` 를 테스트에 링크한다.** 경로·이름·서비스명·로그가 전부 인자이므로,
  테스트가 주는 값은 임시 디렉터리와 dummy 뿐이다. 제품 경로를 가리킬 방법이 없다는 것을
  `validate()` 처럼 **구조로** 만든다.

### 2.3 무엇을 실제로 검증하는가

| # | 검증 | 방법 | 라이브 접촉 |
|---|---|---|---|
| E1 | 계획대로 **실제로 떴는가** | 임시 root 에 dummy exe(즉시 종료, 종료코드로 자기를 식별) 배치 → `relaunch` 호출 → **PID·종료코드**로 확인 | 없음 (임시 디렉터리) |
| E2 | **중복으로 뜨지 않는가** | 같은 이미지 2개를 stopped 로 주고 dummy 실행 횟수를 센다 | 없음 |
| E3 | **감독 대상은 안 뜨는가** | `SupervisedByAnother` 로 표시된 dummy 가 **한 번도 실행되지 않음**을 확인 | 없음 |
| E4 | **표에 없는 이름은 못 뜨는가** | 표 밖 이름을 stopped 로 주고 실행 0 확인 | 없음 |
| E5 | **비승격 실행이 실제로 동작하는가** | dummy 를 사용자 토큰 경로(`launch_as_shell_user`, `CreateProcessWithTokenW`)로 띄우고 **무결성 수준**과 **돌려받은 handle**을 읽는다. 셸 경유(`launch_via_shell`)는 그것이 실패할 때의 폴백으로 따로 본다 | 없음 (dummy) |
| E5c | **선택 이미지가 commit 뒤에만 뜨는가** | 정상 경로에서 **commit 전 optional 기동 0 / 후 1**, 롤백 경로에서 **롤백 전 0**. 순서를 되돌려 실패하는지까지 확인(반대 증거) | 없음 |
| E5b | **셸 폴백이 소유를 주장하지 않는가** | 토큰 경로 실패를 강제 → 셸로 뜬 뒤 `ownershipUnknown` 이고 `stopStarted` 의 `unstoppable` 에 들어가며 **롤백이 시작되지 않는지** 확인(시나리오 7 + 역대조) | 없음 |
| E6 | **셸 경로가 없을 때 승격으로 대체하지 않는가** | 셸 dispatch 실패를 강제하고 **실행 0** 확인 — 폴백 부재가 시험 항목 | 없음 |
| E6b | **그 실패가 성공으로 기록되지 않는가** | 같은 조건에서 `run_update` 결과가 **`Done`/`Updated` 가 아니라 `UpdatedButNotRelaunched`** 이고, detail 이 **어느 이미지가 안 떴는지 이름을 대는지** 확인 | 없음 |
| E6c | **호스트 실패와 클라이언트 실패가 구분되는가** | 호스트만 실패 / 클라이언트만 실패 두 경우의 항목별 결과가 **다른 값**임을 확인 — `bool` 하나로 뭉개지지 않을 것 | 없음 |
| E7 | **서비스 실패 경로** | 없는 서비스명 → `false` + 이유. 서비스 **생성은 하지 않는다**(관리자 필요) | 없음 |
| E8 | **health 가 이번 실행만 보는가** | 이미 회귀 있음(`update_relaunch_test.cpp`), E1 과 연결해 dummy 가 쓴 줄로 확장 | 없음 |

**E5 의 한계를 미리 적어 둔다**: 이 세션이 비승격이면 "부모보다 낮은 무결성" 을 비교할 수 없다.
그때는 **셸 경유 실행이 성공했다는 것**까지만 단정하고, 승격 대비는 UPD-FIELD-01 로 남긴다.
**"검증했다" 와 "여기까지만 검증했다" 를 섞지 않는다.**

**E7 의 한계**: 서비스 등록·시작에는 관리자 권한이 필요하다. 실패 경로만 회귀로 덮고, 성공 경로는
UPD-FIELD-05 로 남긴다.

### 2.4 실 HTTPS

- 격리된 로컬 HTTPS 서버 + **테스트 전용 CA**로 정상 체인 1건, 그리고 **실패 경로**: 만료 인증서 ·
  이름 불일치 · **https→http 리다이렉트** · URL 자격증명.
- ⚠️ **운영 인증서 검증 우회는 계속 금지.** `WINHTTP_OPTION_SECURITY_FLAGS` 는 지금도 설정하지
  않으며 앞으로도 설정하지 않는다. 테스트 CA 는 **테스트 프로세스의 신뢰 저장소에만** 넣고, 제품
  코드에는 어떤 예외도 만들지 않는다.

## 3. 진행 순서

1. **R1·R2 + E1~E8** — 실행계층을 먼저 실제로 검증한다. 배선 전에 부품이 실행되는지부터 안다.
2. **W1·W2·W2a** — 업데이터 바이너리와 payload. 나머지 배선이 얹힐 바닥. 설치 위치는 W2a 로 확정(`installDir` 안 + 자기 복사본 실행).
3. **W3·W4·W4a·W4b·W4c·W5·W6** — Host 승인 + handoff, Client 승격 실행, **재실행 실패의 보고·안내**, **Host 무인 재시작**, 세션 복원 계약, Quiesce/Relaunch/Health 연결.
4. **W7** — Android.
5. **W8** — 발행 ↔ 소비 추적표.

**버전 인상·설치본 생성·설치·라이브 조작·배포·push 는 계속 금지.** 운영 서명키는 fail-closed 유지 —
다만 그것이 이 코드를 만들지 않을 이유는 아니다.
