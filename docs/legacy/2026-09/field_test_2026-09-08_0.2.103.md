# 0.2.103 실기: 정적 지연·UAC·고화질 영상 정지 직접 조사

작성: Codex, 2026-09-08. 기준 HEAD `edb1ec9`, 제품 소스 `acd8233`. 제품 수정·설치·서버 배포 없음.

## 1. 결론과 증거 수준

**이번 고화질 정지는 UAC 복귀 후 디코더가 Congested에 고착한 사건이 아니다. 첫 사건은 영상/제어 UDP 유입이 끊기고, 뷰어 수신 루프는 타임아웃으로 계속 돌다가 제어 채널이 peer-lost로 끝난 사건이다. 호스트는 그동안 후속 P/IDR 송신 성공을 기록했다.** 재접속으로 새 UDP 포트를 쓰면 잠시 통신하다 다시 멈췄다. 최초 패킷이 사라진 위치(호스트 NIC 이후·공유기·경로·회사망·회사 PC 네트워크 스택)는 기존 로그만으로 확정할 수 없다. sendto 성공은 NIC/상대 수신 성공의 증명이 아니다.

코드상 악화/복구 공백은 확인했다. Normal 상태에서 마지막 불완전 AU의 NACK가 소진돼도 후속 완료 AU가 없으면 복구 상태로 가지 않는다. 호스트 ABR은 피드백 단절 약 5초 뒤에야 하향하고, 재접속 tune은 다시 높은 설정으로 복귀한다. 순간 송신 정책은 12Mbps UI 값보다 훨씬 높은 burst를 허용한다. **이 경로들은 수정·설계 검토 대상이지만, 회사 방화벽/공유기 차단을 입증한 것은 아니다.**

정적 반응은 별개다. 호스트 표본에서 AU capture stamp→입큐 전 송신 준비가 102~185ms였고, 현재 비동기 인코더의 다음 입력 의존과 trailing kick 150ms 정책이 지연 후보로 직접 확인됐다. 입력 이벤트→그 결과 픽셀의 종단 지연은 아직 측정하지 않았다.

## 4. 최초 정지를 코드 실행 경로로 분해

1. `host_stage_encode_send_h264.cpp`→`host_stage_encode_send_h264_au.cpp`→`host_encoded_sender.cpp`→`host_net_io.cpp:115-226`: 인코딩과 UDP 송신이 계속됐다. `wire`는 key/지연 표본만 기록하므로 이 줄 수로 전체 FPS를 계산하지 않았다.
2. `viewer_video_receiver.cpp:197-221`: n>0이면 필터링·조립·디코드보다 먼저 lastDatagramUs를 갱신한다. 첫 정지의 link-silent는 이 값이 3.14초 전이고 현재 stage는 Recv이다. 잘못된 generation/codec 때문에 모든 수신 프레임을 버리는 설명만으로는 **lastDatagram 자체의 정지**를 설명할 수 없다.
3. timeout에서 `drain_deliveries`→NACK→`fg.tick`은 실행된다. 그러나 후속 완료 AU가 없으면 assembler가 head를 보존하고, 스케줄러 라운드 소진은 waitForKey를 켜지 않는다. 당시 Normal/waitForKey0이므로 frame gate 타이머는 새 reason7 요청을 하지 않는다. [수정 원장의 A04](stabilization_audit_2026-09-08.md)를 참조한다.
4. `viewer_session_watchdog.cpp:70-78`의 link-silent는 로그만 남긴다. 주석의 “keyframe recovery timer keeps asking”은 Normal 상태에서는 성립하지 않는다. control 종료 이후의 dead-session 처리는 자동 재연결/relay 전환이 아니다.
5. 제어도 같은 UDP 경로를 공유한다. `UdpControlChannel::Tick` 및 `UdpControlLink::EnsureInbound`가 응답 소실 후 재시도를 소진하고, `viewer_control_client.cpp:326-341`이 제어 실패로 종료한다. 호스트도 세션을 닫아 스트림을 중단한다.

따라서 **무수신 최초 발생 위치는 미확정**, 그 뒤 손실 복구·속도 하향·재접속이 부족한 실행 경로는 확인됐다. A01(401 spin)·A02(빈 출력 FIFO) 등 감사 결함을 이번 정지의 원인이라고 자동으로 붙이지 않는다. 해당 구간에 그 트리거의 직접 증거는 없다.

### 방향을 좁혀 주는 재접속 후 ping

gen4 ping3→4에서 hostRecv 증가량은 1,012,302µs, clientSend 증가량은 1,012,243µs로 차이가 59µs다. hostRecv와 hostSend는 같은 값으로 기록됐다. 그럼에도 ping4 RTT는 763,496µs였다. 짧은 구간의 시계 속도가 안정적이라는 조건에서, 추가 지연은 요청 전송/호스트 처리보다는 **호스트 응답 준비 이후 회사 PC 수신·처리까지**에 생겼다는 근거다. 이것도 NIC 양단 캡처를 대신하거나, 네트워크와 회사 PC 수신 처리를 완전히 분리하는 증거는 아니다.

## 5. 송신 속도와 재접속 정책

- 시작 로그: `udpPacePeakPercent=500`, floor40Mbps, keyframe peak100Mbps. 12Mbps 적용 시 delta pacing60Mbps. 인코더는 mean12Mbps/peak24Mbps VBR을 요청한다. setter 성공은 모든 드라이버가 실제 비트레이트를 지킨다는 증거가 아니다.
- host 09:59:26.464의 `mbps=23.5525`는 해당 stats tick의 `sentBytes×8/1e6` 값이다. 30초 전체 평균이나 순간 NIC 계측으로 부르지 않는다. 누적 udpTx로 계산한 09:59:26.464~56.446은 54,676,950 payload bytes /29.982s ≈14.59Mbps(영상·정지·재접속 혼합 구간). FEC/UDP/IP 헤더·재전송은 이 payload byte 값에 전부 포함되지 않는다.
- `host_net_io.cpp:94-107`은 큰 key에 높은 별도 속도를 주고 작은 프레임은 pacing을 생략한다. 재전송 `:248-280`은 별도 byte bucket 허용 후 패킷을 연속 전송한다. 따라서 UI12Mbps를 종단 wire 상한으로 해석할 수 없다.
- `host_stage_stats_h264.cpp:319-320`의 피드백 유효기간3초와 `host_abr.hpp`의 stale/pressure 누적이 결합된다. 실기에서는 first outage 뒤 09:59:31.461, second 뒤44.446에야 9Mbps로 낮췄다. 단절 전에 네트워크를 지켜낸 동작이 아니다.
- `host_stage_runtime_tune.cpp:130-142`는 명시 요청을 받으면 high profile로 돌아간다. 재접속마다 09:59:38.039와48.176에12Mbps/60Mbps pacing으로 다시 복귀했다. 최근 실패한 전송 부하를 기억해 낮게 시작하는 장치가 없다.
- **남은 가설:** 평균·burst/pps 부하에 따른 경로 손실/제한 또는 회사 PC 네트워크 수신 문제. 공유기/회사 방화벽/ISP 중 특정 장비를 지목할 증거는 없다. relay에서도 동일할지 이번 로그로 판단 불가.

## 6. UAC·정적 반응

### UAC

- 사용자 클릭 정확 + host dispatch target1920×1080. 다중 모니터/원점 변경의 일반 검증은 아니다.
- WGC 첫 frame hold31,328µs, DXGI 복귀 첫 current frame hold22,696µs(둘 다 **입큐 전 시각−capture stamp**, 실제 wire 총지연 아님). old97B P를 폐기하고 current IDR을 수락했다.
- 09:58:25~09:59:10 뷰어 congestion 전환0, stale-reference recovery0, 렌더 실패 카운터0. 따라서 이 구간에서는 0.2.103의 UAC 복귀 보정이 의도대로 동작한 근거가 있다.
- readback: 30초마다 로그에 남은 **각 1초 집계 표본**에서 UAC 전 captureUnmapWaitAvg1.7~2.0ms/workerD3dCallAvg18~25µs, 이후 약8ms/7ms, d3dMt on. 30초 전체 평균이 아니다. 추가 지연은 남지만 이번 고화질 정지를 수백ms readback 고착으로 설명할 근거는 없다.

### 정적 반응

- host 누적 송신: 09:57:26.447~56.447 267/30s=8.9fps, 다음30초255/30s=8.5fps. 정적 화면에서 낮은 출력 cadence 자체는 오류 증명이 아니다.

- `host_stage_encode_send_h264.cpp:363-369`는 마지막 real input 후 kick을 arm하고 `host_kick.hpp:45`는150ms다. 다음 입력까지 MFT 출력이 보유되는 경우가 있어 정적 반응 후보가 된다. `host_bgra_scale.cpp:113-129`는 전체 block 비교 후 작은 변화도 최소1을 반환하므로 “문자 변화가 샘플링에서0으로 사라져 무조건8fps 제한”이라는 과거 설명은 현 코드에 적용되지 않는다.

## 7. 후속 조치·완료 기준

1. [수정 필요 원장](stabilization_audit_2026-09-08.md)의 확인 결함을 먼저 추적: 업로더 busy loop, epoch FIFO/overflow, NACK 대상·hold·소진 폴백. 이번 증상과 인과가 입증되지 않은 항목은 그렇게 표시한다.
2. 고화질 정지 대응: Normal 무수신/불완전 AU 소진, 피드백 단절 하향, 재접속 초기 bitrate/pps, 경로 전환을 하나의 복구 계약으로 설계. 단순 IDR 추가나 decoder reset 반복으로 물리 유입 중단을 해결했다고 주장하지 않는다.
3. 최초 드롭 위치 확인에 필요한 증거: 동일 seq/gen의 UDP를 호스트 NIC 송신·회사 PC NIC 수신 양단에서 제한된 구간 캡처; 목적 IP/port·원본/FEC/NACK·송신 pps를 대조. 회사 NIC에서 사라지면 그 앞의 경로, NIC에는 있지만 recv에 없으면 회사 PC 필터/소켓/소스 endpoint를 조사. 기존 로그로 이 구간을 메울 수 없다.
4. 안전한 실기 비교: 동일 영상·해상도에서 현재 설정 vs 낮은 전송 예산, 직결 vs 명시 relay 비교. 입력 RTT만 아니라 lastDatagram·새 frame 표시·NACK 결과·복구 시간을 측정. 실제 사용 중인 프로세스는 이번 조사에서 중단하지 않았다.
5. 정적 지연은 입력 event ID→처리→해당 변경 픽셀/AU→표시를 연결해 측정하고, 시계 오차와 합성 프레임을 분리한 뒤 보유 정책을 조정한다.
