# 0.2.104 실기 17:50~ 720p 고착 — 증거 보전과 코드 경로 교차확인

작성: 작업용 Claude, 2026-09-08. 대상 릴리스 `0.2.104`(`dist/GNLinkSetup-0.2.104.exe`, history #426).
**이 문서는 증거 보전·기록·코드 교차확인이다. 제품 수정은 위임되지 않았고 하지 않았다.** 라이브 조작·설치·배포·빌드·테스트·새 패킷캡처 없음.

> **17:16 세션 건(`docs/field_test_2026-09-08_0.2.104.md`)과 다른 사건이다.** 그 문서는 링크 무수신과 뷰어 자동 종료를 다루고, 이 문서는 해상도가 720p 로 내려간 뒤 돌아오지 않는 것을 다룬다. **두 사건을 동일 원인으로 엮지 않는다.** 별도 파일로 둔 이유가 그것이다.

## 4. 고착의 핵심 관측

**[C]** `17:56:08.297` 에 ABR 프로파일이 **high · 12 Mbps 로 복귀**했다. 그런데 같은 행의 `encode=` 는 **`1280x720`** 이다.

**[W] 정밀화**: 이 발췌 창(17:45~18:05)에 `[abr]` 행은 **위 4건이 전부**다. 즉 17:56:08 이후로는 프로파일 변경 시도조차 없고, **high 12 Mbps @ 720p 상태가 그대로 유지된다.** 비트레이트 예산은 돌아왔는데 해상도만 돌아오지 않았다.

> **이것이 사용자 증상("복구되지 않음")과 직결되는 관측이다.** ABR 은 이미 최상위 프로파일(high · 12 Mbps)에 도달해 있으므로 **더 올릴 것이 없다.** 그런데 실제 인코드는 720p 다. 즉 **시스템이 "최대 품질" 이라고 여기는 상태와 화면에 나오는 720p 가 어긋나 있고, 로그에는 그 뒤 어떤 재시도도 기록되지 않았다.**
>
> 이것은 **사실 진술이다** — "스스로 벗어날 수 없다" 를 코드로 증명한 것이 아니라, **이 창의 로그에 복구 시도가 한 건도 없다**는 관측이다. 원인은 6절의 코드 경로와 정합하지만, 7절의 한계가 그대로 적용된다.

**[W] 정밀화**: 뷰어 쪽 전환 시각이 정확히 잡힌다 — 마지막 `size=1920x1080` 이 **17:55:21.557**, 최초 `size=1280x720` 이 **17:55:21.763**. 그 뒤 발췌 끝(18:03:40)까지 `1280x720` 499 표본, `1920x1080` **0 표본**이다. "17:58~ 지속" 보다 강하게, **17:55:21.763 부터 연속**이다.

## 6. 코드 경로 교차확인 — 되먹임이 코드상 폐곡선으로 성립한다

**[V]** 검증용 Claude 가 원본 대조한 경로이며, **작업용이 전부 재확인했다.** 아래 줄 번호는 **재확인한 실제 값**이다(정정 사항은 6.6).

### 6.1 축소는 되지만 확대는 안 된다

`fit_size_preserving_aspect` — `apps/native_poc/src/host_bgra_scale.cpp:35-47`:

```
const double scale = std::min({(double)boxW / (double)srcW,
                               (double)boxH / (double)srcH, 1.0});   // :43-44
*outW = clamp_even_dim(lround(srcW * scale), 2, srcW);               // :45
*outH = clamp_even_dim(lround(srcH * scale), 2, srcH);               // :46
```

`scale` 의 상한이 **`1.0`** 이고 출력이 `clamp_even_dim(..., 2, srcW/srcH)` 로 **source 크기까지만** 허용된다. **원본보다 큰 출력은 나올 수 없다.**

### 6.2 목표는 source 에 맞춰 잘린다

`EncoderState::ApplyTarget` — `host_encoder_manager.cpp:32-...`:

```
encoder.nominalEncodeW = targetW;                                    // :44
encoder.nominalEncodeH = targetH;                                    // :45
fit_size_preserving_aspect(encoder.encodeSourceW, encoder.encodeSourceH,
                           targetW, targetH, &targetW, &targetH);    // :46
```

`nominalEncodeW/H`(목표 박스)를 먼저 저장한 뒤 **`encodeSourceW/H` 를 기준으로 fit** 한다. 따라서 `encodeSource` 가 1280x720 이면 1920x1080 을 목표로 줘도 `min(1.5, 1.5, 1.0) = 1.0` → 결과는 **1280x720** 이다. 주석(`:42-43`)은 `nominal` 을 기억하는 이유를 "source 크기 변화 시 같은 예산으로 재적합해 ratcheting down 을 막기 위해" 라고 밝힌다.

### 6.3 `encodeSource` 가 오염되는 지점

`encodeSourceW` 에 쓰는 곳은 저장소 전체에 **정확히 세 곳**이다 [W]:

| # | 위치 | 값 | 조건 |
|---|---|---|---|
| 1 | `host_startup_graphics.cpp:330` | `capture.width` (**원본 geometry**) | 기동 시 1회 |
| 2 | `host_encoder_manager.cpp:124-125` | 확정된 새 캡처 geometry | `ApplyConfirmedCaptureGeometry` — **aspectClose 예외 없음** |
| 3 | `host_stage_encode_send_h264.cpp:170-171` | **프레임 payload 의 `w`,`h`** | **무조건** (아래) |

**[W]** 3번의 `w`/`h` 출처를 끝까지 따라가면 `TickContext::w/h`(`host_main_loop.hpp:157-158`)이고, 그 대입은 **`host_stage_pop_frame.cpp:276-277` 의 `res.frame.width` / `res.frame.height`** 다. 즉 **큐에서 꺼낸 프레임의 실제 크기**이며, 전처리로 축소된 프레임이면 축소된 크기다. "전처리로 축소된 payload 가 새 원본이 된다" 는 서술이 코드로 확인된다.

> **이 세 곳뿐이라는 사실이 이 문서에서 가장 강한 코드 근거다.** `encodeSource` 는 fit 의 기준이므로(6.2) 그 값이 어디서 바뀌는지가 전부인데, 후보가 셋으로 닫힌다. 그중 1번은 기동 시 1회고 2번은 교정을 건너뛰지 않으므로(6.5), **오염 가능 경로는 3번 하나로 좁혀진다.** 즉 "어딘가 다른 데서 바뀌었을 수도 있다" 는 여지가 코드 수준에서 남지 않는다.
>
> 다만 이것은 **어느 경로가 실제로 실행됐는지의 증거는 아니다** — 런타임 관측이 없다는 7절 첫 항목이 그대로 적용된다.

### 6.4 핵심 — 대입은 무조건, 교정은 조건부

**[V]** `host_stage_encode_send_h264.cpp` 의 같은 블록 안에서 **두 동작의 조건이 다르다**:

```
const bool aspectClose =
    std::abs(refitAspect - activeAspect) <= activeAspect * 0.02;     // :166-169
encoder.encodeSourceW = w;                                           // :170  ← 무조건
encoder.encodeSourceH = h;                                           // :171  ← 무조건
if ((refitW != encoder.activeEncodeW || refitH != encoder.activeEncodeH)
    && !aspectClose) {                                               // :172  ← 조건부
  ... encoder.ApplyTarget(...)                                       // :177
}
```

- `encodeSourceW/H` 대입(`:170-171`)에는 **아무 조건이 없다.**
- 교정용 `ApplyTarget`(`:177`)은 **`!aspectClose`** 일 때만 실행된다.
- **1280x720 과 1920x1080 은 둘 다 16:9 다.** 두 종횡비의 차이는 0 이므로 2% 허용치 안에 들어가 **`aspectClose` 가 참**이 된다.

따라서 이 경우 **스래싱 방지 가드가 하필 `source` 만 낮추고 교정을 건너뛴다.** 주석(`:150-153`)이 밝히는 가드의 의도는 창 드래그 중 매 프레임 MFT 재구성을 막는 것인데, 같은 종횡비의 축소에서는 **오염만 남고 보정이 빠진다.**

6.2 의 `nominalEncodeW/H` ratcheting-down 방지 장치도 여기서 무력화된다 — `nominal` 은 1920x1080 으로 보존되지만, 그것을 fit 하는 기준인 `encodeSource` 자체가 720p 로 바뀌었기 때문이다.

### 6.5 대비되는 경로

**[V]** `EncoderState::ApplyConfirmedCaptureGeometry`(`host_encoder_manager.cpp:111-142`)는 정반대다:

```
encoder.encodeSourceW = newW;                                        // :124
encoder.encodeSourceH = newH;                                        // :125
// Confirmed change: no aspectClose skip. A smaller same-aspect source must still
// shrink activeEncode to avoid upscaling. ...                       // :131-133
if (encoder.ApplyTarget(..., encoder.nominalEncodeW, encoder.nominalEncodeH, ...)) // :134
```

주석이 **"확정된 변경에는 aspectClose 건너뛰기가 없다 — 같은 종횡비의 더 작은 source 도 activeEncode 를 줄여야 upscaling 을 피한다"** 고 명시하고, 실제로 조건 없이 재적용한다. **같은 문제를 이미 알고 한쪽 경로에서만 막아 둔 셈이다.**

### 6.6 검증용 서술 대비 정정 1건

- **`OnSourceSizeChanged` 라는 심볼은 저장소에 없다.** 실제 함수는 **`EncoderState::ApplyConfirmedCaptureGeometry`**(`host_encoder_manager.cpp:111-142`)이고, `encodeSource` 대입은 `:123-124` 가 아니라 **`:124-125`** 다. 대비 구조에 대한 지적 자체는 정확하다.
- 나머지 4개 인용(`host_bgra_scale.cpp:43-46`, `host_encoder_manager.cpp:44-46`, `host_stage_encode_send_h264.cpp:170-171`, `host_startup_graphics.cpp:330`)은 **원문과 일치한다.**

## 7. 판단 한계 (약화하지 않는다)

- **런타임 `encodeSourceW/H` 를 직접 관측한 로그가 없다.** 이 문서가 보인 것은 **① 코드상 폐곡선이 성립한다는 것**과 **② 실기 관측(720p 고착 + `capturePreprocessed` 증가 + 프로파일만 복귀)이 그 폐곡선과 정합한다는 것**뿐이다. **정합은 일치이지 증명이 아니다.** 런타임 변수 실측은 하지 않았다.
- `assembly dropped`/`FEC`/`NACK` 수치를 **UDP 손실률로 단정하지 않는다**(5.1).
- **`moderate` 판정의 원인은 스냅샷 시차 때문에 단정하지 않는다**(5.3).
- **무조건 upscale 허용은 해법이 아니다.** `min(..., 1.0)` 을 풀면 실제로 낮은 원본을 확대하게 되고, 그것은 다른 결함이 된다. 방향 후보는 **"원본 geometry 를 source 의 진실로 유지하고, readback 출력을 재설정해 복구한다"** 이며 — **이 task 에서 구현하지 않는다.** 설계·승인은 별도 단계다.
- **17:16 세션 건과 다른 사건이다.** 동일 원인으로 엮지 않는다.
- 호스트와 뷰어의 시계는 정렬되어 있지 않다. 두 로그의 표시 시각 차이를 지연이나 선후 인과로 해석하지 않는다.

## 8. 미확인

1. 런타임 `encodeSourceW/H`·`nominalEncodeW/H`·`activeEncodeW/H` 의 실제 값 (관측 로그 없음, 위 7절 첫 항목).
2. `capturePreprocessed` 를 증가시킨 전처리 경로가 **어떤 조건으로 진입했는지** — 진입 조건 자체는 이번에 추적하지 않았다.
3. `moderate` 판정에 들어간 클라이언트 지표 스냅샷이 **어느 시점의 상태**였는지.
4. 사용자가 그 사이에 한 조작(있었다면)과 화질 저하의 관계.
5. 17:55:21.763 의 뷰어 해상도 전환과 17:55:22.425 의 호스트 `mid_to_low` 로그 사이의 선후 — **시계 미정렬이라 판정하지 않는다.**
6. 이 고착이 `0.2.103` 이전에도 재현되는지(회귀 여부).
