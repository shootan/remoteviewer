### diff 교차검증 (2026-08-28, 코덱스)

원장 처리 후 `779390e` / `4aaa451`을 코덱스가 diff 단위로 다시 봤고 **blocker 2 + High 1**이
나왔다. 전부 코드에서 확인해 `a67522f`로 닫았다.

| 지적 | 판정 | 처리 |
|---|---|---|
| **H-23이 데드락 대신 publication race를 열었다** — `slot->state`가 컨텍스트 작업 *전에* 이미 GpuPending인데 meta 확정을 락 해제 *뒤로* 옮겼다. 그 사이 워커가 집으면 실패한 preprocess를 `preprocessed=true`로, 반환 예정 NV12 lease를 유효 surface로 소비자에게 넘긴다. `submitUs=0`은 실패와 무관하게 매 프레임 창이 열린다 | **내 회귀. 확정** | `SlotState::Submitting` 추가 → 워커는 GpuPending만 poll, Submit이 meta 확정 후 **마지막에** 승격. 락 순서는 `slotMu→contextMu` 유지 |
| **identity fence가 약하다** — 같은 generation 안에서 슬롯이 재사용돼도 staging 텍스처는 동일하므로 포인터는 fence가 아니다 | 확정 | `submitSeq`로 교체(Submit·워커 양쪽) |
| **NV12 실패 lease 반환이 identity 밖에 있다** — Reconfigure가 회수하고 같은 index를 재대여한 뒤면 ABA | 확정 | identity 안으로 이동 |
| **H-02의 내 추론이 틀렸다** — "stop=true라 새 소켓을 못 넘긴다"는 새 accept만 막을 뿐, owner가 load와 shutdown 사이에 close하는 것과 무관하다. atomic은 값만 게시하지 수명을 고정하지 못한다 | **확정 / blocker** | `controlClientSockMu` 도입. 게시/해제+close/외부 shutdown 전부 그 아래 |
| **H-01 기동 레이스** — Stop이 `CreateProcessW` 도중에 오면 TerminateChild가 미게시 child_를 보고 아무것도 안 죽이고, 이후 게시+`Wait(INFINITE)`로 join이 영구 대기 | 확정 / High | 게시 임계구역에서 `running_` 재확인 |
| H-01 핵심(wait 중 handle close), H-03 lease 규칙 5경로 + "publish 후 meta -1" | **PASS** | 변경 없음 |

**재검증 (2026-08-28, `a67522f`)**: 코덱스가 셋 다 닫힌 것으로 확인, 추가 blocker/High 없음. 비차단 관찰 1건은 위 H-25로 기록했다. 코덱스는 21커밋 전체를 일괄 승인하지는 않았다 — 검증된 것은 `779390e` / `4aaa451` / `a67522f` 세 개다.

**처리하며 새로 드러난 것** (원장 작성 시점에는 몰랐던 것들):

1. **H-03에 6번째 경로가 있었다.** 코덱스가 지적한 (a)~(e) 외에, worker가 publish **성공** 후에도
   `slotRef->meta.nv12Slot`을 지우지 않아, (c)의 일괄 반환을 그냥 넣으면 이미 인코드 루프로
   넘어간 lease를 CreateSlotsLocked가 다시 반환하는 double-free가 됐다. 인계 시점에도 -1로
   지우는 규칙을 추가해 `meta.nv12Slot >= 0` == "링이 아직 소유"라는 불변식을 세웠다.
2. **H-16 목록이 두 번 틀렸다.** 처음 18개는 스캐너의 함수 블록 분할 오류로 과대집계였고
   (코덱스가 15개로 정정), 파일 단위로 다시 스캔하니 코덱스가 확인해준 파일 밖에서 19개가
   더 나와 최종 32개였다.
3. **H-11의 클램프 식이 틀렸었다.** `max(old+1s, t)`는 `next == t`가 되어 다음 루프에서 즉시
   재발화한다(코덱스 지적). `nextAtUs <= t`일 때 `t + 1s`로 재앵커해야 한다.
4. **죽은 쓰기 하나 추가 발견.** `startup_configure_control_state`의
   `backend.reqValue = ...from_env()`는 reqPending을 세우지 않아 아무도 읽지 않았다.
   실제 env 경로는 `startup_init_graphics`의 `backend.requested`다. H-22/Phase 4에서 제거.
5. **중간에 구 바이너리가 PASS로 보인 적이 있다.** H-05에서 `capture_cadence_gate_test`가
   컴파일에 실패했는데 이전 exe가 그대로 PASS를 냈다. 이후로는 매번 재빌드 후 실행한다.

## 규칙

1. 호스트 분할 리팩터(Phase 0~3)는 완료됐고 실기(0.2.58)도 통과했다. 이 원장은 **Phase 4(스레드 소유권 재설계) 착수 전 호스트 전체 소스를 전수 분석**해 만든 목록이다. 뷰어 원장과 같은 규칙으로 **기록만** 하고, 수정은 별도 커밋/사이클에서 한다.
2. ID는 `H-NN` (뷰어 원장의 `F-NN`과 구분).
3. 동작이 바뀌는 항목은 호스트 e2e 6/6 + 실기 게이트를 건다.
4. **전 항목이 `검증용Codex`(a2a `remote#sa9wm39t`) 교차검증을 거쳤다** (2026-08-27, 3통 왕복). "판정" 열이 그 결과다. 기각·조건부·정정된 것은 그 내용을 그대로 남긴다 — 다음 세션이 같은 결론에 도달했다가 되돌리는 비용을 없애기 위해서다.
5. 표의 "판정"은 교차검증 결과이며, 처리 커밋은 위 상태 표에 있다.
6. **교차검증이 바꾼 것**: 누수 대표 경로(H-03e)와 데드락(H-23)은 코덱스가 추가 발견했고, 내가 보고한 것 중 H-09(인터리브 버그)는 기각, H-14·H-18은 조건부로 강등, H-16은 목록이 과대집계여서 18 → 15로 정정됐다.
