## 2) 설계 원칙

호스트 계획 §2의 1~7을 그대로 승계(기능 기준 분할, 행동 보존, 1클래스 1파일 ≤800줄 + 5줄 머리 요약, 30줄 초과 람다는 멤버로, 참조로만 알고 main이 조립, 순수 결정은 시간을 인자로, 파일 머리 `// thread:` 블록). 뷰어 추가분:

8. **파일 접두사 `viewer_`, 네임스페이스 `remote60::native_poc::viewer`.** 셸(`client_shell_*`, GNLinkClient)과 구분하고, 호스트 `host_args.hpp`의 `Args/parse_args/env_truthy…`와 같은 이름이 `remote60::native_poc`에서 충돌하지 않게 한다. 기존 `client_macro_window`/`client_session_toolbar`는 이름을 바꾸지 않는다.
9. **전역은 0-0에서 `viewer_globals.hpp`(extern) 경유로만 다른 TU에 노출**한다(이름·타입·초기값 불변, anonymous → 명명 namespace = 링크만 변경). Phase 1에서 struct로 흡수되고 Phase 3에서 헤더가 소멸한다. 동적 초기화 전역 19개(SharedFrame·mutex·std::string·상태모델 등)는 초기화식이 다른 전역을 참조하지 않으므로 TU 분리에 안전(§8-G로 확인).
10. **UI 스레드 친화는 근본 제약**: HWND/GDI/툴바·매크로 창/D3D 스왑체인 present는 UI 스레드에서만. 이를 깨는 재설계는 없다.
11. 로그 문자열·필드명·순서 불변(§8-F). 리네임은 `automation/rename_outside_strings.pl`(호스트 Phase 1 도구)로 문자열 리터럴 밖에서만.
12. 중복(공유 헤더와 byte-동일한 사본)은 이동하지 말고 **공유본으로 대체**한다(호스트 0-5 교훈). 호스트 파일을 건드리는 통합은 별도 커밋 + 호스트 게이트.
13. **발견은 기록, 수정은 나중에.** 리팩터 커밋은 이동·리네임·래핑만 담는다. 버그·불일치·dead code·고도화 거리를 보면 `뷰어_리팩터_발견사항.md`에 F-NN으로 적고 코드는 그대로 옮긴다(필요하면 `// F-NN` 주석만). 이 문서의 0-14(dead code 삭제)도 같은 이유로 원장 F-04로 이관했다.

## 6) Phase 3 — 조립: `ViewerContext` + main() ≤150줄

```
main():
  1 선언            ViewerContext ctx  (state struct 13 + 클래스 5: VideoReceiver/ControlClient/SelectionGate/PickerGesture/DecoderStage; 모놀리스 선언 순서 = 파괴 순서)
  2 startup 함수열  viewer_startup.hpp 13개 호출, 실패 시 exit code 그대로 반환
  3 스레드 시작     ctx.control.Start() (controlReady일 때만) → ctx.receiver.Start()
  4 UI 루프         pump_messages() / push_toolbar_tick(500ms) / time_limit(args.seconds) / Sleep(5)   ← 5276~5313 그대로 3 함수
  5 shutdown_viewer(ctx)
```

- WndProc ↔ ctx: `CreateWindowExW`의 `lpParam`으로 `ViewerContext*`를 넘겨 **WM_NCCREATE에서 `GWLP_USERDATA`에 저장**, 이후 모든 메시지가 ctx를 본다(생성 중 WM_NCCREATE 이전 메시지는 현재도 default 처리 → 동작 동일). 전역 `gHwnd`는 ctx.session.hwnd로.

## 7) 스레드 소유권 — 지금 규칙의 성격과 Phase 4 재설계

### 7.1 판정

**(a) 근본 제약 — 리팩터 후에도 유지 (4개)**

| 제약 | 이유 |
|---|---|
| HWND/GDI/툴바·매크로 창/D3D 스왑체인 present는 UI 스레드 | Win32 창 친화. reveal이 "recv가 기록, UI가 커밋"인 이유(2204~2208 주석) |
| MFT 디코더 submit/drain은 recv 스레드 하나 | Media Foundation 계약(호스트 인코더와 동일) |
| 비디오 소켓 읽기는 recv 스레드 하나, 컨트롤 쓰기는 control 스레드 하나 | UDP 터널은 같은 소켓을 recv(read)/control(write)이 나눠 씀 — 1 reader/1 writer는 허용, 늘리면 안 됨. recv timeout tick이 터널 heartbeat인 이유(4916~4919) |
| `gPaintQueued` invalidate 병합 | UI 메시지 큐 폭주 방지(4곳 동일 패턴) — 규칙은 유지하되 함수 1개로 |

**(b) 인위 규칙 — 전역 atomics 58개로 락 없이 신호하려다 생긴 것 (Phase 4에서 제거)**

| 현재 패턴 | 왜 생겼나 | 재설계 |
|---|---|---|
| 선택 게이트 atomics 8개 + "recv는 Ready*만 기록·UI가 재검증 후 커밋" 프로토콜(836~843) | 구조체·락이 없어서 | `SelectionGate` 내부를 mutex 1개 + 값 struct로. PostMessage 커밋은 유지(근본 제약 a) |
| `gRemoteCursor*` 7개 latest-wins atomics | 〃 | `CursorSample` 스냅샷 1개(락 또는 seqlock) |
| `gHostCaptureTarget*` 5 atomics + mutex + string 2 | 〃 | `HostCaptureMeta` 스냅샷 1개 |
| present 카운터 8 atomics + WM_PAINT `static` 4 → recv 1s 집계가 delta 계산 | 〃 | `PresentStats::Snapshot()` |
| `gClientMetrics` atomic 20(recv 쓰기 / control·UI 읽기) | 〃 | 호스트 1-10과 동일 — 락 아래 통째 교체/복사 |
| `gCatchupSuppressUntilUs`/`gLastPresentedCaptureUs`를 UI가 리셋하고 recv가 읽음 | 〃 | FrameGate 입력 스냅샷 |
| 1s 통계 블록 5회 복제 | 람다 안에서 early-return마다 복사 | Phase 2-1에서 1개 |
| `ClientSessionController`(Android 패리티)와 뷰어 control/recv 루프의 이중 구현 | 뷰어가 먼저 있었고 세션 컨트롤러가 나중 | 통합 검토(설계 변경, 뷰어가 컨트롤러 위에 올라타는 형태) |

## 9) HANDOFF / 구현계획과의 관계

- Phase 0은 순수 이동이라 **실기 판정(HANDOFF A)과 무관하게 지금 진행 가능**.
- **P3 클라 paced playout**은 present 경로가 대상 → Phase 2-8(present 분리) + Phase 4 PresentScheduler 뒤에 하면 한 번에 끝난다. 그 전에 하면 두 번 고친다.
- **SyntheticRefresh flag**(HANDOFF 부채, P2 착수 전 게이트)는 FrameGate(2-2)의 입력 한 필드 + T1 시나리오 1개로 흡수 가능 — 동작 변경이므로 Phase 4 항목으로 별도 커밋.
- 선택 게이트/피커 규칙은 Android(commit 4892dea) 패리티 — T2/T3가 그 계약을 고정한다.
- 0-15 공유 통합은 호스트 파일을 건드리므로 호스트 빌드 + UDP e2e 13/13을 추가 게이트로 건다.
- 호스트 Phase 4(스레드 소유권)와는 파일이 겹치지 않아 병행 가능하나, 문서/브랜치 정책상 한 번에 하나만 진행한다.
