# 직접 연결(펀치) vs 중계 — GNLink 실측 집계 (검증용 remote#wwml7h91, 2026-10-22)

사용자 지시(10-22): "1번 진행" — OSLink 펀치 조사 전에 GNLink 자체 로그로 중계 경유 빈도와 원인을 본다. 읽기 전용(NAS gnlink 계정, journalctl --user).

## 출처·정의 (소스 고정, main 5063cd9)
- 서버: `remote60-directory.service` journal, 2026-10-09 ~ 10-22 01:3x. 한 접속 = `connect=<id>`.
  - `[relay] connect=X eligible client=<공인IP>:port … host=<이름>@…` — 중계 후보를 준 접속과 **클라이언트가 서버에 보인 주소**.
  - `[relay] connect=X bound client=…` — **실제로 중계를 탄 접속**. 없으면 "중계 안 탐"(직접 성공 또는 실패 — 이 집계에선 구분 안 함).
  - 서버는 중계 펀치 응답을 `RELAY_GRACE_MS`=2500 ms 늦게 보낸다(`apps/directory/server.js:245,1682-1688`) → 직접 경로가 2.5 s 안에 답하지 못한 경우에만 중계가 이긴다.
  - `[host-hb] host=… wire=<서버가 본 송신 주소> public=<광고하는 공인 주소> aim=…` — 호스트 하트비트.
- PC 뷰어: `viewer.log*` 의 `[attempt] … punch answered=1 kind=… ms=` 와 `directory chose ip:port`. ⚠️ `candidate_kind_name`(connect_candidates.hpp:43-49)에 relay 이름이 없어 **중계도 `public` 으로 찍힌다** → 중계는 주소 `175.207.45.151:29190` 으로 판별했다(같은 이유로 뷰어의 `relayPath` 표시도 중계를 못 알아볼 가능성 — 별건 확인 필요).
- 휴대폰: `apk.log*` 의 `[directory_target]`/`[directory_chosen] ip|kind`(relay 이름 그대로).
- 망 구분(클라이언트 공인 IP): 175.207.45.x = 집, 211.218.222.x = 회사, 118.235.x·106.240.x·175.209.x = 그 밖(이동통신 등, 미확정).

## 결과 2 — 원인 (강한 정황)
**디렉터리 서버(NAS)가 집 LAN 안에 있다.** 그래서 집에 있는 호스트·클라이언트의 진짜 공인 NAT 매핑을 관찰할 수 없다:
- 집 호스트 하트비트는 공유기 hairpin 을 거쳐 `wire=192.168.0.1:<port>` 로 보이고, 서버는 그 port 를 그대로 붙여 `public=175.207.45.151:<port>` 로 **추정 광고**한다.
  - f6e8e54a: 관찰 port 가 43000(16.4k 회)·25870(6.0k)·3478(3.5k)·16016(1.6k)·14570 으로 바뀐다 → 43000/3478 일 때는 외부에서 직접 성공 가능, hairpin 이 바꾼 port 일 때는 외부 패킷이 엉뚱한 port 로 가서 실패 → 중계. **회사→집 63% 중계와 들쭉날쭉함이 이것으로 설명된다.**
  - 1c8ebffe: 관찰 port 가 **한 번도 43000 이 아니다**(16166·58029·14922) → 광고 주소가 항상 틀림 → **외부 접속 27/27 중계.**
- 반대로 클라이언트가 집에 있을 때(집 → 회사 PC 14/20 중계)도 서버가 클라이언트의 진짜 공인 매핑을 모르니, 호스트가 뚫어야 할 주소가 틀릴 수 있다(추정 — 호스트 쪽 펀치 대상 로그로 확인 필요).
- 대조: 회사 PC 는 서버가 밖에서 `211.218.222.1:43000` 을 직접 관찰 → 이동통신 → 회사 PC 33/33 중계 없음.
- 회사 같은 망(휴대폰 회사 Wi-Fi → 회사 PC) 11/23 중계는 다른 원인 — 사설 후보(192.168.20.50)가 Wi-Fi 격리/서브넷 차이로 안 닿고 회사 공유기 hairpin 도 안 되는 경우로 보인다(작업목록 SL, 미확정).

## 시사점 (설계 제안 — Codex 판정 전)
- OSLink 가 직접 연결되는 핵심 차이는 펀치 "기법" 보다 **집 밖(클라우드)에 있는 STUN/시그널링 서버로 진짜 매핑을 관찰**한다는 점일 가능성이 높다(8월 실측: 알리바바 클라우드 대역 시그널링).
- 후보: ⓐ 집 호스트·집 클라이언트가 **외부 STUN**(공개 STUN 또는 작은 외부 VPS)으로 자기 공인 매핑을 직접 알아내 디렉터리에 보고 ⓑ 집 공유기 UPnP/NAT-PMP 로 고정 port 매핑 요청 ⓒ 서버가 LAN 경유 관찰을 "공인 매핑" 으로 광고하지 않도록(hairpin port 를 public 으로 쓰지 않기, 43000 고정 매핑일 때만) — 각각 신뢰 경계·외부 의존 검토 필요.
- OSLink 패킷 관찰(2번)은 위 ⓐ 를 정할 때 "어느 STUN 을 몇 개, 몇 초 안에" 의 참고로만 필요.
