## 4. 확정된 결정 (Codex 확정 2026-09-08 + 검증용 실측)

step1 최초 작성 시 이 절은 "Codex 결정 대기" 로 비어 있었다. B1(전송)·B2(서명)·B3(Android 키)이 확정되고 검증용 Claude 의 read-only 실측 2건이 더해져 아래로 채운다. 출처는 **[Codex 확정]** / **[검증용 실측]** 으로 구분한다.

> **이 절 전체에 걸리는 제약**: 아래는 **설계 확정**이며 **배포 승인이 아니다.** 운영 서명키의 생성·교체·보관 위치 결정, 운영 도메인·엔드포인트 확정, 실제 배포는 **모두 별도 승인 사항**이다. 4.5 에서 "코드 준비완료" 와 "배포가능" 을 분리해 정리한다.

### 4.1 전송과 아티팩트 출처 검증

#### 4.1.1 전송 — 업데이트 전용 WinHTTP HTTPS 클라이언트 신설 [Codex 확정]

- **업데이트 경로 전용으로 WinHTTP 기반 HTTPS 클라이언트를 새로 만든다.** manifest 조회와 아티팩트 다운로드가 그 대상이다.
- **기존 코드를 전면 전환하지 않는다.** `directory_client`(등록·하트비트·connect), 인증, `log_upload` 는 현행 평문 경로를 유지한다. 이들의 HTTPS 전환은 이 설계의 범위가 아니다.
- 신설 이유는 1.4.4 에 이미 기록된 사실 그대로다: 현행 공개 API 는 `http_post()` 하나뿐이고(`directory_client.hpp:98-103`), GET·Range·재시도가 없으며, 응답 본문을 **64 KB 에서 자르고**(`directory_client.cpp:346-355`), `https://` 를 명시적으로 거부한다(`:83-93`). 3.5 MB 급 아티팩트를 받을 수단이 아니다.
- **금지 사항 (예외 없음)**:
  - TLS 인증서 검증 끄기 금지 (`WINHTTP_OPTION_SECURITY_FLAGS` 로 오류를 무시하는 형태 포함).
  - 인증서 오류 우회·무시 금지. 검증 실패는 다운로드 실패로 처리한다.
  - **HTTPS → HTTP 리다이렉트 허용 금지.** 리다이렉트를 따라가더라도 스킴 강등은 거부한다.
- TLS 와 서명은 **둘 다** 유지한다. 하나가 다른 하나를 대체하지 않는다 — TLS 는 전송 구간을, 서명은 아티팩트 자체의 출처를 지킨다.

#### 4.1.2 출처 검증 — manifest detached 서명 + 바이너리 내장 공개키 [Codex 확정]

- **manifest 에 detached 서명을 붙이고, 신뢰 공개키는 제품 바이너리에 내장한다.** 검증은 클라이언트가 내장 키로 수행한다.
- **manifest 가 계약의 중심이다.** 플랫폼 · 버전 · 크기 · SHA-256 · 아티팩트 식별을 **모두 하나의 서명 대상에 묶는다.** 개별 필드를 따로 서명하거나, 일부만 서명 밖에 두는 형태는 채택하지 않는다 — 그러면 서명된 manifest 와 다른 아티팩트를 짝지어 붙이는 것이 가능해진다.
- **알고리즘 (기본안): ECDSA P-256 + SHA-256.** 대안은 RSA-2048 PSS + SHA-256.
  - 선택 근거: 세 런타임 모두 **표준 라이브러리로 제공**한다 — Windows 는 BCrypt/CNG, Android 는 `java.security.Signature`, 서버(Node)는 `crypto`.
  - **Ed25519 는 제외한다** — CNG 지원이 불균일해 Windows 쪽 가용성이 보장되지 않는다.
- **자체 암호 구현 금지.** 해시·서명·인코딩 모두 플랫폼 표준 API 를 쓴다.

#### 4.1.3 Authenticode 와 혼동하지 말 것 [Codex 확정]

**이 서명은 Authenticode 가 아니다.** 아티팩트가 우리가 발행한 것인지를 우리 클라이언트가 검증하는 수단일 뿐이다. 따라서:

- **UAC 게시자 신뢰(“알 수 없는 게시자” 표시)를 해결하지 않는다.**
- **SmartScreen 평판을 해결하지 않는다.**
- 이 둘은 Authenticode 코드 서명 인증서가 필요한 별개의 문제이며, 현재 저장소에 그 인프라는 없다(1.4.4·이전 4.1 기록).

### 4.2 Android 서명·키 정책과 앱 데이터 보존

#### 4.2.1 실측 — 동일 키 재사용이 가능하다 [검증용 실측]

검증용 Claude 가 read-only 로 확인한 사실:

| 항목 | 값 |
|---|---|
| 출하 APK | `dist/GNLink-0.2.12.apk` |
| 서명자 DN | `C=US, O=Android, CN=Android Debug` |
| 인증서 SHA-256 | `dcc806aeb30b2e3c53e4a0b96b9675f9e25af2bf071dbb37a3cb09f6b8ec2990` |
| 서명 스킴 | v2/v3 만 (**v1 JAR 서명 없음**) |
| 키 | 2048-bit RSA, SHA256withRSA |
| keystore | 이 PC 의 `%USERPROFILE%\.android\debug.keystore`, 별칭 `androiddebugkey`, PKCS12 |
| 유효기간 | **2026-04-06 ~ 2056-03-29** |

출하 APK 의 지문과 로컬 `debug.keystore` 의 `androiddebugkey` 지문이 **완전히 일치한다.** 서로 다른 출처가 같은 값을 가리킨다 — 1.5 에 기록한 `docs/history.md:5566`·`:5815` 의 인증서 지문(`dcc806ae…2990`)이 이 실측과 일치한다.

#### 4.2.2 확정 — 동일 키 in-place 업데이트 [Codex 확정]

- **같은 키로 서명해 기존 설치자에게 in-place 업데이트한다. 앱 데이터는 보존된다.**
- **제거 후 재설치 안, 데이터 소실을 전제한 안은 미승인이다.**
- step1 최초본이 적었던 "키 전환 = 제거 후 재설치 = 데이터 소실" 서술은 **동일 키를 쓸 수 없게 된 경우에 한정**된다. 지금은 그 경우가 아니다.

#### 4.2.3 기록해 둘 의존성

- **이 `debug.keystore` 가 사실상 유일한 릴리스 서명 신원이다.** 이 파일을 잃으면 기존 설치자에게 업데이트를 보낼 수단이 사라진다. **백업·보관 위치 결정이 필요하며 별도 승인 사항이다.** (키 파일 내용·비밀번호는 이 문서에 기재하지 않는다. 위 표의 지문·DN·유효기간은 비밀이 아니다.)
- **Play 스토어는 debug 인증서로 서명된 APK 를 거부한다.** 따라서 이 경로는 **직접 APK 배포 전용**이다. 스토어 배포를 하려면 별도의 릴리스 키와 그에 따른 신원 전환 문제가 다시 생긴다.
- `app/build.gradle.kts` 에 `signingConfigs` 가 없다(1.5). 릴리스 빌드가 같은 키로 서명되도록 **명시적 signingConfig 설정이 필요하다** — 지금은 `assembleDebug` 산출물을 배포해 우연히 같은 키가 쓰이고 있을 뿐이다.
- **`versionCode` 는 gradle 의 현재 값(11)이 아니라 실제로 배포된 최고값을 확인한 뒤 증가시킨다.** Android 는 `versionCode` 가 낮으면 업데이트를 거부한다.

#### 4.2.4 설치 경로

- **`REQUEST_INSTALL_PACKAGES` 권한이 필요하다** — 현재 매니페스트에는 없다(1.5). 사용자 승인 경로와 **취소 경로**를 함께 설계한다(취소해도 앱은 계속 쓸 수 있어야 한다).
- **FileProvider 가 무조건 필요한 것은 아니다.** 설치 방식에 따라 갈린다:
  - **(A) 파일 Intent 방식** (`ACTION_VIEW`/`ACTION_INSTALL_PACKAGE` 로 APK 파일 URI 전달) — 다른 앱(패키지 설치자)에 파일을 넘겨야 하므로 `FileProvider` 와 `content://` URI 가 **필요하다**.
  - **(B) `PackageInstaller` 세션 스트림 방식** — 앱이 세션을 열고 APK 바이트를 **직접 써 넣으므로** 파일 URI 를 다른 앱에 넘기지 않는다. 이 경우 `FileProvider` 는 **필요하지 않다.**
  - 어느 쪽을 택할지는 구현 단계 결정이며, 그 결정이 `FileProvider` 필요 여부를 정한다. **이 문서에서 (A)를 전제로 단정하지 않는다.**

### 4.3 manifest 스키마

4.1 확정에 따라 아래로 확정한다. **서명 대상은 manifest 문서 전체이며**(4.1.2), 아래 필드는 모두 그 안에 있다.

| 필드 | 내용 | 비고 |
|---|---|---|
| 스키마 버전 | manifest 형식 자체의 버전 | 미래의 형식 변경을 클라이언트가 거부/무시할 수 있게 한다 |
| 플랫폼 | `windows` / `android` | 한 manifest 가 여러 플랫폼을 담든 플랫폼당 하나든, **플랫폼 식별이 서명 안에 있어야 한다** |
| 제품 버전 | 배포 버전 문자열 | 2(d) 의 **버전 비교 계약**을 따른다 — 성분 숫자 비교, 비숫자 접미사에서 중단. manifest 의 표기가 그 계약과 모순되면 안 된다 |
| 아티팩트 식별 | 다운로드 위치와 아티팩트 이름 | |
| 크기 | 바이트 | `Download` 완료조건(3.6)이 이 값과 대조한다 |
| SHA-256 | 아티팩트 콘텐츠 해시 | `Verify` 단계의 무결성 근거 |
| (Android) versionCode | 정수 | 4.2.3 의 제약이 걸린다 |
| 서명 | manifest 문서에 대한 detached 서명 | 본문 밖에 둔다 |

- **64 KB 절단은 이 스키마의 제약이 아니다.** 그 한계는 `directory_client.cpp:346-355` 의 것이고, manifest 는 4.1.1 의 **신규 WinHTTP 클라이언트**가 받는다. 따라서 manifest 크기를 64 KB 에 맞출 필요가 없다.
- 서명 검증이 실패하면 manifest 의 어떤 필드도 신뢰하지 않는다 — 버전 비교조차 하지 않는다.

### 4.4 서버 신규 엔드포인트

4.1·4.3 확정에 맞춰 아래로 확정한다.

- **manifest 조회 엔드포인트를 신설한다.** 현행 라우트 테이블은 `메서드 경로` 정확 일치이고 접두사 매칭이 없으므로(`server.js:564-585`) 새 키를 추가하는 형태가 된다.
- **아티팩트 자체는 디렉터리 서버가 스트리밍하지 않는 것을 기본안으로 한다.** 현행 서버에 정적 파일 서빙도 바이너리 GET 경로도 없고(1.4.1), 3.5 MB 급 파일을 Node 이벤트 루프로 흘리는 것은 릴레이·하트비트와 같은 루프를 공유한다. 아티팩트는 **HTTPS 로 접근 가능한 정적 위치**에 두고 manifest 가 그 위치를 가리킨다.
- **인증**: manifest 조회는 기존 두 인증 수단(Bearer 세션 / `x-host-token`, 1.4.2)을 재사용한다. 다만 **세션은 메모리 전용이라 서버 재시작으로 소멸하므로**(`server.js:490`), 업데이트 확인이 세션 만료로 실패하는 것은 정상 동작으로 취급하고 다음 주기에 재시도한다(3.1 의 `CheckRequested` 실패 처리와 같다).
- **남용 방지**: 로그 업로드의 계정/기기별 레이트 리밋(`server.js:346-349`)을 선례로 삼는다.
- **운영 도메인·실제 엔드포인트 URL 확정과 배포는 별도 승인 사항이다** (4.5).

### 4.5 "코드 준비완료" 와 "배포가능" 의 분리 [Codex 확정]

두 상태를 문서에서 섞지 않는다.

**코드 준비완료** — 이 설계로 구현·검증이 끝난 상태. 다음이 모두 성립할 때:

- WinHTTP HTTPS 클라이언트, manifest 파서·서명 검증, 업데이터 상태기계(3.1)가 구현되고 3.7 의 회귀로 덮인다.
- **테스트 키**로 서명한 manifest 로 전 경로가 통과한다. 테스트 키는 **격리된 테스트 전용이며 실배포 신뢰키로 절대 쓰지 않는다.**
- Android 쪽은 `signingConfigs` 설정과 `REQUEST_INSTALL_PACKAGES` 경로가 구현되고, 설치 방식(A/B, 4.2.4)이 결정돼 있다.

**배포가능** — 실제로 사용자에게 업데이트를 내보낼 수 있는 상태. 위에 더해 다음이 **모두 별도 승인**을 받아야 한다:

- **운영 서명키 생성·보관 위치·교체 절차** 결정. 바이너리에 내장할 공개키가 이 키의 것으로 확정되어야 한다.
- **Android keystore 백업·보관 위치** 결정 (4.2.3).
- **운영 도메인과 엔드포인트 URL** 확정, 그리고 아래 4.6 의 nginx vhost 작업.
- 실제 서버 배포. **이 문서 작성 시점에 실배포는 하지 않았고, 하지 않는다.**

### 4.6 서버 TLS 현황 — 5절 미확인 1번 해소 [검증용 실측]

검증용 Claude 가 NAS 를 read-only 로 확인했다:

- **nginx 가 :443 에서 LISTEN 중이고 TLS vhost 가 다수 있다** (`shotan.org` 및 하위 도메인), Let's Encrypt 인증서 보유 (`/etc/letsencrypt/live/shotan.org`, `/etc/letsencrypt/live/vpn.shotan.org`).
- **그러나 29180/8080 으로 프록시하는 vhost 는 없다.** 그리고 `REMOTE60_DIR_TLS_KEY`/`REMOTE60_DIR_TLS_CERT` 는 설정돼 있지 않다 → 디렉터리 서비스는 **:29180 평문으로 직접 노출**되어 있다(1.4.3 의 조건부 TLS 분기에서 http 쪽으로 떨어진다).

**따라서 HTTPS 추가는 인증서 구매 문제가 아니라 nginx vhost 설정 작업이다.** 인증서와 TLS 종단은 이미 있고, 디렉터리 포트로 가는 프록시 정의만 없다.

- 이것은 4.1.1 의 HTTPS 전송 전제를 **충족 가능하게** 만든다 — 새로 확보할 것이 아니라 설정할 것이다.
- **운영 도메인·엔드포인트 확정과 vhost 적용은 배포 단계 의존성이며, 이 문서는 실배포를 하지 않는다** (4.5).
